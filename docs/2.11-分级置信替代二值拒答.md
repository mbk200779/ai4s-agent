# 07 · 分级置信替代二值拒答

> 一句话：**把「能答 / 不能答」换成「已验证 / 需核对 / 证据不足」，并且逐句说清缺什么。**
> 拒答只在"一条都没检索到"时出现——其余情况一律作答 + 标注，把判断权交回读者。

## 1. 问题：二值拒答在科研场景里是错的

旧口径只有两种结局：答案通过校验，或者整条拒答。但科研用户读一段带引用的答案时，
脑子里的判断从来不是二元：

1. 原文直接写着这句话，我信，可以直接引用；
2. 原文有相关证据，但结论是推出来的（跨段、跨篇、跨表），得回去核一眼；
3. 原文里根本没有，这句话不能用。

把 2 折叠进 1，就是幻觉的来源——"看起来有引用"和"引用真的支持这句话"被混为一谈；
把 2 折叠进 3，则等于把本来可用的信息扔掉，用户还得自己重问一遍。
**三档不是"更细的 UI"，而是把推理链上本来就存在的三种状态显式化。**

顺带被修掉的是一个更隐蔽的问题：旧口径把"检索分低"也当成拒答理由。
于是用户看到"无法回答"时分不清是**库里没有**（事实）还是**检索没找到好片段**（系统能力）。
这两种情况的处理方式完全不同，混在一个按钮里，用户只能猜。

## 2. 三档判定规则（交付物 1）

### 2.1 档位定义

| 档位 | 含义 | 判定为真时用户该做什么 |
| --- | --- | --- |
| `verified` | 有直接原文证据，可据此判定 | 可以直接引用 |
| `needs_check` | 有相关证据，但需人工核对 | 回原文看一眼再决定 |
| `unsupported` | 没有找到能支撑这句话的原文 | 不要用这句话 |

`applicable=false` 单独留给闲聊/直答：那种回答没有句子要校验，塞进任何一档都是错的
（说"已验证"会把这个词稀释掉）。

### 2.2 句子级规则

先按"有没有证据"分两层，再在"有证据"里分深浅：

```
无角标                    → unsupported（no_citation：这句话没有引用标注）
有角标但全都没对上         → unsupported（no_match：片段里找不到能支撑这句的句子）
有至少一条证据对上了       → 进入下面的"深浅"判定
```

"深浅"用**有效支持度** `effective = max(字面分, 语义支持度)` 与一组"缺什么"的判据共同决定：

- `effective ≥ verified_score`（默认 0.55）**且** `missing` 为空 → `verified`
- 否则 → `needs_check`，并把 `missing` 逐条带出去

为什么取 `max` 而不是加权平均：两个分各自都有"确定"的场景——
数值/符号对上时字面分接近满分（语义模型反而可能因为句子长而偏低）；
中文改写英文原句时字面分接近 0（语义模型能到 0.9）。取平均会让两边都变弱。

### 2.3 整条回答的规则：最弱一句决定整体

| 情形 | 整体档位 |
| --- | --- |
| 一条都没检索到（`sources == []`） | `unsupported` + **完整拒答** |
| 所有句子都 unsupported | `unsupported`，但**作答保留** |
| 只要有一句 needs_check | `needs_check` |
| 只要有一句 unsupported（其余有据） | `needs_check` |
| 全部 verified | `verified` |

规则偏保守，但方向是对的：用户扫一眼"需核对"就该知道这段回答里有需要他亲自确认的地方，
而不是被"已验证"骗过去。

### 2.4 定位精度不参与分档

`sentence / cell` 能画框到句，`block / line` 只能画到一段。一开始我把它算进 `missing`，
结果本库锚点覆盖率只有 38%~59%，绝大多数正确引用被压成"需核对"——把"定位粗糙"
说成了"证据不足"。现在它单独放在 `claim.confidence.locate`：

- 不影响档位（证据句仍然是从 chunk 原文里切出来的真实句子）；
- 前端照样标注「块级定位」，阅读器只框到那一段；
- 只有 `ocr` 留在 `missing` 里，因为 OCR 的**文字本身**可能是错的，那是证据质量问题。

## 3. 信号从哪来

分档只用检索与锚点阶段已有的信号，**不在定档时再调大模型**——
多一次模型调用会让"置信"本身变成不可复现的东西。

| 信号 | 来源 | 用在哪条判据 |
| --- | --- | --- |
| 字面分 `match_score` | `anchor_select.score()`：词面 0.5 + 数值/符号 0.4 + 包含 0.1 | 有效支持度 |
| 语义支持度 `sem_score` | 多语言 MiniLM 的跨语言余弦，映射到 0~1 | 有效支持度 |
| 锚点精度 | `chunks.anchors[].precision` | `locate` / `ocr_precision` |
| 片段类型 | `chunks.chunk_type`（text / table / figure / reference） | `no_table` |
| 命中论文数 | `arxiv_id` 去重 | `single_paper` |
| 证据片段数 | `chunk_id` 去重 | `cross_section` |
| 检索融合分 | `routing.recall.top_raw_score` vs 策略阈值 | `weak_retrieval` |

### 3.1 为什么必须补一层语义核验

答案用中文写，原文是英文。字面分只认 ASCII 词与数字，于是
「BERT 的预训练用了 MLM 和 NSP」这种**完全正确**的中文结论，在原句上的字面分只有 0.25——
按字面线只能判 `needs_check`。`verified` 于是退化成"只有数值题能拿到"的一档。
（这条判断后来被实测修正了，见 3.3：影响是句子级的，不是题目级的。）

所以加了一层 `semantic.py`：`paraphrase-multilingual-MiniLM-L12-v2`（384 维、12 层），
懒加载单例 + 启动预热，一次问答批量 embed 所有 (claim, 证据句) 对。

选它的理由（实测）：

| 模型 | 维度 | 6~12 条短句耗时 | 备注 |
| --- | --- | --- | --- |
| 链路里已有的 e5-large | 1024 | 约 900~1400ms | 太重，会把总时长从 2s 拖到 3s；且它是**检索**模型，与索引绑定不能换 |
| **MiniLM-L12 multilingual** | 384 | **约 80ms**（单条 5ms） | 本身就是跨语言释义相似度训练出来的 |

校准（8 个正例 / 6 个负例，容器内实测）：

| 类别 | 余弦区间 |
| --- | --- |
| 同义改写 / 直译对 | 0.562 – 0.927 |
| 无关句对 | 0.008 – 0.330 |

两簇之间的空档很宽（0.33 → 0.56），所以把 `[0.35, 0.85]` 线性映射到 `[0, 1]` 作为
"语义支持度"，边界不会因为一两句措辞波动而左右横跳。映射而不是再卡一个语义阈值，
是为了让分档只依赖一条 `verified_score` 线——否则调阈值要同时改两个数，还容易改漏。

### 3.3 A/B：语义核验到底值多少

同样的 30 题、同一套判据，只把 `CONFIDENCE_SEMANTIC_ENABLED` 关掉再跑一遍：

| | 题级 verified / needs_check / unsupported | 句级 verified / needs_check / unsupported |
| --- | --- | --- |
| 开 | 8 / 11 / 9 | **18** / 7 / 27 |
| 关 | 8 / 11 / 9 | **13** / 11 / 26 |

结论要说清楚，否则这层就是"凭感觉加的"：

- **题级分布一模一样**。因为题级要求"每一句都 verified"，而模型平均每题有一句不带引用，
  题级 `verified` 本来就稀缺——**瓶颈在引用标注率，不在语义核验**。
- **句子级 5 条从 needs_check 变 verified**（占全部"有据句"的 20%），这正是它该起作用的地方：
  中文改写但确实对的句子，不再被误判成"要人工核对"。
- 所以它是值得留的，但别指望它改变题级分布。真正卡住题级 `verified` 的是 `no_citation`（第 8 节）。

### 3.2 缺什么：完整清单（`missing` 的 code）

| code | 什么时候报 | 文案模板 |
| --- | --- | --- |
| `no_citation` | 这句话没有 `[引#N]` | 这句话没有引用标注 |
| `no_match` | 有角标，但片段里找不到能支撑的句子 | 引用的片段里找不到能支撑这句话的句子 |
| `weak_match` | 有效支持度 < 验证线 | 证据句与原话的重合度只有 {score}，低于验证线 {threshold} |
| `no_table` | 断言含数值，但**一个数都不在**证据原句里，且无表格出处 | 数值 {numbers} 不在证据原句中，缺表格里的原始数据 |
| `entity_mismatch` | 断言里的专有名词在**被引用的整段正文**里都找不到 | 结论中的 {terms} 未在证据原句中出现，可能换了对象 |
| `no_experiment` | 断言含比较/效果表述，但证据里没有任何数值 | 结论含比较表述，但证据里没有对照实验或基线数值 |
| `cross_section` | 有推断连接词（因此/说明/意味着…），或证据来自 ≥2 处片段 | 证据由 {chunks} 处片段拼接而成，属于推断而非直引 |
| `single_paper` | 对比/综述题，但整条回答只覆盖 1 篇论文 | 只有 {papers} 篇论文支持，跨文献结论需再核一篇 |
| `ocr_precision` | 证据来自 OCR 页 | 定位来自 OCR，识别文本可能有个别错字 |
| `weak_retrieval` | 检索融合分低于该策略阈值 | 检索融合分 {top} 低于阈值 {threshold}，片段可能不是最佳出处 |

三条判据的边界是踩出来的，值得单独说明：

- **`no_table` 要求"一个数都不中"**，不是"缺一个就报"。断言里混杂着型号数字（`ViT-H/14` 的 14）、
  标准差（`88.55 ± 0.04` 的 0.04），按"缺一个"判会把正确的直引句全打成缺表格——实测 3 条错 2 条。
- **`entity_mismatch` 按整段判，不按这一句判**。证据句常常是中段的一句话，不会重复主语
  （"We mask 15% of tokens…" 里没有 BERT），按句判会误伤正确证据；按整段判仍然抓得住
  "问 TPU、原文写 GPU"这种真错配（`TPU` 在整段里确实没有）。
- **`single_paper` 判的是整条回答覆盖几篇**，不是这一句引了几篇。
  "ViT 用 JFT-300M，BERT 用 BooksCorpus" 拆成两句后每句只引一篇，按句判会把正常的对比
  答成"仅单篇支持"——30 题里误报过 11 次，改完剩 2 次。

## 4. 返回结构扩展（交付物 2）

`POST /api/v1/qa/ask` 与 SSE 的 `done` 事件都多了一组字段（两者结构完全同构）：

```jsonc
{
  "answer": "LoRA 可以把可训练参数减少 10,000 倍 [引#1: … p.5]。",
  "rejected": false,
  "claims": [                       // 逐句（与流式 claim 事件同一结构）
    {
      "claim_id": "c1",
      "span": [0, 42],
      "text": "LoRA 可以把可训练参数减少 10,000 倍。",
      "status": "supported",        // 证据级：校验过没过（05/06 口径）
      "level": "verified",          // 结论级：能信到什么程度（07）
      "level_label": "已验证",
      "reason": null,
      "missing": [],
      "confidence": {
        "level": "verified", "label": "已验证", "score": 0.9,
        "missing": [],
        "locate": { "precision": "block", "note": "块级定位（该片段未建立句级锚点）" },
        "signals": {
          "best_score": 0.9, "sem_score": 0.79, "effective_score": 0.9,
          "papers": 1, "precisions": ["block"], "kinds": ["text"],
          "numeric_claim": true, "comparative": false, "inferential": false,
          "caps_terms": ["LoRA"], "retrieval_weak": false
        }
      },
      "citations": [ { "index": 1, "status": "supported", "page": 5, "match_score": 0.9, "sem_score": 0.79, … } ]
    }
  ],
  "confidence": {                   // 整条回答
    "applicable": true,
    "level": "verified", "label": "已验证",
    "description": "原文有直接证据，可据此判定",
    "score": 0.9,
    "counts": { "claims": 1, "verified": 1, "needs_check": 0, "unsupported": 0 },
    "missing": [],
    "notes": ["全部 1 句都能在原文中直接找到对应句子"],
    "signals": { "sources": 6, "papers": 3, "top_raw_score": 0.31, "retrieval_weak": false,
                 "query_type": "point", "block_located": 1 },
    "config": {
      "version": "conf-v1.0.0", "prompt_version": "v1.0.0", "fingerprint": "fbb81a6199",
      "thresholds": { "verified_score": 0.55, "needs_check_score": 0.15, "cross_paper_min_sources": 2 },
      "labels": { … }, "descriptions": { … }
    }
  },
  "claim_stats": { "claims": 1, "verified": 1, "needs_check": 0, "unsupported": 0, "supported": 1 }
}
```

几个刻意的设计：

- **`status` 与 `level` 并存**。`status` 回答"引用校验过没过"，`level` 回答"这句话能信到什么程度"。
  它们不是同一件事：有据但需核对 = `supported` + `needs_check`。老日志老前端读 `status` 不会坏。
- **`signals` 原样带出**。档位必须可复核——看到 `level=needs_check` 的人应该能一眼看到
  "因为 effective 只有 0.42"，而不是只能相信系统的判断。
- **`missing[].code` 稳定、`text` 可读**。文案会改会翻译，但"缺表格"这个事实不会变；
  统计"30 题里有多少条缺表格"只能靠 code。
- **`config` 带 `version` + `fingerprint`**。见第 6 节。

流式侧：`claim` 事件直接带 `level / missing / confidence`，`done` 带 `confidence`；
`retrieval` 事件多一个 `retrieval_weak`，前端可以在正文出来之前就提示"检索偏弱"。

## 5. 拒答口径的改变

| | 06 及以前 | 07 |
| --- | --- | --- |
| 无检索结果 | 拒答 | 拒答（唯一入口） |
| 检索分低于策略阈值 | **拒答** | 照常作答，整条标 `needs_check` + `weak_retrieval` |
| 有片段但全部无据 | 拒答（部分策略） | 作答保留 + 全部标 `unsupported` |
| 闲聊 | 直答 | 直答（`applicable=false`） |

用 `REJECT_ON_LOW_SCORE=true` 可以复现旧口径，用于 A/B 对比"拒答率"这个指标。

**30 题实测**：旧口径下会有 3 题被拒答（`t4`/`o7`/`o8`），新口径下这 3 题照常作答，
最终都落在 `unsupported`——也就是说，放开拒答并没有换来"一本正经地胡说"，
只是把"我们试过了，但没找到"这件事说清楚了。

另外要说明：这次 30 题里**完整拒答一次都没触发**，因为融合检索在这套语料上总能返回 6~8 个片段。
这本身是个发现——"无命中"在真实系统里是极少数，旧口径实际上是靠"分低"在替它挡，
挡掉的同时也挡掉了 `unsupported` 与 `rejected` 的区别。

## 6. 阈值可配置 + 版本可追溯

| 配置项 | 默认 | 作用 |
| --- | --- | --- |
| `CONFIDENCE_VERIFIED_SCORE` | 0.55 | 有效支持度到这条线才可能 verified |
| `CONFIDENCE_NEEDS_CHECK_SCORE` | 0.15 | 低于它判无证据（与 `claim_min_evidence` 同源，但单独留键） |
| `CONFIDENCE_CROSS_PAPER_MIN_SOURCES` | 2 | 对比/综述题至少几篇才算 verified |
| `CONFIDENCE_SEMANTIC_ENABLED` | true | 关掉后只用字面分（中文结论会一律落到 needs_check） |
| `CONFIDENCE_SEMANTIC_FLOOR` / `CEILING` | 0.35 / 0.85 | 余弦 → 支持度的映射区间 |
| `CONFIDENCE_VERSION` | conf-v1.0.0 | 阈值版本号 |
| `REJECT_ON_LOW_SCORE` | false | 复现旧拒答口径 |

**0.55 是怎么来的**：本语料上直引句（claim 几乎逐字来自原文）的有效支持度落在 0.62~0.98，
跨句改写/只有关键词对上的落在 0.25~0.45，中间 0.45~0.62 基本没有样本。
0.55 是把边界放在两簇之间的空档里，不是取中位数。

**版本 + 指纹**：`version` 是人给的，`fingerprint` 是从阈值数值算出来的 sha1 前 10 位。
两个都要——`version` 用来对"我们对外宣称的配置"，`fingerprint` 用来抓
"有人改了 `.env` 但忘了 bump version"：这种情况下指纹会变，日志里立刻能看出来，
不至于把两套线的结果混在一起比较。每次问答的 `confidence.config`、provenance 记录里都存一份。

## 7. 前端三档标记（交付物 3）

三档在界面上是三种**看得见**的形态，而不是三种颜色的同一个东西。样式集中在
`frontend/src/components/answer/confidence.tsx` 一处定义（句子下划线、角标、汇总条、待核清单
四处都从它取），改一处不会漂移。

| 档位 | 正文装饰 | 角标 | 句末标记 | 汇总条 |
| --- | --- | --- | --- | --- |
| `verified` | 无 | 实心青绿 + `✓` | 无（避免满屏标签） | 青绿圆点「已验证」+ 说明 |
| `needs_check` | 琥珀**虚**线下划线 | 琥珀虚线边 + `?` | 「需核对 · 缺表格…」 | 琥珀「需核对」+ N 处待看 |
| `unsupported` | 红色**点**线下划线 | 灰色虚线、**禁用**（点进去只会落空） | 「证据不足」 | 红色「证据不足」+ 已保留说明 |

为什么 `needs_check` 用虚线而不是实线：实线在正文里像超链接，会被误认为"点开有别的页面"。
为什么 `unsupported` 的角标不可点：它本来就没落到任何句子，点了只会得到一个空弹窗。

「需核对」与「证据不足」都在句末留了**文字**标记，不只靠颜色——色盲用户与打印稿读不出来。
`verified` 不加句末标签是因为每句都挂一个会淹没正文，它的说明放在汇总条上。

点开汇总条会展开**待核清单**：每一条带档位徽标、原句、定位精度、支持度（含语义分）、
证据条数，以及"缺什么"的逐条说明。这是"不得静默降级"在界面上的落点——
置信不是一个小色块，而是可以逐句展开、能看到"为什么这句只到需核对"的账。

| 缺项 | 句数 |
| --- | --- |

`no_citation` 占绝对多数，是个协议层面的发现：模型在多句回答里常常有一两句不带 `[引#N]`

## 9. 踩坑记录

1. **`status` 与 `level` 混用会出人命**。`needs_check` 的句子在证据层是 `supported`，
   如果前端拿 `status` 上色，就永远看不到琥珀色。现在两套字段各管一段，`levelOf()` 统一兜底。
2. **块级定位算进缺项 → `verified` 名存实亡**。本库锚点覆盖率 38%~59%，把它算作降级理由后
   几乎所有正确引用都变 `needs_check`。拆到 `locate` 之后分布才正常（第 2.4 节）。
3. **`no_table` 用"缺一个就报"会误伤型号数字**。`ViT-H/14` 的 14、`88.55 ± 0.04` 的 0.04
   让正确直引句被判缺表格，3 条错 2 条。改成"一个数都不中"才稳。
4. **`entity_mismatch` 按句判会误伤主语省略**。证据句常不重复模型名，改按整段 chunk 判。
5. **`single_paper` 按句判误报 11 次**。对比题拆句后每句只引一篇是正常的，改按整条回答覆盖的论文数判。
6. **中文 claim 的字面分天然接近 0**。不是 bug，是分词器只认 ASCII；靠语义核验补，别去调分词器
   （调了会把 05 的句子选择也带偏）。
7. **不建锚点的片段被误判成"无证据"**。历史 chunk 里有相当比例没有句级锚点，直接判 unsupported
   会把"定位能力不足"报成"原文里没有"。现在退到 chunk 内现场切句（`anchor_select.select_in_text`），
   `precision=block`。
8. **`docker restart` 不会重读 compose 的环境变量**。换模型必须 `up -d --force-recreate`，
   或者用 `docker exec -e` 起临时进程（eval 脚本的 `--inprocess` 就是为这个加的）。
9. **e5-large 不能拿来当核验模型**。它是检索模型，与索引绑定；换成它要重建全库向量，
   而且单条 150ms，一次问答就多 0.9s。

## 10. 复现

```bash
# 1) 一次性接口看分档
curl -s --noproxy '*' -X POST localhost:8000/api/v1/qa/ask \
  -H 'Content-Type: application/json' \
  -d '{"question":"LoRA 把可训练参数减少了多少倍？","top_k":6}' \
  | python -m json.tool | sed -n '1,40p'

# 2) 流式：claim 事件里逐句看 level / missing
curl -sN --noproxy '*' -X POST localhost:8000/api/v1/qa/stream \
  -H 'Content-Type: application/json' \
  -d '{"question":"这几篇论文里，哪个报告的 ImageNet 准确率最高？","top_k":6}' \
  | grep -E '^event: (claim|done)' -A1 | cut -c1-400

# 3) 30 题分布
docker exec ai4s-api python -m scripts.eval_confidence --out eval/confidence_dist

# 4) 关掉语义核验做 A/B（结果见 3.3：题级不变，句级 verified 18 → 13）
docker exec -e CONFIDENCE_SEMANTIC_ENABLED=false ai4s-api \
  python -m scripts.eval_confidence --inprocess --out eval/confidence_nosem
```

产物：`backend/eval/confidence_dist.{md,json}`（主表）与 `confidence_nosem.{md,json}`（A/B 对照）。
两份 json 都保留了逐题的 `claims[].signals`，可以直接算"哪一句从哪一档变到哪一档"。
