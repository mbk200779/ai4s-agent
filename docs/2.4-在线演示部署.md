# 2.4 在线演示 —— 部署记录

> 对应大赛 2.4 节：可公网访问的在线演示地址 / 评审期间保持服务可用。

## 一、当前演示地址

```
https://demo.mabokai.site
```

- **固定域名**：Cloudflare 命名隧道（`cloudflared tunnel run --token`）+ 自有域名
  `mabokai.site` 的 `demo` 子域，容器重启后地址不变（早期用的快速隧道
  `surrey-tradition-bee-trails.trycloudflare.com` 已废弃，域名已回收）
- **这个地址为什么「不会变」**：域名是 Cloudflare 账号里的一条 CNAME，指向隧道 UUID；
  隧道本身靠 `.env` 里的 token 认证。重启容器 / 重启 Docker / 重启电脑 / 重建镜像 /
  换机器（改 token 即可）都只影响「能不能连上」，不影响域名本身。
  它与 `trycloudflare.com` 那类随机域名是两回事——后者每次重建换名、且 DNS 记录会被回收。
- **代价**：可用性依赖这台机器开机且 Docker 在跑（已配开机自启，见 §八）
- 入口页：`/`（文献上传）、`/qa`（问答）、`/library`（论文库）、`/writing`（写作辅助）、
  `/graph`（引用图谱）均可访问
- 无需登录（前端未做登录页，2.4「如需登录」一条不适用）
- **页面指纹**：公网拉回的 `/` 与 `localhost:8080` 逐字节相同（22642 B，
  `<title>AI4S 学术研究 Agent</title>`），确认隧道指向的就是本机这套服务

## 二、链路结构

```
评审浏览器
   │ https
   ▼
cloudflared 容器（ai4s-tunnel，出站隧道，无需公网 IP / 无需路由器端口映射）
   │ http://ai4s-gateway:80
   ▼
Nginx 网关（ai4s-gateway）
   ├── /api/*  →  api:8000 （FastAPI，超时放宽到 300s）
   └── /*      →  web:3000  （Next.js standalone）
```

容器均在 `2026-10-21-16-54-36_ai4s-net` 网络内，与原有 6 个服务同一 bridge 网络互通。

## 三、为什么要加这一层 Nginx 网关

**Next.js 的 `rewrites` 反向代理存在 30 秒硬性超时。**

实测（同一条请求）：

| 路径 | 结果 |
|---|---|
| 浏览器 → `localhost:3000/api/v1/writing/outline` | 30.08s 后返回 **500**，容器日志 `Failed to proxy ... ECONNRESET` |
| 浏览器 → `localhost:8080/api/v1/writing/outline`（经 Nginx） | 43s 后返回 **200** |

写作大纲/绘图生成依赖 LLM 推理，实测 40~90 秒，**经 Next.js 代理必然失败**。
网关把 `/api/*` 直连 FastAPI 并设置 `proxy_read_timeout 300s` 后问题消除。

> 该问题在本地直接访问 8000 端口时不复现，只有走前端代理才暴露，
> 属于上线前必须发现的坑；前端代码无需任何改动。

## 四、中文字体问题（已修复）

容器基础镜像 `python:3.11-slim` 不含 CJK 字体且无 fontconfig，
matplotlib 渲染中文标题会输出方框：`Accuracy□□□□□□□`。

修复分两处：

| 文件 | 改动 |
|---|---|
| `backend/Dockerfile` | 新增 `fonts-noto-cjk` 安装层（OFL 授权，可随仓库分发） |
| `backend/app/services/drawing_service.py` | 导入期显式 `addfont()` 并设置 `font.sans-serif` / `axes.unicode_minus` |

> 当前运行中的 `ai4s-api` 容器是**热补丁**（已把补丁后的 py 与 SimHei 字体拷入容器并重启）。
> `docker compose build api` 重建镜像后，上述源码与 Dockerfile 改动会自动生效，届时无需再打补丁。

## 五、运维命令

```bash
# 查看隧道与网关状态
docker ps --filter name=ai4s-tunnel --filter name=ai4s-gateway

# 查看隧道日志（命名隧道看「Registered tunnel connection」，域名不再变化）
docker logs ai4s-tunnel 2>&1 | grep -E "Registered tunnel connection|ERR"

# 隧道挂了：重启即可（域名固定，不用改材料里的地址）
docker restart ai4s-tunnel

# 后端整体重启
docker compose -f docker-compose.yml restart api worker

# 完全停止演示
docker rm -f ai4s-tunnel ai4s-gateway
```

## 六、风险与后续建议

| 风险 | 影响 | 建议 |
|---|---|---|
| **国内到 Cloudflare 边缘丢包** | 实测约 2/3 的请求 TCP 连不上，通的那次 1.5–2.1s 返回 | 现场演示一律用 `localhost:8080`；公网地址只作「回去再看」 |
| 依赖本机开机 + Docker Desktop 运行 | 关机/睡眠即断 | 电源设置改为「从不睡眠」，关闭自动更新重启 |
| Cloudflare 免费隧道有速率限制 | 大量并发可能变慢 | 评审期一般够用 |
| 本机上行带宽有限（家庭/校园网） | 首屏 22 KB 尚可，上传 PDF 会慢 | 演示前用本地文件，不现场传大文件 |

**已完成的升级**：原先的 `trycloudflare` 快速隧道（域名每次重启都变）已替换为
Cloudflare 命名隧道 + 自有域名 `demo.mabokai.site`，地址固定。若后续要换机器部署，
只需在新机器上带着同一个 `CLOUDFLARE_TUNNEL_TOKEN` 起 `cloudflared`，域名无需改动。

**关于「本机打开很卡、外部却 1 秒」**——这不是站点问题，结论有数据支撑：

| 观测 | 数据 |
|---|---|
| 本机直连（同一时段） | 6 次里 4 次 200，但耗时 3.7s / 8.7s / 10.1s / 12.0s，2 次超时 |
| 本机走快速隧道 | 域名解析直接 NXDOMAIN（DNS 记录被回收），0.01 秒失败 |

## 八、关机重启后的恢复（2026-11-05 改造）

### 改造前的问题

| 检查项 | 改造前 | 后果 |
|---|---|---|
| `docker-compose.yml` 的 `restart:` | 一个都没有（默认 `no`） | 重启后 6 个服务全停 |
| `ai4s-gateway` / `ai4s-tunnel` | compose 之外手工 `docker run` | 名字会与 compose 冲突 |
| Docker Desktop `AutoStart` | `false` | 登录后不自启 |
| 恢复手段 | 靠记忆敲 3~4 条命令 | 容易漏起网关或隧道 |

### 改造后

1. compose 中 8 个服务全部 `restart: unless-stopped`；
2. `gateway` 与 `tunnel` 纳入 compose，隧道挂 `profiles: ["tunnel"]`，
   token 读 `.env` 的 `CLOUDFLARE_TUNNEL_TOKEN`（`.env` 已在 `.gitignore`）；
3. Docker Desktop 的 `AutoStart` 置为 `true`；
4. 新增 `deploy/start-all.sh`。

### 日常用法

```bash
bash deploy/start-all.sh            # 开机后恢复，含构建确认与四条链路验收
bash deploy/start-all.sh --status   # 只体检，不做变更
bash deploy/start-all.sh --no-build # 跳过镜像构建，最快
bash deploy/start-all.sh --rebuild  # 强制重建 api/worker
```

单独操作时等价于：

```bash
docker compose --profile tunnel up -d      # 起全部（含隧道）
docker compose up -d                       # 起服务但不碰隧道
```

### 一个必须注意的历史包袱

`ai4s-api` 曾经是热补丁容器（字体与 `drawing_service.py` 直接拷进容器内）。因为
`backend/Dockerfile` 与源码里的字体修复已经就位，**只要镜像重建一次**，热补丁就固化了；
否则容器一旦被 compose 重建，中文图表会变回方框。`start-all.sh` 默认会先
`docker compose build api worker` 把这件事做掉，命中缓存时只要几秒。

### 仍然存在的限制

隧道方案的本质是「把本机作为源站向外打洞」，因此：

- 关机 / 睡眠 / 断网 / 退出 Docker → 域名返回 **530**（Cloudflare 边缘正常，找不到隧道连接）
- 面板上点「刷新令牌」→ 容器内旧 token 失效 → 同样 530，且需同步改 `.env`
- 需要 7×24 在线时，应把容器迁到云服务器，而不是继续依赖本机

## 九、2026-11-09 重启实测：两个新坑

按要求真实走了一遍「关机 → 开机 → 恢复」，`deploy/start-all.sh --no-build` 第一次执行即报错：

```
✗ Container ai4s-web Error dependency failed to start
✗ compose up 失败
```

### 坑 1：Next.js 只绑容器 IP，健康检查永远失败

`ai4s-web` 一直是 `unhealthy`，但**网站本身是好的**。证据：

| 探测方式 | 结果 |
|---|---|
| 容器内 `curl localhost:3000` | 连接被拒绝 |
| 从 `ai4s-api` 访问 `http://web:3000/` | **200** |
| 容器内监听地址 | `172.22.0.7:3000`（**没有 0.0.0.0**） |

原因：Next.js standalone 服务默认绑定 `$HOSTNAME`，而容器里 `HOSTNAME` 是容器 ID，
于是它只监听自己那个 IP。外部经 `web:3000` 访问一切正常，唯独健康检查探 `localhost` 必然失败。
后果是 `web` 永远 unhealthy → 依赖它的 `gateway`、`tunnel` **根本不会启动**，公网自然是 530。

修复（`docker-compose.yml` 的 web 服务）：

```yaml
    environment:
      PORT: "3000"
      HOSTNAME: "0.0.0.0"    # 关键：否则只监听容器 IP
```

改后 `docker compose up -d --no-deps --force-recreate web`，6 秒转 healthy。

### 坑 2：celery 健康检查超时太紧

`ai4s-worker` 报 unhealthy，但健康检查的输出里明明有 `pong`：

```
Health check exceeded timeout (10s): -> worker@xxx: OK
        pong
```

`celery inspect ping --timeout 5` 自身要 5 秒，加上解释器启动接近 10 秒，正好卡在
`timeout: 10s` 边界上。改成 `interval: 30s` / `timeout: 25s` 后 20 秒转 healthy。

### 坑 3（脚本层面）：并行构建导致依赖装两遍

`docker compose build api worker` 会并行构建两个服务，二者共用同一 Dockerfile 却
互不共享缓存，于是 pip 依赖被完整装了两遍。无缓存时实测 18 分钟还没结束，且因为
构建输出被重定向到文件，终端看起来像卡死（Git Bash 最后直接「未响应」）。

现在的处理：`start-all.sh` **默认不构建**；需要构建时用 `--rebuild`，脚本会串行
`build api` → `build worker`（第二个命中第一个的缓存），并把日志实时打到终端。

### 坑 4：Git Bash 下 `curl -o /dev/null` 会让探测误报

在 Git Bash 里写 `/dev/null` 有时会触发 `curl: (23) client returned ERROR on write`，
导致 HTTP 码被记成 `000`，看起来像站点挂了。脚本里已统一改为写真实临时文件。

### 关于本机到 Cloudflare 的链路抖动

同一个域名，从这台机器测会出现 200 与 000 交替，但源站 Nginx 日志显示请求**已到达并返回 200**：

```
04:31:45 GET / HTTP/1.1" 200 5493  "curl/8.21.0" "120.85.43.221"
```

且同一次测试中真实浏览器（Edge）能正常打开并渲染。判断为本机出口（共享 IP、
国际链路抖动）问题，不是服务端问题；外部访客走自己的网络，不受影响。
若演示当天出现大面积打不开，优先怀疑本机网络，可先用手机流量交叉验证。

## 十、备用入口：临时快速隧道（按需生成）

**先说结论：这条链路不能当「固定链接」用，连「临时稳定」都保证不了。**

2026-11-12 10:0x 实测：容器 `Up`、隧道连接注册正常、日志无错误，但它的域名在
`getaddrinfo` 上直接 **NXDOMAIN**——DNS 记录被 Cloudflare 回收了，此时 `curl` 0.01 秒
就失败。过几分钟再查又可能恢复。也就是说这类域名的「会变」之外还有「会消失」，
不可用于任何需要长期有效的场合。

主域名 `demo.mabokai.site` 的**正常**表现是 1–2 秒返回；但 2026-11-12 上午本机复测
发现有一半请求会卡到超时。**已经排除**「某个边缘 IP 坏了」这个假设：

| 边缘 IP | 结果 |
|---|---|
| `172.67.137.40` | TLS 0.51s 建连成功；外部节点（香港 / 新加坡 / 奥地利 / 西班牙）200，0.79–1.61s |
| `104.21.7.182` | TLS 0.52s 建连成功；外部节点（加拿大 / 日本 / 德国 / 俄罗斯 / 美国）200，0.40–0.95s |

两个 IP 的 TLS 都能通，慢在数据传输阶段；同一时刻 11 个外部节点 10 个 1 秒内拿到
完整的 22642 B（详见 §七）。所以瓶颈是本机出口的吞吐，不是隧道、不是源站、也不是域名。

**临时兜底做法**：再起一条 Cloudflare 快速隧道（`trycloudflare`），它的域名落在
`104.16.x.x` 段，实测 3~4 次全部 1 秒左右返回。已封装成一个脚本，三条命令：

```bash
bash deploy/backup-tunnel.sh          # 重建隧道，自动等到能访问并打印地址
bash deploy/backup-tunnel.sh status   # 随时查回当前地址（不动容器）
bash deploy/backup-tunnel.sh stop     # 删掉容器，域名随之失效
```

脚本内部做的事（想手工执行也可以照这个顺序）：

```bash
docker run -d --name ai4s-tunnel-backup \
  --network 2026-10-21-16-54-36_ai4s-net --restart unless-stopped \
  cloudflare/cloudflared:latest tunnel --no-autoupdate --url http://gateway:80

# 从日志里取这次分配到的域名（每次启动都不一样）
docker logs ai4s-tunnel-backup 2>&1 | grep -oE "https://[a-z0-9-]+\.trycloudflare\.com" | head -1
```

**两个必须知道的时序问题**（2026-11-12 实测踩到过）：

1. **域名拿到 ≠ 能访问。** 新域名的 DNS 大约要 20–40 秒才生效，这期间解析直接返回
   NXDOMAIN，`curl` 0.01 秒就失败——看起来像"隧道坏了"，其实只是还没传播完。脚本因此
   自检 15 次 × 4 秒，最多等 60 秒。
2. **容器会自己退出。** 上一次用的 `--restart no` 在 13 分钟后被 SIGTERM 停掉（日志
   `Initiating graceful shutdown due to signal terminated`），链接随即变成 530。
   现在改成 `--restart unless-stopped`，至少容器能自己活过来；但**重建后的域名是新的**，
   旧链接必然失效，需用 `status` 查回。

**这套链路能做什么、不能做什么**

| 项 | 说明 |
|---|---|
| 能做 | 临时给评审/队友一个能打开的地址；主域名卡住时用它救场；测 API 与页面是否同源可用 |
| 不能做 | **容器重启即换域名**，不能写进提交材料；没有固定域名，无法长期挂着 |
| 访问方式 | 浏览器直接打开，无需登录；接口同源（`<该域名>/api/v1/...`），与主域名共用同一套后端 |
| 生成所需输入 | 只需要本机 Docker 与现有镜像 `cloudflare/cloudflared:latest`，**不需要任何账号或 token** |
| 输出形式 | 一段 HTTPS 域名（`https://<三到四个随机词>.trycloudflare.com`），出现在容器日志 `Your quick Tunnel has been created!` 那一行 |

同一时段两条链路的实测对比（2026-11-12 09:50 / 10:05，直连、不经过代理）：

| 链路 | 实测结果 |
|---|---|
| `demo.mabokai.site`（命名隧道 / http2） | 5.2s、8.0s（截断）、超时、1.9s —— 不稳定 |
| 快速隧道（`trycloudflare`）09:50 | 1.26s、1.03s、0.99s、1.11s |
| 快速隧道（`trycloudflare`）10:05 | 1.84s、1.32s、1.56s、1.84s，均 22642 B 与本地一致 |

另外验证过：把命名隧道的协议从 http2 换成 QUIC 并没有改善（四条连接就绪后测 4 次，
0 次完整返回），所以 `docker-compose.yml` 里仍然是 `--protocol http2`，没有改动。
根因是**客户端到某一片 Cloudflare 边缘 IP 的路径**，换隧道协议绕不过去。
