# 2.8 · 查询理解与检索分流

> 目标：不同问法走不同检索策略，停止用一套 top-k 打所有问题。
> 代码落点是 `services/rag/`（新建 4 个模块）+ `retrieve` 落点、`qa_service` 接线。

## 一、改造前的问题

分流之前，所有问题走同一条路：`dense + sparse → RRF(k=60) → top_k`。
这条路对"解释 self-attention 怎么算"是正确的，对下面三类问题都是错的：

| 问题 | 单一路径错在哪 |
|---|---|
| 「β2 设为多少」 | 排序信号是语义相似度。附录里那张超参大表语义上也"很像"，还常常排在正文实验设置段前面——而真正的答案只有一行 `β2 = 0.98` |
| 「BERT 与 Transformer Encoder 的继承关系」 | 单轮召回按分数取前 8，很容易被一篇论文刷满。两篇都要，而且是**成对**要 |
| 「原文里 "warmup_steps = 4000" 出现在哪」 | 这是**字面**问题，向量相似度对它没有帮助。字面完全一致的片段反而可能被排到第 5 位 |

一句话：**召回的目标不是"最像 query 的 k 段"，而是"能回答这类问题的 k 段"，这两者只在某些问法下重合。**

## 二、分类器：规则 6 : 小模型 4，全程 300ms 预算

```
question
   │
   ├─ 规则表（25 条正则，0 延迟）──► 每类得分 + 命中证据
   │        └ 置信度 ≥ 0.82？─────────── 是 ──► 直接定类型
   │
   ├─ 本地原型分类器（fastembed 编码 1 条 query，~20ms）
   │        └ 与 46 条原型句比余弦，min-max 归一到 [0.62, 0.90]
   │
   └─ 加权融合 0.6·规则 + 0.4·原型 ──► 置信度 < 0.45 ──► generic（分流前行为）
```

### 为什么小模型不是 LLM

实测用 LLM 做一次 JSON 分类要 **400~900ms**，直接违反 300ms 约束。
换成"本地 embedding 原型分类器"后成本只剩**一条 query 向量**：原型句（46 条）向量算一次常驻进程。
它补的是规则写不到的说法（"这两种架构各自的取舍是什么"里没有任何比较关键词），
又能干净降级：模型加载失败 → 纯规则，`trace.degraded=true` 且写明原因。

### 置信度怎么算

```python
confidence = 0.5 + 0.45 * ((top - second) / (top + second))   # 上限 0.95
```

只看**第一名比第二名强多少**，不看绝对值。两条分数接近 = 判不准 = 该退 generic。
这个数不参与除阈值外的任何决策，只用于 trace 展示和"要不要调小模型"。

### 规则表（`rag/rules.py`，节选）

| 组 | 规则 id | 权重 | 判据 |
|---|---|---|---|
| 闲聊 | `chitchat-greet` / `-self` / `-ack` / `-thanks` | 1.0 / 0.9 / 0.7 / 0.55 | 纯问候、问助手自身、简短应答、致谢 |
| 点查 | `point-beta` | 0.95 | 点名 β1/β2/ε |
| | `point-hyper` | 0.75 | 学习率、warmup、dropout、batch size、权重衰减… |
| | `point-hardware` | 0.70 | GPU/P100/V100/A100/H100、显存、硬件配置 |
| | `point-chart` | 0.60 | 图/表/公式/算法 + 编号 |
| | `point-metric` / `-value` / `-dim` | 0.55 / 0.45 / 0.40 | BLEU/F1/困惑度、多少/取值、维度/头数/层数 |
| 对比 | `compare-diff` | 0.90 | 差异、区别、异同、优劣、vs |
| | `compare-multi` | 0.80 | 这两篇/三篇/几篇/跨论文 |
| | `compare-with-in` | 0.70 | "A 与 B 的差异"（补 `compare-diff` 抓不到的句式） |
| | `compare-relation` / `-vs` | 0.60 / 0.65 | 继承、演进、借鉴；vs / 和…相比 |
| 综述 | `survey-word` | 1.00 | 综述、研究现状、发展脉络、survey |
| | `survey-enumerate` / `-summarize` | 0.70 / 0.50 | 有哪些方法、分几类；总结、梳理、概览 |
| 定位 | `nav-original-mention` | 1.00 | "原文/正文 … 有没有提到/出现" |
| | `nav-where` | 0.95 | 哪一页、第几节、何处 |
| | `nav-which-paper` | 0.85 | "哪篇论文提到 X" |
| | `nav-original` / `-mention` / `-source` | 0.80 / 0.75 / 0.70 | 原句/原话；是否提到；出自 |

三条防刷分/防误判的规则：

- 同一类型最多计 3 条规则（长问句不能靠数量堆分）；
- 每条规则对同一问句只记一次命中；
- 问句出现学术信号词（论文/模型/实验/attention…）时，**闲聊规则权重 ×0.15**——
  否则"你好，帮我看看这篇论文的 β2"会被判成闲聊。

### 原型独占判断的三道门槛

规则一条都没命中时，判断完全交给小模型，风险最大，因此额外设三道闸：

1. `top_sim ≥ 0.80`（相似度得真高）；
2. `top_sim - second_sim ≥ 0.02`（不能贴得太近）；
3. **结构校验**：判为 compare 时，问句里至少要有 2 个实体或命中"这几篇"这类全称指代。

第 3 条是踩坑加的：`BERT 的预训练任务是什么` 规则零命中，被原型判成 compare（0.88），
结果白跑 3 次检索、还召不回任何第二篇。看到"像对比"不等于"能对比"。

## 三、五条检索策略（`rag/strategies.py`）

### 3.1 point：赋值形态优先 + 稀疏加权

```
hop1  dense + sparse 各取 40 条，加权 RRF（dense 0.38 / sparse 0.62）
hop2  按 ①参数名≈数值 赋值形态 ②表格/实验设置段 ③图表编号 重排
hop3  同名异义去噪：首条已有赋值证据时，剔掉别的论文里提到同一符号的片段
```

**关键信号是"参数名 ≈ 数值"的赋值形态，不是"这一段是表格"。**
附录里的超参大表几乎必然是表格，只按 `kind=table` 加权会把附录顶到首位；
而只有正文实验设置段会写成 `β1 = 0.9, β2 = 0.98 and ϵ = 10−9`。
所以：

- `_value_assignment_score()`：参数名后 24 字符内出现数字 → +0.50（最强信号）；
- `POINT_TABLE_BOOST` 从 0.34 降到 0.15（表格只是弱证据）；
- `POINT_REFERENCE_PENALTY` 0.22 → 0.35，且**参考文献片段不给赋值分**——
  参考文献里那些"β2 = 0.98"式的排版噪声不该参与排序。

漂移教训：`extract_numbers` 一度把 `beta2` 里的 `2` 当成"用户关心的数值"，
于是"片段里有数字"就加分——几乎每段都有数字，这个加成等于给所有结果发同等奖励。
现在 `_NUMBER_RE` 用 `(?<![A-Za-z0-9])` 排除紧贴字母数字的情况，单个数字也直接丢弃。

### 同名异义：把"β2"当成一个符号，而不是一段语义

语料里同时有优化器论文和光纤论文时，两边的 `β2` 是两件事（二阶矩衰减率 vs 色散系数）。
检索没问题——两段都真的含 `β2`；错的是**把它们一起塞进上下文**，
于是 LLM 会去引光纤那篇的 `β2 = −20ps/nm/km`。实测就发生过。

hop3 的处理：首条已经拿到赋值证据、且问题没有点名多篇时，
只保留首条所在论文的相关片段，把其他论文里提到同一符号的片段剔掉，
并在 trace 的 `params.dedup_same_symbol` 与 hop3 里写清剔了哪几条。
只对高区分度参数名（β1/β2/ε/warmup/dropout/batch size/…）生效，
`hidden size` 这种用单字母 `d` 表示的参数名不进这个名单——`d` 到处都是，按它去噪会误删正文。

### 3.2 compare：三跳，不做单轮

```
hop1  实体消解：把问题里的名字映射到具体论文（标题权重 2 / 正文画像权重 1）
hop2  逐篇受限召回：每篇单独 filter={arxiv_id}，保证每篇都有代表片段
hop3  成对交错输出：A1,B1,A2,B2…  让上下文中两篇的观点天然相邻
```

hop1 消解失败不退化：改为先全局召回，再按"各篇出现次数"挑出主论文，二次受限召回。
这就是多跳的第二跳——**第一跳失败不能直接掉回单轮**，否则"能对比"这件事就丢了。
trace 里 hop1 会写明 `定位论文` 还是 `实体消解失败，改由召回分布定位主论文`，
hop3 会把前 6 组配对（arxiv_id + 章节 + 页码）列出来。

### 3.3 survey：广度召回 + 去重（聚类交给步骤 08）

```
hop1  dense + sparse 各取 4×top_k（BREADTH=4）
hop2  按（论文, 章节）去重，每章最多留 2 段，输出 2×top_k
```

这里只解决"覆盖够不够广"，不做归类。把 285 个片段压成几个主题是步骤 08 的事，
在这一层做会把它和检索耦合在一起。

### 3.4 nav：全文精确匹配 + 段落定位

```
hop1  对语料逐片段做归一化子串扫描（去空白/标点差异），命中锚点越长分越高
hop2  字面命中不足 top_k 时，补稀疏召回，但分数压 ×0.45（不许抢精确匹配的位置）
```

锚点按可信度排序：引号里的片段（≥2 字符）> 问题里的拉丁实体（≥4 字符）> 数字（≥3 字符）。
中文长句不做整句子串匹配——PDF 抽出来的正文会断行、缺空格，整句几乎必 miss，
真正要定位的那句通常就在引号里。

命中片段会切一段 ±120 字符的 `snippet` 写进 Citation，
前端能直接展示"这一句在第 7 页，上下文是……"。

### 3.5 chitchat：不检索

直接返回固定话术，`results=[]`、`hops=[{hop:0, action:"跳过检索"}]`。
分流前"你好"会召回 8 段毫无关系的正文，然后被拒答逻辑判成"库中无相关内容"——
两类错误叠在一起，用户看到的是一个莫名其妙的拒答。

### 3.6 generic：兜底，逐字复用旧路径

`run_generic()` 调用的就是分流前的 `dense + sparse + RRF(60)`，
**不是重写出来的另一套代码，而是同一份代码**。
所以"分流前后对比"是干净的：基线不是仿制品。

## 四、routing trace 结构

每次问答都会把这条 trace 写进响应体 `routing` 字段与 provenance 记录：

```jsonc
{
  "query": "β2 设为多少",
  "search_text": "what is the value of beta2",   // 中文问题先翻成英文再检索
  "type": "point", "type_label": "点查", "confidence": 0.95,
  "classifier": {
    "method": "rules",            // rules | rules+prototype | fallback | forced:xxx
    "latency_ms": 0.1, "budget_ms": 300, "degraded": false, "degrade_reason": null,
    "rule_hits": [{"rule": "point-beta", "type": "point", "weight": 0.95,
                   "note": "点名 Adam 的 β1/β2/ε", "evidence": "β2"}],
    "prototype": {"used": false}   // 用上了则有 top3 相似度 + margin + build_ms
  },
  "slots": {"hyper_terms": ["beta2"], "numbers": [], "entities": [], "chart_refs": [], "quoted": []},
  "strategy": {
    "name": "point_boost_sparse", "label": "表格与实验设置段优先 + 稀疏加权",
    "params": {"top_k": 8, "rrf_k": 60, "dense_weight": 0.38, "sparse_weight": 0.62,
               "candidates": 40, "table_boost": 0.15, "value_assign_boost": 0.5},
    "latency_ms": 38.6,
    "hops": [{"hop": 1, "action": "dense+sparse 召回", "dense": 40, "sparse": 40},
             {"hop": 2, "action": "按表格/实验段/图表编号加成重排", "boosted": 3},
             {"hop": 3, "action": "同名异义去噪（只留赋值证据）",
              "dropped": [{"arxiv_id": "upload_8bb2…", "page": 2, "why": "其他论文提到同一符号（同名异义）"}]}],
    "notes": [],
    "direct": false,
    "reject_threshold": 0.0          // 命中赋值形态 → 证据口径，直接放行
  },
  "recall": {"returned": 8, "papers": 3, "sections": 6, "kinds": {"text": 6, "table": 2},
             "top_score": 1.46, "top_raw_score": 0.0153,
             "paper_list": [{"arxiv_id": "1706.03762", "title": "Attention Is All You Need"}]},
  "top_k": 8, "rrf_k": 60, "total_ms": 61.5,
  "fallback": {"used": false, "reason": null, "label": "点查"}
}
```

两个字段值得单独说：

- **`recall.top_raw_score`**：`score` 是归一化+加成后的相对分，最大值恒为 1，
  拿它判拒答会永远判"有把握"。所以原始 RRF 分单存一份，拒答只看这个绝对量。
- **`strategy.reject_threshold`**：各策略的"什么算有把握"口径不同，分两种：

  | 口径 | 适用 | 判据 |
  |---|---|---|
  | 分数口径 | generic、point 的常规情况 | 原始融合分 ≥ `RRF_MIN_SCORE × (dw+sw)/2`，即"两路都召回得不错" |
  | 证据口径（阈值 0） | point 命中赋值形态、nav 字面命中、compare/survey 覆盖到 ≥2 篇 | 拿到了比分数更硬的东西，直接放行 |

  为什么必须有证据口径：RRF 分数衡量的是"两路检索是否一致"，不是"库里有没有这个内容"。
  这条线上踩了三个坑，都是同一个病根——**拿分数的尺子去量别的东西**：
  1. 点查把 sparse 权重调到 0.62 后，两路都命中的上限从 0.033 掉到 0.016，
     若阈值不同比缩放会集体误拒；缩放之后又出现"0.0149 vs 0.0150"这种一线之差，
     同一个问题换个译文就从能答变成拒答。正文里明明写着 `β2 = 0.98`，却因为分数差 0.0001 拒答，是尺子用错了。
  2. compare 逐篇受限召回（`filter=arxiv_id`）把候选压到单篇，分数上限天生只有全库召回的一半，
     拿同一把尺子量必然把"这三篇的方法有何差异"判成查不到。
  3. nav 原来只要"问句里有锚点"就放行，等于永不拒答；反过来，有锚点却一个字都没匹配上，
     恰恰是"库里没有这句话"的表现。现在改成看**字面命中数**。

  修正之后，18 条评测集上"分流后新增误拒"为 0（`scripts/check_reject_threshold.py` 可复核）。

前端 `components/RoutingTrace.tsx` 默认收起，一行显示
`POINT · 点查 | point_boost_sparse | 规则命中 · 0.1ms · 召回 8 段 / 3 篇`，
点开后按"策略 → 规则 → 原型 → 槽位 → 每一跳 → 召回 → 降级原因"逐层展开。
兜底与降级都带可见标签，`fallback.used=true` 时显示"沿分流前行为"。

## 五、分流前后召回对比（`backend/eval/routing_both.md`）

数据集 `eval/routing_queries.json`：18 条，覆盖五类 + 2 条 generic 兜底，gold 为（论文 + 页码）。
基线 = `RetrievalService.search()`（分流前唯一路径），分流侧 = `RAGRetriever.route()`。

| 侧 | hit@k | MRR | 平均耗时 | 论文覆盖(对比/综述) | 类型准确率 | 分类耗时 均值/峰值 |
|---|---|---|---|---|---|---|
| 分流前 | 88.9% (16/18) | 0.648 | 206.9 ms | 0.8333 | — | — |
| 分流后 | **100.0% (18/18)** | **0.931** | 137.4 ms | **0.9286** | **100%** | 12.1 / 95.1 ms |
| 差值 | +11.1% | +0.282 | −69.5 ms | +0.095 | | |

提升集中在三处：

| 类别 | 典型条目 | MRR 前 → 后 | 原因 |
|---|---|---|---|
| 点查 | `p-beta2` | 0.00 → 1.00 | 赋值形态加权把正文实验设置段顶到第 1（原 top1 是附录超参表） |
| 点查 | `p-warmup` / `p-vit-batch` | 0.17 → 1.00 / 0.50 → 1.00 | 同上 + sparse 权重上调 |
| 定位 | 三条 `n-*` | 0.50 → 1.00 | 字面精确匹配，不再靠语义相似度猜 |
| 闲聊 | `ch-hello` | ✗ → ✓ | 不检索，不再把 8 段无关正文当召回 |

**没有下降的部分**：两条 generic 兜底的 MRR 与分流前逐位一致（1.00 → 1.00、0.25 → 0.25）。
这是"不得因为分流导致原有单篇问答效果下降"的直接证据——兜底走的就是原路径。

分类耗时均值 12.1ms、峰值 95.1ms，全部落在 300ms 预算内——但这是把 ONNX 线程数显式定成 8
之后的结果（见下）。定之前同一批问句均值 46.8ms、峰值 395.8ms，"规则判不准"的那几条会稳定超预算。

### 一个与分类无关、但决定分类能否达标的发现

`fastembed` 默认让 onnxruntime 按核数开线程。16 核机器上，**同一句短文本**：

| 线程 | 单条 query | 20 条长文本批量 |
|---|---|---|
| 不指定（按核数） | 197~350 ms | 8.8 s |
| 1 | 128 ms | — |
| 2 | 61 ms | 12.5 s |
| 4 | 45 ms | 6.2 s |
| **8** | **40 ms** | **4.4 s** |
| 12 | 70 ms | 5.0 s |

线程越多越慢，是因为单条短文本的计算量撑不起线程调度开销。这条对两件事同时生效：
分类延迟（300ms 预算）与长文档解析（embedding 占总时长约九成）。
所以 `EmbedderService` 显式传 `threads=settings.embed_threads`（默认 8，环境变量可覆盖），
不做"让它自己按核数选"。改前改后的评测数字就是上表里的 46.8/395.8ms → 12.1/95.1ms。

## 六、自检

三条自检标准，均通过：

| 自检 | 结果 |
|---|---|
| 「β2 设为多少」命中实验设置段 | `point`（conf 0.95，命中 `point-beta`），top1 为 Attention §5.3 正文第 7 页（`β1 = 0.9, β2 = 0.98 and ϵ = 10−9`）；端到端答案为 `β2 = 0.98 [引#1: Attention is All You Need p.7]` |
| 「BERT 与 Transformer Encoder 的继承关系是什么」两篇都召回并配对 | `compare` 多跳：hop1 定位到 `1810.04805` + `1706.03762`，hop2 逐篇受限召回，hop3 `pairs=3`（召回 4 篇） |
| 「这三篇的方法有何差异」走多跳 | `compare` + `compare_multi_hop`，4 跳齐全（定位 → 分布定位主论文 → 重排 → 成对交错），非单轮 |

第三条的细节值得写下来：问句里没有拉丁实体，"这三篇"又不在 `_ALL_SCOPE_RE` 的词表里，
所以 hop1 实体消解失败——但策略没有退回单轮，而是改由召回分布挑主论文继续跳。
trace 的第二跳会明确写"实体消解失败，改由召回分布定位主论文"，不会假装消解成功。

复现命令：

```bash
docker exec ai4s-api python -m scripts.eval_routing --mode both --top-k 8 \
  --json-out eval/routing_both.json --md-out eval/routing_both.md
```

## 七、落点与配置

| 文件 | 作用 |
|---|---|
| `services/rag/taxonomy.py` | 类型枚举、策略元信息、全部阈值常量（一处改、全局生效） |
| `services/rag/rules.py` | 规则表、槽位抽取、原型句 |
| `services/rag/query.py` | `QueryRouter.analyze()`：规则 → 原型 → 兜底；原型向量后台预热 |
| `services/rag/strategies.py` | 五条策略 + generic，返回 `StrategyResult` |
| `services/rag/retrieve.py` | `RAGRetriever.route()`：派发 + `_build_trace()` |
| `api/v1/endpoints/rag.py` | `POST /rag/route`（可强制类型调试）、`GET /rag/rules`（规则表） |
| `app/main.py` | 启动时 `warmup_router()`：后台线程建原型向量，不阻塞启动 |
| `app/services/embedder.py` | 显式 `threads=8`（`EMBED_THREADS` 可覆盖），分类与解析共同受益 |
| `scripts/eval_routing.py` | 分流前后对比评测（hit@k / MRR / 论文覆盖 / 类型准确率） |
| `scripts/check_reject_threshold.py` | 拒答口径对照：同一条问句在分流前后的最佳原始分与阈值并排打印 |
| `frontend/src/components/RoutingTrace.tsx` | trace 展开面板 |

全部阈值集中在 `taxonomy.py`，调参不需要翻策略代码：

```python
MIN_CONF = 0.45            # 低于此值退 generic
STRONG_CONF = 0.82         # 高于此值不再调小模型
POINT_SPARSE_WEIGHT = 0.62 # 点查的稀疏权重
POINT_VALUE_ASSIGN_BOOST = 0.50
COMPARE_MAX_PAPERS = 4
SURVEY_BREADTH = 4
NAV_MIN_MATCH_CHARS = 8
```

## 八、已知边界

1. **冷启动首条查询会慢**：原型向量后台预热（实测 6.4s，含 ONNX 首次加载）；
   预热完成前到达的请求自动跳过小模型，trace 记 `prototype_warming`。
   这是有意的取舍——宁可第一条少一路证据，也不让任何一条请求去等预热。
2. **实体消解靠字符串匹配**：`BERT` 能映射到 `bert`，但"那个预训练模型"这种指代无法消解，
   会走 hop1 的备用分支（召回分布定主论文）。
3. **语料全量扫描有上限**：nav 的精确匹配扫 `NAV_SCAN_LIMIT=5000` 段，语料缓存 60s。
   超过上限会跳过字面扫描、只走补召回，trace 的 hop 列表里能看出来（没有 hop1）。
4. **"这三篇"这类指代不做数量校验**：能取到主论文，但取几篇由 `COMPARE_MAX_PAPERS=4` 决定，
   不保证与"三篇"一致；答案质量也取决于 LLM 愿不愿意归纳，实测这一条可能回"无法回答"。
5. **评测集 18 条偏小**：类型准确率 100% 不能外推。真正的验证要靠线上真实问句回流，
   所以 trace 里保留了 `rule_hits` 与 `prototype.top`——用户点"判错了"时，先看这两项。
