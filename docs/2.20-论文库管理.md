# 2.20 论文库管理：看清库里有什么，删掉不该留的

> 目标：用户能在页面上看到数据库当前存的所有论文（标题、作者、存储时间、规模、状态），
> 能对单篇或多篇执行删除，删除前有确认、删除后列表与数量立即同步。

## 1. 这一页要回答的问题

不是"能不能删"，而是三个具体问题：

1. **库里到底有什么？** 包括解析失败的、正在解析的、没有 PDF 原件的半成品——
   这些在旧的 `GET /papers/` 里看不到，因为那个接口读的是向量 meta 集合，
   它只能反映"向量建成了的论文"。
2. **这篇论文是什么？** 标题、作者、arXiv 标识、版本、页数/片段数、存进来的时间。
3. **删了会怎样？** 不只是那一行消失：片段向量、PDF 原件、引用关系会一起没，
   问答与综述立刻检索不到它。这句话必须在点"确认"之前说清楚。

## 2. 数据边界：以 SQLite 的 `papers` 表为准

一次列表是两条查询在内存里拼起来，而不是一条大 JOIN：

```sql
-- ① 论文行 + 课题名
SELECT p.*, prj.name AS project_name FROM papers p
  LEFT JOIN projects prj ON prj.id = p.project_id
 ORDER BY p.created_at DESC;

-- ② 这批论文的所有版本（按 is_current 优先、ingested_at 倒序）
SELECT id, paper_id, version_label, status, stage, page_count, chunk_count, ...
  FROM paper_versions WHERE paper_id IN (...) ORDER BY is_current DESC, ingested_at DESC;
```

**为什么不用一条 JOIN**：一篇论文可能有很多版本，JOIN 会返回多行，还得在 SQL 里
写"取当前版本"的关联子查询；两条小查询 + 字典映射更直白，两百篇以内没有性能问题。

**为什么版本排序是 `is_current DESC, ingested_at DESC`**：`is_current` 理论上唯一，
但历史数据里出现过"全量切流后两个 active"这类事故（见 2.17）。多一个时间兜底，
列表就不会因为缺当前版本而显示成 `null`。

### 状态是算出来的，不是查出来的

`paper_versions.status` 只有 `pending/indexed/failed/duplicate`，但用户要看的是
"解析中 / 已入库 / 解析失败"。而且不能只看 status：

- **复用命中的版本是 `status=pending` + `stage=reused`**——它已经可用，按 status
  判会把它误当成"正在解析"拒掉删除；
- **老数据的 `stage` 可能是空串而 `status=indexed`**——只看 stage 会把它判成未知。

所以判据是"两侧都不在收尾集合里、且 stage 在流水线集合里"：

```python
RUNNING_STAGES = {"queued", "downloading", "parsing", "structuring", "indexing"}
SETTLED_STATUS = {"indexed", "failed", "duplicate"}
SETTLED_STAGES = {"indexed", "failed", "duplicate", "reused", "skipped"}
```

## 3. 删除：四处要一起清

| 位置 | 不清的后果 |
|---|---|
| `papers` 行（外键级联 versions / chunks / refs / citations / fingerprints） | 条目还在列表里 |
| Qdrant 的 chunk 点 | **删了还能被检索到**，答案会引用一篇已删除的论文 |
| Qdrant 的 meta 点 | 去重预检仍能命中它，上传同一文件会秒回"已解析" |
| MinIO 里的 PDF 原件 | 后台一直占着对象存储 |

`papers` 的级联依赖 `PRAGMA foreign_keys=ON`（`app/db/connection.py` 每次连接都设），
所以只需 `DELETE FROM papers WHERE id = ?`。

### 三条硬规则

1. **id 里有一个不存在 → 整批 404**，不做部分删除。用户看到的清单和实际不符时，
   最不该发生的事是"以为删了 5 篇，其实删了 3 篇"。
2. **有论文在解析 → 整批 409**，并把还在跑的列出来（`《标题》解析中`）。
   否则 worker 正在写 chunks，行删了、点又被写回来，留下幽灵向量。
3. **向量点是 `(arxiv_id, version)` 级共享的**，别的课题还挂着同一版本时**不删点**，
   只删本课题的行——否则会顺手把另一个课题的检索打死。PDF 同理按 `pdf_s3_key` 判共享。

第 3 条不是防御性编程，而是数据模型决定的：点 ID 由 `arxiv_id + version + kind + idx`
派生，同一篇论文被两个课题各导入一次时，两行 `paper_versions` 指向同一批点。

## 4. 前端：数量与列表必须来自同一时刻

列表接口把 `summary` 和 `items` 一起返回。分成两个接口时，删除后两个请求如果间隔返回，
会出现"数量已经变了、列表还没变"的错觉。

删除成功的处理顺序是：

1. 本地按 id 摘掉行，**并立刻用响应里的 `summary` 覆盖四个计数格**；
2. 清空选择集、关闭弹窗、弹 toast（只报真实发生的清理量）；
3. 静默重拉一次，把其它标签页/后台任务的差异一并对齐。

### 确认弹窗

不用 `window.confirm`——它只能放一句纯文本，说不清"删了会连带清掉什么"。
弹窗里做三件事：

1. 要删的论文**逐条列出**（超过 6 条折叠成"另外 N 篇"），避免"我选了 3 篇，不知道删的是哪 3 篇"；
2. 写明会连带清除的附属物与数量：`N 个片段向量`、`M 个 PDF 原件`、去重关系与引用记录；
3. 不可撤销只用一次红色强调，不默认聚焦危险按钮，Esc / 点遮罩可取消，删除中按钮进入 loading 并锁住。

### 其它细节

- **筛选在本地做**：库里最多几百篇，一次拉全量比每次敲键都发请求快，也不会闪。
- **时间固定按 UTC+8 展示**：这个组件服务端也会渲染一次，容器是 UTC、浏览器是东八区，
  直接 `toLocaleString()` 会让两边文本不一致、触发 hydration 警告。固定偏移 + `getUTC*`
  取值，两边逐字相同。
- **不可删的行禁用勾选并给出原因**（`正在解析中，完成后才能删除`），而不是点了才报错。
- **窄屏不摆表头**：390px 下"论文（标题/作者/标识）"这一格会被固定列宽挤成一列竖排字，
  所以 `<sm` 收起表头与状态列，把状态、存储时间、页数/片段数并进行内第二层，
  宽度留给标题；桌面端（`≥sm`）仍是七列表格。实测横向溢出 0px。

## 5. 踩到的两个坑（都不报错）

### 5.1 近似计数把"空删除"的短路分支废掉了

`delete_chunks()` 的注释写得很清楚：Qdrant 1.11 的稀疏倒排索引在"某个 token 的
posting list 被删空"时会 panic，线程一死后续所有写入都回 `channel closed`，
所以要**先 count、为 0 就跳过删除**。

但它用的是 `exact=False`：

```
1706.03762                 approx=138  exact=60
upload_2c828a184f131294    approx=138  exact=0    ← 库里根本不存在的 arxiv_id
```

近似计数在带 payload filter 时并不按命中条件去数，而是拿集合的近似总量回答。
后果两条：① 短路分支永远不触发，空删除照发，正好踩上 panic 路径；
② 返回值虚高——删除一篇 2 个片段的测试论文，返回 `vectors: 70`，
界面上就成了"清理了 70 个片段向量"。改成 `exact=True` 后返回 2，
对不存在的 arxiv 返回 0（验证里专门测了这条）。

删除是低频操作，精确数一次的代价远小于报错数。

### 5.2 `delete_pdf` 分不清"删掉了"和"本来就没有"

MinIO 的 `remove_object` 对不存在的 key 不报错。原来的实现 `except S3Error: pass`，
调用方拿不到任何信息，于是"清理了 2 个 PDF 原件"里可能混着 2 个从来没上传成功过的条目。
改成先 `stat_object` 探一次，返回 bool，只有真的存在过才计入。

## 6. 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/v1/library/papers?project_id=&q=&limit=` | 清单 + `summary` + `projects` |
| `DELETE` | `/api/v1/library/papers/{paper_id}` | 删单篇 |
| `POST` | `/api/v1/library/papers/delete` | 批量删，body `{"ids":[...]}` |

批量用 POST 而不是带 body 的 DELETE：部分代理/网关会丢掉 DELETE 的请求体，
表现为"点了删除没反应"——这类问题排查极费时间，不如直接避开。

路由放在 `/library` 而不是塞进 `/papers`：`/papers/{arxiv_id}/pdf` 那组是按论文标识
访问内容的运行时接口，失败模式是 404（内容缺失）；这里是"库里有哪些行"，失败模式是
409（状态不允许）。混在一个前缀下客户端难以区分。

## 7. 验证记录

用容器内真实环境跑完整流程（不是只测接口）：

```
删除前：DB papers 7 / versions 8 / chunks 281
        该 arxiv 的 chunks 行 2、Qdrant chunk 点 2、meta 点可查、MinIO 原件存在
删除：  POST /library/papers/delete {"ids":["pap_344c923a70a24689"]} → 200，68.6ms
删除后：DB papers 6 / versions 7 / chunks 279
        chunks 行 0、Qdrant chunk 点 0、meta 点不可查、MinIO 原件不存在
```

- **解析中拒删**：上传一份 2 页 PDF，解析期间 `status=running / deletable=false`、
  行内提示"正在解析中，完成后才能删除"；此时调用删除接口返回
  `409 {"message":"有论文正在解析，暂不能删除","blocked":[{"title":…,"status_label":"解析中"}]}`。
- **空删除**：`delete_chunks("upload_does_not_exist","v1")` → `0`，无 panic。
- **浏览器端到端**（Edge 实拍）：8 篇 → 勾选 2 篇 → 弹窗列出 2 篇与"16 个片段向量、2 个 PDF 原件"
  → 确认 → 列表 6 篇、计数 `8→6`、`267→251 片段`、`116→91 页`，toast 与结果一致；
  单行"删除"按钮走同一条路径。

## 8. 没做的部分

- **恢复站（回收站）**：现在是硬删除。要做得先有软删标记 + 定期物理清理，
  并且检索侧要 filtering，属于一次独立改造。
- **按课题整批清空**：接口支持传多个 id，但没做"清空某课题"的一键入口。
- **删除操作的审计流水**：目前只在 API 日志里留痕，没有写 `dedupe_decisions` 那样的
  结构化记录。做的话建议单独一张 `library_events` 表，不要复用判定记录。

## 9. 入库区并入本页（2026-11-10）

首页原来自己带一块 `INGEST`：左卡上传 PDF、右卡导入 arXiv。问题不在功能，在位置——
传完只拿到一句「已入队」，库里有几篇、这篇有没有进去、解析到哪一步，都得跳到另一个页面才看得见。
所以把这块整体搬到论文库，顺序变成「导入 → 计数 → 清单」，一次操作从头到尾都在同一屏。

**代码位置**

- 新组件 `frontend/src/components/ingest/IngestPanel.tsx`：上传/arXiv/去重弹窗/进度条四件事都在里面，
  逻辑与搬迁前逐字一致，只多了一个 `onIngested` 回调。
- `frontend/src/app/library/page.tsx`：`<section id="import" className="scroll-mt-24">` 放这块，
  `onIngested` 指向 `reloadAfterIngest`（`load(true)`，静默重拉，不把正在看的清单闪成骨架屏）。
- `frontend/src/app/page.tsx`：整块表单连同 state / 去重预检 / 进度条一起删掉，只留下入口常量
  `INGEST_HREF = '/library#import'`。

**入口统一**

| 位置 | 原来 | 现在 |
| --- | --- | --- |
| 导航第一项 | 「上传」→ `/` | 「首页」→ `/`（图标换成房子） |
| 首页 Hero「开始使用」 | 滚动到页内 `#upload-section` | `/library#import` |
| 首页能力卡「论文入库」 | `/#upload-section` | `/library#import` |
| 图谱空态「去上传」 | `/` | `/library#import` |
| 论文库头部「导入论文」 | `/` | `#import`（平滑滚到本页导入区） |
| 论文库空态「去导入论文」 | `/` | `#import` |

**两个实现细节**

- 带 `#import` 进来时浏览器滚不过去：首屏是客户端渲染，锚点目标还没挂载。
  组件挂载后补一次 `scrollIntoView`（80ms 后），实测 `scrollY=158`、区块顶边 96px（= `scroll-mt-24`）。
- 进度组件的 `onDone` 在 effect 依赖里，父组件每渲染一次身份就变一次，会重连 SSE。
  入库面板里把它包成 `useCallback([onIngested])`，论文库那边也把回调 `useCallback` 住。

**验证**

- CDP 实测：在 `/library` 的导入区填 `2106.09685` 点「拉取并解析」→ 回显
  「命中已解析文件，秒级复用：2106.09685::v2」，随后 `/api/v1/library/papers` 请求计数 +1（`refetch=1`）。
- 实拍：桌面 1440px 导入区两卡并排、计数 6 篇 / 251 片段、清单 6 行；390px 两卡上下堆叠、无横向溢出；
  首页只剩 Hero + 能力卡（论文入库指向 `/library#import`）+ Pipeline。

## 10. 状态实时刷新（2026-11-10）

### 现象

传完一篇论文停在论文库页，进度条不出现、列表状态一直「解析中」，等 8 分钟也不变；
手动点「刷新」才发现早就入库了。数据库和 worker 日志显示任务 39 秒就结束了。

### 四个独立原因

| # | 位置 | 原因 |
| --- | --- | --- |
| 1 | `library/page.tsx` | 清单只在挂载时拉一次，之后只有删除/入库回调会刷。解析 40 秒到 9 分钟这段没人管 |
| 2 | `IngestProgress.tsx` | SSE 一建立就停掉轮询。链路抖动时 EventSource 变半开连接——不报错、不再来消息，`done` 永远收不到 |
| 3 | `IngestPanel.tsx` | 进度组件没有 `key`。连续传两篇时实例复用，`doneRef` 还是上一轮的 true，第二次的 `onDone` 不触发 |
| 4 | `IngestProgress.tsx` | 轮询拿到终态后不退出，任务完成仍在每 1.2 秒拉一次，直到关页面 |

### 改法

**页面级轮询**（覆盖面最广，入口不止进度条一个）

只要 `summary.running > 0` 就每 3 秒静默重拉 `/library/papers`，`running` 归零时
定时器随 effect 清理自动停。后台标签页降到 10 秒一次，切回前台立刻补一次。
`load` 用 ref 保存，避免 `toast` / `onIngested` 引用变化把定时器重建。

**后端心跳**

SSE 只在快照变化时推，而一批 20 页向量化要 15~30 秒，期间静默是正常的。
加 `HEARTBEAT_SECONDS = 10`，超过 10 秒没变化就发 `event: ping`，不携带数据。
这样「静默」和「断线」才区分得开，顺带避免代理按空闲超时切连接。

**前端看门狗**

`ping` 只更新 `lastMsgRef`，不动界面状态。25 秒（容忍丢两次心跳）没有任何事件
就判定连接已死：关掉 EventSource，`setUsingSse(false)`，轮询接管。

**其他两处**

- `<IngestProgressPanel key={taskId || versionId || ''} />`：任务变了就重建，
  `doneRef` / EventSource / 轮询一起重置。
- 轮询循环加 `if (doneRef.current) return`，终态即停；续跑时把 `done` 置回 false
  并 `pollEpoch + 1` 重新启动轮询。

### 验证

CDP 实测（headless Edge，`document.visibilityState = visible`）：

- 造一条 `status=parsing` 的临时记录 → 2.5 秒内 1 次请求，9.5 秒累计 4 次（3 秒/次）；
- 第 9.5 秒把它改成 `indexed` → 列表行从「解析中」变「已入库」，
  轮询在拿到这次结果后自行停止（9.5s → 18.5s 只多 1 次请求）；
- 清理临时记录后回到 1 篇 / `running=0`，页面计数与清单一致。
