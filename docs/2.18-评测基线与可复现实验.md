# 2.18 评测基线与可复现实验

> 目标：证明「比别的方案好」，而不只是「跑两遍结果一样」。
> 代码：`backend/eval/baseline/`（数据集 + 跑批 + 报告）；检索层新增通道开关
> （`RetrievalService.channels`）与单路阈值重标定（`SINGLE_CHANNEL_RANK_EQUIV`）。

这一版要回答三个问题，缺一个都不算做完：

1. **好在哪** —— 有基线对比，且基线是同一份检索代码的另一种配置，不是另写一套；
2. **凭什么信** —— 指标定义写得清、分母写得清、噪声底线写得清；
3. **能不能复算** —— 换一台机器、换一天，用同一条命令跑出同一组数字。

第 3 条最容易糊弄过去。所以这里的"可复现"是可执行的：`verify <run_id>` 会重放检索，
逐题比对内容指纹。它不是一句保证，是一条命令。

## 1. 评测集与标注格式（交付物 1）

### 1.1 一道题长什么样

`backend/eval/baseline/dataset/questions.jsonl`，一行一题：

```json
{
  "id": "p01",
  "lang": "zh",
  "type": "point",
  "expect": "answer",
  "question": "Transformer 的 base 模型训练用了多少块 GPU、花了多长时间？",
  "gold": [
    {"arxiv_id": "1706.03762", "page": 7,
     "quote": "We trained our models on one machine with 8 NVIDIA P100 GPUs."},
    {"arxiv_id": "1706.03762", "page": 7,
     "quote": "We trained the base models for a total of 100,000 steps or 12 hours."}
  ],
  "absent_terms": [],
  "notes": "单跳事实，答案在硬件与训练计划一节"
}
```

| 字段 | 含义 | 约束 |
|---|---|---|
| `id` | 题号，`p/c/s/n` + 序号 / `a` 为不可答 | 唯一 |
| `lang` | `zh` / `en` | 决定要不要用固定译文 |
| `type` | point / compare / survey / nav / absent | 只用于分题型统计 |
| `expect` | `answer` / `refuse` | 决定进哪个分母 |
| `gold` | 证据列表，至少一条（`expect=answer`） | **不写 chunk_id**，见 1.2 |
| `absent_terms` | 判别词，`expect=refuse` 时必填 | 全库必须 0 命中 |
| `notes` | 为什么出这道题 | 给人看的 |

### 1.2 gold 标的是"原文"，不是"片段 ID"

这是整份数据集里最重要的一个决定：

```
❌ {"chunk_id": "chk_0756dd418064440e", "page": 8}
✅ {"arxiv_id": "1706.03762", "page": 8, "quote": "Table 2: The Transformer achieves better BLEU scores ..."}
```

chunk_id 会随切分策略、重建批次变化（13 里 `chunk_index` 整批重排过一次）。
标了 chunk_id 的评测集，等于焊死在某一代索引上——换模型、调截断长度、重建一次，
全部题目的 gold 集体失效，而指标只会显示"召回率暴跌"，看起来像检索坏了。

标原文就没有这个问题：新版本的片段只要还包含这句话，就算命中。判定逻辑在
`judge.py`，规则刻意不对称：

- **长引句（>24 字符）** 允许模糊命中，取最长公共子串 ≥ `max(24, 0.6×长度)`。
  PDF 抽取会留连字符断词（`de- composition`、`to- kens`）和连字（`ﬁ`、`ﬀ`），
  死等字符串相等会漏判。归一化时把这些还原（`norm()` 里四步：连字还原 → 接回断词
  → 空白折叠 → 小写），两侧同规则。
- **短引句（≤24 字符）** 只认整串包含。短串的模糊匹配几乎必然命中
  （`rank` 能匹配到 `ranking`），那一格指标就变成噪声了。
- **必须同篇论文**。不同论文里有大量同样的套话（`we train on`），跨文命中会把
  "召回对了"变成"召回巧合"。

### 1.3 不可答题必须"可证伪"

"库里没有"是个很难验证的断言。所以不可答题不靠人拍胸口，靠判别词：

```json
{"id": "a10", "expect": "refuse", "question": "LoRA 的作者比较过 QLoRA 的效果吗？",
 "absent_terms": ["QLoRA"], "notes": "QLoRA 是后续工作，时间上晚于本文"}
```

`validate` 会断言这些词在整个库内 0 命中。命中即判定该题不成立——
出题的时候真的被拒过三次：

| 题 | 判别词 | 实际命中 | 处理 |
|---|---|---|---|
| BERT 是否报告了 SuperGLUE 结果 | `SuperGLUE` | LoRA 参考文献里提到（1 处） | 换成 federated learning |
| LoRA 是否在中文任务上评测 | `Chinese` | soliton 那篇（2 处） | 换成 RLHF |
| ViT 是否做过视频分类 | `video` | ViT 相关工作、Attention（4 处） | 换成 3D 点云 |

第二条尤其说明问题：如果拿"中文"当判别词，这题会永远"通过"校验，
而实际模型只要把 `Chinese` 那一段找来就能答——那不是拒答，是答对了。

### 1.4 48 题的构成

| 题型 | 题数 | 说明 |
|---|---|---|
| point 点查 | 18 | 单个事实/数值，一半中文一半英文 |
| compare 跨文对比 | 6 | gold 两条，分属两篇 |
| survey 综述 | 6 | gold 三到四条，跨三篇 |
| nav 原文定位 | 6 | 问"这个术语在哪一页"，靠字面 |
| absent 不可答 | 12 | 6 个库外主题 + 6 个库内不存在的实验 |

语料是赛题四个预置 PDF：Attention (1706.03762)、BERT (1810.04805)、
ViT (2010.11929)、LoRA (2106.09685)，共 209 段（索引里 279 点，含另一版 Attention）。

**为什么不做成 500 题**：这套集子的用途是"改一版参数，五分钟内知道有没有变差"。
题多了跑不动就没人跑，没人跑的评测等于没有。48 题的代价写在指标里——
**1 道题 = 2.78 个百分点**，报告里每一张表下面都标了这个数。

### 1.5 中文题的译文也进数据集

`dataset/translations.json` 存着每道中文题固定好的英文译文。

不存会怎样：同一个中文问题两次跑出两个英文译法，检索结果跟着漂——
而那不是检索的方差，是翻译的方差。把译文钉死，比较的才是检索方法。
`QAService.ask()` 为此加了 `search_text` 参数：传了就不再翻译。

## 2. 指标定义（交付物 3 的前半部分）

| 指标 | 定义 | 分母 | 为什么要有它 |
|---|---|---|---|
| **Recall@5** | 任一 gold 证据落进前 5 | 可答题（36） | 主指标。只问"找到没有"，不掺生成 |
| MRR@5 | 第一条命中名次的倒数 | 可答题 | 区分"第 1 名命中"和"第 5 名才命中" |
| nDCG@5 | 二值相关性 nDCG | 可答题 | 同上，多证据题更敏感 |
| **覆盖@5** | 被覆盖的 gold 证据比例 | 可答题 | 对比/综述题要多条，Recall 只看一条 |
| **误拒率** | 可答题被判成"不作答"的比例 | 可答题 | 拒答的两个方向必须分开 |
| **正确拒答率** | 不可答题被拒的比例 | 不可答题（12） | 另一半 |
| 拒答准确率 | (正确拒 + 正确答) / 全部 | 48 | 单一汇总，会掩盖方向，只作参考 |
| **可分性 AUC** | `top_raw/threshold` 区分可答/不可答的 AUC | 48 | 与阈值无关，见 2.1 |
| **引用准确率** | 被引原文是否支持该句论断 | 人工抽检 17 条可判 | 见 2.2 |

### 2.1 为什么要有"可分性 AUC"

任何一个"拒答准确率"都隐含一个阈值选择，而阈值是主观的。表里三组基线里，
双路阈值 `0.03`（≈ 两路都进前 5），单路换成名次等价线 `1/(60+5)=0.0154`——
这两个数在语义上对齐了，但幅度完全不同。换个阈值，误拒率和正确拒答率就一起动，
比出来的差异说不清是"信号强"还是"尺子松"。

AUC 只问排序：不可答题的分数是不是系统性低于可答题。0.5 = 完全没有信号。

实测结果很有说服力：

| 配置 | 正确拒答率 | 可分性 AUC |
|---|---|---|
| 纯向量 | 0.00% | **0.5000** |
| 纯 BM25 | 0.00% | **0.5000** |
| 混合（RRF） | 25.00% | 0.7766 |
| 混合 + 精排 | 25.00% | 0.7812 |

单路的 AUC **精确等于 0.5**，不是巧合：单路时第一名永远是 `1/(60+1)`，
36 道可答题和 12 道不可答题的比例值全部相同，排序上没有信息可分。
换句话说——

> **RRF 的双路一致性本身就是拒答信号，而单路配置结构性地没有这个信号。**
> 纯向量、纯 BM25 的"0% 正确拒答率"不是阈值没调好，是压根没有东西可调。

这条结论只有把 AUC 和阈值分开算才看得见。只看拒答准确率，会得出
"单路召回不适合做拒答"这种含糊的结论；看 AUC 才能说清是"信号不存在"。

### 2.2 引用准确率：自动与人工是两件事

两个口径同时报，因为它们量的不是同一件事：

- **引用有效率**（代码校验）：答案里的 `[引#N]` 是否指向真实片段、有无越界。
  实测五组都是 **100%**，`invalid_citations` 全为 0。它是必要条件，不是充分条件。
- **句级无支撑率**（07 的自动核验）：带引用的句子里，被判为"无支撑"的比例。
  实测 2.08%–14.63%。它受跨语言语义核验可用性影响，只能当趋势看。
- **人工抽检**（本节采用的口径）：固定 seed 从 265 条"句子 + 被引原文"里抽 20 条，
  人逐条读，判 支持 / 部分支持 / 不支持 / 不适用。

人工结果（`review_summary.json`）：

| 判定 | 条数 |
|---|---|
| 支持 | 13 |
| 部分支持 | 1 |
| 不支持 | 3 |
| 不适用（关于片段自身的否定陈述） | 3 |
| **可判 17 条：严格准确率** | **76.47%** |
| 宽松（支持 + 部分支持） | 82.35% |
| 明确错引率 | 17.65% |

四点必须说清楚，否则这个数是虚的：

1. **分母不是手算的。** `review 20261110T040312-e59586` 从 `review.csv` 读 `verdict`
   现算，`不适用` 不进分母这条规则写在代码里（`summarize_review`）。
   人只填判定与理由，口径由代码定——否则换个人汇总一次，数字就变一次。
2. **"不适用"单独列、不进分母。** 3 条全是**关于片段自身的否定陈述**——
   "给定片段内没有提到 GPT-4""片段里未明确提及评估指标"。这类句子在逻辑上
   无法被引文"支持"（它断言的是证据的缺席），但也不是错引。算进分母等于拿
   "该不该挂引用"去扣"引用准不准"。
3. **3 条"不支持"里有 2 条是同一个根因**：`r03` 与 `r19` 问的都是 BERT base/large 的
   层数/隐层/参数量，数值答对了，但引的是 **p9 §5.3**（那页有 GLUE 表和带 `#L #H #A`
   的超参表头），真正的出处在 §3.1。绑定环节按词面挑到了"含同形状数字的表格页"——
   答案对、出处错，这是最容易被漏掉的一类错误，因为看上去完全正常。
   第 3 条（`r01`）同理：问 LoRA 推理延迟，引到了 p4 那张**测 adapter 延迟**的 Table 1，
   而"by construction 不加延迟"在 p5。
4. **样本太小，不能分组比较。** 20 条摊到 5 个配置，每组只有 1–5 条，
   组间差异没有意义（`dense` 组只抽到 1 条，那一组是 0%）。要比较配置得把抽检量提到
   100 条以上。

### 2.3 噪声底线

可答集 36 题，1 题 = 2.78 个百分点。所以：

- `hybrid_rerank` 的 Recall@5 0.8333 与 `system` 的 0.8056 差 **1 道题**，在噪声内；
- `dense` 0.7500 与 `hybrid` 0.7500 相同，但 MRR 也不同（0.5764 vs 0.5787），
  同样是一道题的位移；
- 只有 0.0556（2 题）以上的差距才值得当结论说。

## 3. 跑批脚本（交付物 2）

### 3.1 三条命令

```bash
# 校验数据集：gold 引句能否在库内命中、不可答词是否真零命中、页码对不对
python eval/baseline/run_baseline.py validate

# 补齐中文题的固定译文（只在数据集变动后需要）
python eval/baseline/run_baseline.py translate

# 跑一次完整评测（默认五个配置 + 生成）
python eval/baseline/run_baseline.py run --index-version idx-1.0.0-555810c4 --seed 20261110

# 只看检索、不调生成（约 70 秒）
python eval/baseline/run_baseline.py run --no-generate

# 重放某次运行，逐题比对
python eval/baseline/run_baseline.py verify 20261110T040312-e59586

# 只重算指标与报告（口径改了但不想重跑时）
python eval/baseline/run_baseline.py recompute 20261110T040312-e59586

# 人工填完 review.csv 的 verdict 后，重算汇总（不碰 csv）
python eval/baseline/run_baseline.py review 20261110T040312-e59586
```

答辩现场重跑的顺序就是 `validate` → `run` → 看 `report.md` → `verify`。
`run` 的退出码是有意义的：生成失败率超过 10% 会返回 1（见 §7.3）。

### 3.2 五个配置：基线是同一份代码的另一种配置

```python
CONFIGS = [
  Config("dense",         channels="dense",  force_type="generic", rerank=False),
  Config("sparse",        channels="sparse", force_type="generic", rerank=False),
  Config("hybrid",        channels="hybrid", force_type="generic", rerank=False),
  Config("hybrid_rerank", channels="hybrid", force_type="generic", rerank=True),
  Config("system",        channels="hybrid", force_type=None,      rerank=True, numeric=True),
]
```

三个决定，每个都是为了"比出来的差异能归因"：

**① 通道开关做进检索层，不是另写一套检索。**
`RetrievalService.channels` 只控制"这一路要不要发查询"，融合公式、归一分、
精排、trace 全部共用。若基线另写一套，差异里就混进了实现差异，证明不了方法好坏。
关掉一路时 `dense_search` / `sparse_search` 返回空列表而不是报错——
`_rrf_merge` 对"缺一路"免疫（跳过 `rank<=0`），空列表正好表达"这一路没投票"。

**② 基线全部 `force_type="generic"`。**
基线就该是"两路召回直接取 top-k"，不带查询理解、不按类型换策略。
否则"我们的方案比基线好"会变成"我们的方案比另一个我们的方案好"。
`system` 才带查询理解与规则召回。

**③ 单路要重标定阈值，否则比的是尺子。**
单路时 RRF 分只有双路的一半（另一路没有票可投），拿 `0.03` 去量，
纯向量组会 **100% 误拒**。那不叫召回差，叫量具换了。
所以单路时改用名次等价线：

```python
# retrieve.py
if len(active_channels) == 1 and strategy.reject_threshold is not None:
    weight = params.get(f"{active_channels[0]}_weight", 1.0)
    strategy.reject_threshold = round(weight / (rrf_k + SINGLE_CHANNEL_RANK_EQUIV), 6)
```

`SINGLE_CHANNEL_RANK_EQUIV = 5`：双路阈值的语义是"两路都在前 5 名附近"
（`2/(60+5)≈0.031`，与 `RRF_MIN_SCORE=0.03` 同量级），单路没有第二票，
就把同一个名次要求压到一路的分母上。生产恒为 `hybrid`，这段不执行。

### 3.3 一次运行落盘什么

```
runs/<run_id>/
├── manifest.json        这次跑的到底是什么（见 §5.1）
├── retrieval.jsonl      240 条 = 5 配置 × 48 题，逐题召回快照
├── answers.jsonl        240 条生成结果（答案、逐句 claim、逐处证据）
├── metrics.json         全部指标的机器可读版（报告里的表都从这里生成）
├── report.md            对比报告（人读）
├── review.csv           人工抽检表（20 行，verdict 列留空待人填）
├── review_summary.json  抽检汇总（`review` 子命令从 verdict 现算，不是手填）
└── review_pool.json     抽样池大小与 seed（265 抽 20）
```

`retrieval.jsonl` 一条记录（节选）：

```json
{"config": "system", "id": "p07", "type": "point", "expect": "answer",
 "ranked": [{"rank": 1, "chunk_id": "chk_...", "arxiv_id": "1810.04805",
             "page": 4, "score": 0.9589, "raw": 0.0141, "source": "fusion"}],
 "top_raw": 0.016293, "threshold": 0.015, "ratio": 1.0862, "rejected": false,
 "strategy": "point_boost_sparse", "channels": ["dense", "sparse"],
 "doc_sha1": "…", "hit": true, "mrr": 1.0, "ndcg": 1.0,
 "coverage": 1.0, "gold_ranks": [1]}
```

`doc_sha1` 是召回结果的指纹，`verify` 比对的就是它；`ratio` 是
`top_raw/threshold`，可分性 AUC 用它。

| 纯向量 | 46 | 2 | 47 | 1.02 | 51 | 0 | 100% | 14.63% | 3248ms |
| 纯 BM25 | 46 | 2 | 50 | 1.09 | 58 | 0 | 100% | 12.28% | 3216ms |
| 混合 | 47 | 1 | 50 | 1.06 | 53 | 0 | 100% | 8.51% | 3204ms |
| 混合 + 精排 | 47 | 1 | 48 | 1.02 | 53 | 0 | 100% | **2.08%** | 3499ms |
| 本系统 | 47 | 1 | 47 | 1.00 | 50 | 0 | 100% | 10.64% | **2827ms** |

口径说明（这三个数容易被混成一个"引用准确率"）：

- **被引片段** = 答案里真正挂过角标的**唯一片段**数。它必须逐题不同；
  如果五组都精确等于 240（= 48 题 × top_k 5），那说明取错了字段——
  取到的是"检索带回的候选数"，与答案无关。
- **角标数** = 引用**次数**（同一片段被两句引算两次），是"引用有效率"的分母。
- **句级无支撑率** = 07 的自动核验判为无支撑的、**带引用**的句子占比，分母是带引用的句子。

检索层与生成层的拒答判定一致率 **95.83%（230/240）**。不一致的 10 条集中在
"空检索"这条独立通道上：检索层只看分数，`ask()` 还会看语料里到底有没有这个词。
两个口径不一致不一定是 bug，但要知道是哪一类不一致。

### 4.4 结论：写在这里的和不写在这里的

**能写成结论的：**

1. **混合 + 精排对纯单路有稳定增益。** Recall@5 0.8333 vs 0.7500 / 0.8056，
   nDCG 0.5766 vs 0.5694 / 0.5878，覆盖@5 0.7106 vs 0.6528 / 0.6574。
   三个指标方向一致，不是单点抖动。
2. **精排的收益主要在 point 与 compare**：point 0.8333→0.8889，
   compare 0.5000→0.8333。nav 不动（它本来就是字面命中，精排改不了什么）。
3. **拒答能力是混合架构的副产品，单路没有。** AUC 0.78 vs 0.50（§2.1）。
   这条是本次评测最"新"的发现：以前只知道 RRF 能提召回，
   没意识到"两路是否同意"本身就是一个置信度信号。
4. **本系统在 nDCG@5 与覆盖@5 上最高**（0.6062 / 0.7199），
   Recall@5 比最强基线低 1 道题（在噪声内）；nav 类 100% vs 83.33%。
   多证据题上，把 5 个槽位摊给多篇的策略（compare/survey）在 Recall@5 上吃亏，
   但在覆盖@5 上占优——这两个指标测的是不同的东西。
5. **引用错的地方不是"编造"，而是"绑定到隔壁"**：3 条错引里有 2 条答案数值完全正确，
   只是引到了同页附近那段含数字的表格（§2.2 第 2 点）。这类错误用"引用有效率"
   （角标是否越界）查不出来，用"句级无支撑率"也只部分命中——它需要人读原文才能看见。

**不能写成结论的：**

- 组间 1–2 道题的差异（< 0.0556）；
- 引用准确率的组间比较（每组抽检 1–5 条）；
- "本系统全面优于基线"——**主指标 Recall@5 上没有**。诚实的说法是：
  在检索质量基本持平的前提下，本系统换来的是拒答、引用、锚点这些产品能力；
  纯检索指标上它没有压倒性优势。

**还没解决的一个弱点**：`compare` 题型本系统只有 0.5000，比最强基线的 0.8333 差。
`compare_multi_hop` 按论文各取一跳再合并，5 个槽位要摊给两篇，
单篇 gold 容易被挤出前 5。下一步要么放宽 compare 的返回条数，
要么给 compare 单独的 top_k 口径——这是 15 的活。

### 5.2 重放校验：内容与标签都 240/240 一致

```
$ python eval/baseline/run_baseline.py verify 20261110T040312-e59586
存档快照 snap-95cfc8db1ed8 · 当前 snap-95cfc8db1ed8 · 一致
  比对 240/240
------------------------------------------------------------------------------
内容（论文/页码/分数序列）：240/240 一致
标签（chunk_id 序列）：    240/240 一致
✓ 240 次检索逐题一致
```

`verify` 分两个口径，是因为第一版只比 `chunk_id`，而 `chunk_id` 是**标签**不是内容：

- **内容指纹** = `(arxiv_id, page, score)` 序列的 sha1。它判的是"回来的是不是同一批片段、
  同样的顺序、同样的分数"。
- **标签指纹** = `chunk_id` 序列的 sha1。它判的是"标签有没有变"。

两个方向都要算：只比标签，标签变了内容没变（§7.2 的点 ID 修复）会被判成不可复现；
只比内容，标签没变但内容被换（重建后点 ID 被复用）会被判成可复现。
上一轮这里第二行是 0/240（修复发生在跑完之后），本轮修复已进入运行，两行都是 240/240。

还有一次独立验证：同一份数据上单跑 `run --no-generate`（83.4s，零 LLM 调用），
五组配置的 Recall@5 / MRR / nDCG / 覆盖 / AUC **逐位相同**。也就是说这套检索
在三处独立执行里给出了同一组数：正式运行、`verify` 重放、纯检索重跑。

### 5.3 代码指纹：容器里没有 git

`git rev-parse` 在容器里只会返回 `unknown`。而"这次跑的是哪份代码"是复现记录里
最不能缺的一项，所以按文件内容取指纹：

```python
CODE_FILES = [retrieval_service.py, strategies.py, retrieve.py, rerank.py,
              confidence.py, uncertainty.py, answer.py, qa_service.py, index_version.py]
```

它的另一个用处：两次运行指标变了、但 `code_sha1` 没变，问题就不在这几个文件里。

## 7. 评测跑出来的四个真问题（都已修）

评测的价值不在数字，在于它会把"看起来没问题"的东西翻出来。这次翻出四个，
**四个都不报错**：两个让结果变差，两个让指标变成摆设。

### 7.1 点查加成把正确答案顶出前 5（已修）

第一次跑完，`system` 的 Recall@5 是 **0.6944**，比最弱的基线还低。

逐题对比 `system` 与 `hybrid_rerank`，`p07`（问 BERT 掩码比例 15%）是典型：

```
hybrid_rerank 第 2 名: 1810.04805 p4  ← 正确答案 "we mask 15% of all WordPiece tokens"
system        前 5 名: 1706.03762 p7, 1810.04805 p1, 1706.03762 p2, 2010.11929 p5, 1810.04805 p2
                      （第 1 名是 Attention 的训练数据段：36M sentences / 32000 word-piece）
```

根因在 `_point_boost`：它给"实验设置段" +0.3、"表格" +0.15。
这两条加成的前提是"答案以 `参数 = 值` 的形态落在实验里"——
可 `p07` 问的是掩码比例，是 BERT 正文的一句话，不在实验段里。
加成没有前提却在生效，于是**另一篇论文**里那段含数字的实验设置被顶到第一。

修法：给这两条加成加前提。

```python
numeric_question = bool(hyper_terms or numbers or chart_refs)  # 问句里到底有没有被问到的那个量
if numeric_question and _is_experiment_chunk(r):  boost += POINT_EXPERIMENT_BOOST
if numeric_question and kind in _TABLE_KINDS:     boost += POINT_TABLE_BOOST
```

` β2 设为多少` 这类真·数值问题行为不变（`hyper_terms` 非空）；
一般事实题不再被"含数字的段落"带偏。

修完重跑：

| | 修复前 | 修复后 |
|---|---|---|
| Recall@5 | 0.6944 | **0.8056** |
| nDCG@5 | 0.5327 | **0.6062** |
| 覆盖@5 | 0.6088 | **0.7199** |
| 正确拒答率 | 0.00% | 0.00% |

**这就是评测该干的活**：一个加成规则在演示语料上一直是对的，
换一套问法就变成主要的错误来源，而线上没有任何信号会说"你退化了"。

### 7.2 点 ID 映射的 UUID 连字符 bug（已修）

人工抽检时想核对被引原文，按 `review.csv` 里的 `chunk_id` 去库里查——**查不到**。

根因：Qdrant 回包的点 ID 是带连字符的 `8c161695-777e-16a9-…`，
而入库时写进 `chunks.qdrant_point_id` 的是 `uuid4().hex` 的无连字符形式。
`resolve_point_ids` 按原串比对，必然全部落空，于是 `chunk_id` 退化成 point_id。

后果不报错、只是：

- 按 chunk_id 查锚点全部查不到 → 引用"能显示、框不到原句"；
- 引用准确率**无从复核**（连被引片段都找不回来）。

修法：比较与缓存都按"去连字符 + 小写"归一化，回填时用调用方给的原始串做 key。
修完验证：

```
resolve_point_ids(['8c161695-777e-16a9-7c29-4d4b96976d32'])
→ {'8c161695-777e-16a9-7c29-4d4b96976d32': 'chk_0756dd418064440e'}
```

这个 bug 不是 14 引入的，是 13 重建索引后才显形的：旧点用 uuid5（带连字符），
新点用 `uuid4().hex`（不带）。**两代点的 ID 写法不一样**，而代码假设了只有一种。

修复后的端到端证据在本次运行里：`review.csv` 的 `chunk_id` 全部是 `chk_…` 形态，
按它去 `chunks` 表能取回原文（§2.2 的 20 条判定就是这么读出来的），
`verify` 的"标签 240/240 一致"也是同一件事的另一面。

### 7.3 "跑完 ≠ 跑对"：生成全挂也要有人喊

第二次跑正式数据时，provider 欠费（`Access denied ... overdue-payment`），
240 次生成全部抛错。而错误被逐题 `try/except` 吞掉之后，报告安静地写着：

```
作答 2 · 拒答 46 · 引用 15 条 · 引用有效率 100%
```

看起来像"模型今天特别保守"，实际是一次没跑成。修法：

```python
if total_err:
    manifest["status"] = "degraded" if total_err > total_gen * 0.1 else "partial_errors"
    return 1 if manifest["status"] == "degraded" else 0
```

失败率超 10% 时 `run` 返回非零，`manifest.status` 写进文件，报告顶部可见。
**绿色的红灯是最坏的一类 bug**——它比报错更贵，因为你不会去查。

充值恢复后重跑，240/240 生成成功、`status=ok`：同一份代码、同一份数据，
差的只是一次能跑通的机会。这也说明那条守卫是必要的——
它会把"跑了但没跑成"和"跑成了"区分开，而不是都写成一行 `完成`。

### 7.4 引用数恒等于 240：指标不报错，但没意义

第一版把"引用数"取成了 `len(out["sources"])`，于是五组配置的"引用总数"
全部精确等于 **240 = 48 题 × top_k 5**——整齐得可疑，但它不报错、也不越界，
只是把"检索带回几个候选"当成了"答案引了几段"，跟模型行为毫无关系。

区分三个量：

| 量 | 定义 | 本次实测 |
|---|---|---|
| 候选片段数 | 检索返回几段，由 top_k 决定 | 恒为 240（无信息） |
| 被引片段数 | 答案里挂过角标的**唯一** chunk | 47–50（逐组不同） |
| 角标数 | 引用**次数**（同片段被两句引算两次） | 50–58 |

"引用有效率"的分母只能是角标数（非法引用是"角标解析不出来"，是次数问题）；
"句级无支撑率"的分母是带引用的句子数。三个数混成一个，就会得到
"引用准确率 100%"这种看着漂亮、实际只说明了"没有越界"的数字。

**判据**：如果一个指标在五组配置上完全相同，先怀疑它是不是由常数决定的，
再怀疑模型。这条经验在 §7.1（Recall 掉 0.11）和本节各命中一次。

## 9. 没做的部分

- **没有答案正确性指标**（accuracy）。判"答得对不对"需要另一套标注（gold answer），
  成本比 gold evidence 高一个数量级，这次只做到"检索到没检索到 + 引用支持不支持"。
- **人工抽检样本偏小**（20 条）。要分组比较，得 100 条以上。
- **没有做显著性检验**。48 题上做 bootstrap 区间意义不大，等题量上去再说。
- **没有把评测接进 CI**。现在是手动跑，`run` 一次 4.5 分钟 + 240 次 LLM 调用，
  直接进 CI 太贵。合适的做法是"每日跑一次 retrieval-only（70 秒、零 LLM 调用）"，
  这个已经支持（`--no-generate`），只是还没排上。
- **`compare` 策略在 Recall@5 上仍弱于基线**（0.5000 vs 0.8333），见 §4.4 末尾。
- **引用绑定没有独立的评测**。本次 3 条错引全部是"答案对、出处错"（§2.2 第 2 点），
  根因在 claim→证据的绑定环节，而绑定质量目前只靠 20 条人工抽检看。
  要系统性地测它，得给每条 gold 补"支撑句"，成本与 gold answer 同级。
- **没有多轮/追问场景**。48 题都是单轮独立问题。
