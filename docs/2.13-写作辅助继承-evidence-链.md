# 2.13 写作辅助：继承 evidence 链

> 目标：写作模块不是独立玩具。写出去的每一句都能查——查得到是哪一段原文、哪一页、哪一篇文献。

## 1. 问题：写作模块原来是「独立玩具」

改造之前，`writing_service.generate_outline` 只有一句话：检索 top-k → 让模型写大纲。产出是一段 Markdown，每个小节后面挂个 `arXiv:xxxx`。三个问题：

1. **挂的号没人核对**。模型写 `arXiv:2106.09685` 和写 `arXiv:2106.09666` 的成本一样，读者没有任何办法判断哪个是真的。这不是"模型可能出错"，是"错了也看不出来"。
2. **句子没有身份**。一段话里的"LoRA 在长文本上更稳定"到底是哪篇论文的哪一句？无从回答。导出成 Word 之后连编号都没了。
3. **写不出就编**。库里没有覆盖这个话题的文献时，模型照样能写出一段通顺的话——它用的是自己的参数，不是库里的证据。

所以 09 不是"把大纲功能做强一点"，而是换掉产出物的形态：**从"一段文字"换成"句子结构体 + 文献表 + 映射"**。

## 2. 三层数据模型：为什么必须有两套编号

```
句子 (type=claim) ──cite_nos──▶ 引#N ──chunk_id──▶ chunks 行（原文/页/章节）
                                    │
                                    └──paper──▶ 参考文献 [K]（papers 表一条记录）
```

- **`引#N` 是 chunk 级**：指向一句具体原文。正文里点它，能看到"第几页、哪一段、英文原句是什么"。这是溯源真正需要的那一级。
- **`[K]` 是文献级**：参考文献列表的编号，是读者在论文里看到的形态。
- 两者由 `chunk → paper` 连起来，响应体里同时给出 `sentences[].cite_nos`、`sentences[].ref_nos` 和 `ref_map[]`。

为什么要两套而不是合并成一套：**合并就必然丢信息**。只留 `[K]`，同一篇论文的五个不同段落变成一个号，句子之间就无法区分"哪一句支撑哪一句"；只留 `引#N`，读者拿到的不是一篇能投的稿子。任务要求"导出时必须保留引用编号与文献列表的映射关系"，说的正是这条链不能断。

## 3. 流水线

```
规划段落 → 逐段检索证据 → 逐句写作 → 句子级校验 → References 生成 + 回库复核 → 渲染/导出
```

| 阶段 | 模块 | 确定性? |
|---|---|---|
| 规划段落 | `compose.plan_sections` | LLM 出结构，服务端过滤「参考文献」类章节、失败退模板 |
| 检索证据 | `evidence.collect_section_evidence` | 检索 + 版式过滤 + 相关性下限，全确定性 |
| 逐句写作 | `compose.write_section` | LLM 出句子与类型 |
| 句子级校验 | `sentences.*` | 全确定性：类型复核、编号越界、数值落地 |
| References | `references.build_references` + `verify_references` | 全确定性：从 `papers` 表生成并回库复查 |
| 渲染导出 | `service.render_markdown` + `_export` | 全确定性 |

一句话概括分工：**模型只负责"在给定证据里把话说顺，并老实标明哪句是过渡"，其余全部由服务端算。**

## 4. 句子级来源绑定

`write_section` 的产出不是字符串，是句子数组：

```json
{"id":"s1-1","type":"claim","text":"注意力机制在序列建模中已是核心组件。",
 "cite_nos":[3],"chunk_ids":["chk_12fa20f0918e445d"],"ref_nos":[1]}
```

实现上有四个坑，都是实测踩出来的：

### 4.1 切句必须连引用一起切

模型写的是「……更稳定。[引#3]」——引用在句号**之后**。只在句号处切，`[引#3]` 会被甩到下一句开头，于是本句"没有引用"被判删、下一句凭空多出一个引用。综述模块踩过（一次丢掉 15 个簇的首句），这里直接沿用结论：句子单元 = 到句末标点为止的正文 + 紧跟其后的引用标记。

### 4.2 编号越界即作废

编号是全篇唯一的，所以"本段合法编号"就是本段证据那一小撮。模型引了本段之外的号（甚至别的段的号），该号作废并记账 `cite_out_of_section`；作废后没有有效引用 → 整句删。

### 4.3 引用可以写在数组字段里，但别指望

主路径是行内 `[引#N]`。模型偶尔输出 `{"text":"…","cite":[3]}`，`_normalize_declared` 兜了一层：数组里有号而正文没有标记时，把号补成行内标记。**但这是兜底不是鼓励**——综述阶段试过"引用放数组字段"，模型会把字段名写进正文（`……。refs":[2]`），整块 JSON 解析失败、全篇降级。

### 4.4 模型会把 `[12]` 当引用

它按论文习惯写方括号数字，那是它脑补的文献序号，库里没有这套编号体系。`BRACKET_REF_RE` 在切句时清掉并记 `bracket_ref_stripped`——留着就是一条假引用。

## 5. 「无需引用」的过渡句：必须有，但必须防滥用

任务要求"过渡句、逻辑连接句标记为无需引用类型"。这句话落到实现上是个**口子**：只要能标 bridge，就可以不给引用。

三道防线：

1. **改判**（`sentences.sentence_type`）：模型标 bridge 的句子，服务端复核文本——含数字、含比较/效果断言（优于/高于/提升/降低/显著/出色/广泛…）、或带引用标记的，一律改判 `claim`；改判后没有引用 → 整句删。
2. **判残片**：模型常把承接词单独输出成一项（`{"type":"bridge","text":"在此基础上，"}`），后面紧跟 claim 项。渲染出来是正文里孤零零一行"在此基础上，"。这类残片（<8 字或无句末标点）判废 `bridge_fragment`。
3. **服务端补结构性过渡**：段首若无 bridge，由服务端插入一句

   > 在上文关于「X」的讨论基础上，本节进一步讨论「Y」。

   这句话只陈述"上一节讲什么、本节讲什么"，不涉及任何事实、数字、判断——所以它天然不需要引用，也不可能编造。反过来，让模型自由发挥过渡句，它很容易写成"综上可见，该方法具有广阔前景"，那正是这个口子最危险的用法。

改判在 `--selftest` 里可以直接看到：

```
① bridge 伪装成过渡句
   模型声明：bridge   实际判定：claim（bridge_with_claim_cues）
   无引用 → 整句删除
```

**已知边界**：线索词法挡不住"弱断言"。"在此基础上，注意力机制在处理图像时遇到了一些挑战。"不含数字、不含比较词，会被放行。这是词表法的天花板，见 §10。

## 6. References：模型根本没有写参考文献的机会

任务要求"禁止生成库外文献条目，即使格式看起来正确"。靠 prompt 里写"不要编造参考文献"是守不住的——参考文献恰好是大模型最擅长编得像真的东西：作者、年份、会议、页码、DOI 全能编得整整齐齐。

所以换了思路：**模型不产出 References**。正文只有 `[引#N]`，参考文献由服务端按被引 chunk 反查 `papers` 表生成，顺序 = 首次被引顺序。

### 6.1 三次校验

| 检查 | 触发条件 | 处理 |
|---|---|---|
| `not_in_library` | `papers` 表按 id 查不到 | 整条拒收，计入 `stats.refs_rejected` |
| `arxiv_mismatch` | 查到的论文 arxiv_id 与条目不符 | 拒收（两个 id 指向两篇论文，不能猜） |
| `title_mismatch` | 库里标题与生成用的不一致 | 以**库内标题为准**覆盖（文献是真的，只是元数据漂了） |
| `no_chunks` | 论文在库但没有正文 chunk | 保留条目，标 `checked=false` + `unverifiable` |

### 6.2 反向审计：正文里的库外标识

正文里出现的 `arXiv:xxxx` / `DOI` 若不属于任何一条参考文献，视为模型自己写进去的库外文献——**从正文删掉**并计入 `stats.fabricated_refs`。删完还要清理残句：`已有工作（arXiv:2401.12345，doi:10.9999/fake.2024）给出……` 直接删标识会留下 `已有工作（，doi:）给出……`，这种残句比留着假文献更糟，读者会以为这里原本有内容。所以还有一步"空括号 + 裸标签"清理。

```
③ 库外文献标识
   清理后正文：已有工作给出了相同结论。
   被清掉的标识：[arxiv 2401.12345, doi 10.9999/fake.2024]
```

### 6.3 校验器第一次跑就把自己人抓了

第一版 `build_references` 用 chunk payload 里的 `paper_id` 去查 `papers` 表，结果：

```
refs 0   refs_rejected 2
```

8 句结论、2 篇真实文献，References 列表**空的**。原因：向量库 payload 的 `paper_id` 不是 `papers.id`，而是入库时拼的 `{arxiv_id}::{version}` 复合键（`2106.09685::v2`）。关系库里根本没有这个 id。

这件事的价值不在"修了个 bug"，而在**校验器没有放行**：它回库重查，查不到就拒，而不是生成一条 `paper_id=2106.09685::v2` 的参考文献。修法是换 join key——`arxiv_id` 才是持久身份（`references.index_by_arxiv`）。

### 6.4 同一份响应里不能有两种 `paper_id`

上面那个坑还有下半场：join 改对了，但接口把 chunk payload 的原样 `paper_id`（`1810.04805::v2`）直接返回给前端，前端拿它去查论文必然查不到。修法不是"前端兼容两种 id"，而是**对外只给一种**：

```python
paper_by_arxiv = {r["arxiv_id"]: r["paper_id"] for r in refs}
"paper_id": paper_by_arxiv.get(u.arxiv_id, ""),   # 关系库 papers.id
"chunk_paper_ref": u.paper_id,                   # 复合键，仅备查
```

`evidence[]` 和 `ref_map[]` 两处都按这个口径改，没有例外——同一份响应里一半字段能点开论文、一半点不开，是最难查的那类 bug。

验证：`pap_0932b4d974124926` / `pap_dbfad0ef3d384d3a` 直接对应 `papers` 表的 `id`（BERT / LoRA），不是拼出来的。

### 6.5 `used_in` 骗过自己人

`ref_map` 早先的 `used_in` 取的是 `EvidenceUnit.sections`——那是**检索时命中过它的段落**。于是"LoRA p.5"这条证据明明一次都没被正文引用（`ref_no` 为空），`used_in` 却写着 `["S1","S2","S3","S4"]`。看 json 的人只会得出一个结论：这段原文四段都用上了。

改成两个字段，各说一件事：

| 字段 | 含义 | 空值说明 |
|---|---|---|
| `used_in` | 真的引用了它的**句子 id** | 检索到但正文没用 |
| `hit_in` | 检索命中过它的段落 id | 没被任何段落检索到 |

实测一份稿子里 6 条证据，`used_in` 非空的只有 4 条，另 2 条 `ref_no` 为空、`used_in` 为 `[]`——这才是真实情况。

## 7. 无证据段：占位而不是编造

三种情况都走占位，且都必须说清"缺什么"：

1. **检索不到正文**：命中的全是表格残渣/参考文献/图注。
2. **相关性不过关**：检索永远返回 top-k，库里没有这个话题时它照样端上一堆别的论文的段落。实测拿「量子纠错码的表面码容错阈值」去检索，回来的全是 LoRA 论文的正文，模型于是写出「低秩适应在量子计算中的应用」——每句都有引用，整段是胡话。**引用校验拦不住这种错误（引用是真的）**。
3. **模型读完说写不出**：prompt 明确允许 `{"sentences":[],"insufficient":true,"gap":"…"}`。

第 2 条需要一道"这段证据到底在不在讲这件事"的闸。用的是 07 的跨语言语义模型（`services/rag/semantic.py`），闸门跑**主题**而不是段落 query：

| 样本 | 余弦 |
|---|---|
| 同主题正文（"注意力架构" ↔ ViT 段落） | 0.40 ~ 0.60 |
| 同主题正文（"ViT 图像识别" ↔ ViT 段落） | 0.598 |
| 跑题正文（"量子纠错" ↔ LoRA 段落） | 0.185 / 0.213 |
| 页眉/版权行（"Published as a conference paper…"） | 0.305 ~ 0.328 |

阈值取 0.30，页眉那类不靠阈值兜——它们由版式特征单独剔掉（`evidence._BOILERPLATE_RE`）。**闸门用主题、检索用段落 query**：先用段落 query 试过一次，一节 4 段证据全部低于阈值、整段变占位，可库里明明有 ViT 的局限讨论——段落 query 太具体（"Transformer 及类似架构在实际应用中遇到的问题或限制"），跨语言余弦被措辞差异拖死。粗判断交给闸门，细判断本来就是检索排序的活。

真实结果（「量子纠错码的表面码容错阈值」）：

```
[1] 引言                    —— 占位：缺乏关于量子纠错码和表面码基本概念的介绍以及研究重要性的证据
[2] 表面码的基本原理        —— 占位：本段检索不到可用的正文证据（命中的都是表格/参考文献等非正文片段）
[3] 表面码容错阈值的研究方法 —— 占位：缺乏关于表面码容错阈值的研究方法和技术具体证据
[4] 局限与未来方向          —— 占位：缺乏关于表面码容错阈值局限性及未来研究方向的证据

段落 4 · 句子 0 · 结论句 0 · 参考文献 0 · 无证据占位 4
拒答：本主题下没有任何句子通过引用/数值校验，全部段落为空——按约定不生成正文，只报缺口。
```

**整篇拒答也是结果**：给空稿 + 每段缺什么，而不是给一段看起来正常的空话。

## 8. 导出：映射关系跟着文件走

两份产物，同一个中间表示：

- **Markdown**（人读）：正文保留 `[引#N]`，末尾 `## 参考文献` 用 `[K]`，再附「引文映射」表（引# → [K] → 页 → chunk_id）。
- **JSON**（机读）：完整 `sections/sentences/references/ref_map/stats`，不裁剪字段。md 里的表会截断 chunk_id，重新编号或二次处理需要 json。

映射表只列**正文真的引用了的**证据。把"检索到但没引用"的也列进来，读者会看到一堆 `[—]`（无对应文献），第一反应是"引用错乱"；那些留在 json 的 `ref_map` 里，md 末尾用一句"另有 N 段证据被检索到但未被引用"交代。

### 8.1 中文文件名把导出打成 500

`Content-Disposition: attachment; filename=注意力…md` —— HTTP 头按 latin-1 编码，星例在 `v.encode("latin-1")` 处抛 `UnicodeEncodeError`：

```
UnicodeEncodeError: 'latin-1' codec can't encode characters in position 33-41
```

用户看到的是 `Internal Server Error`。更糟的是前端只 `res.blob()`、不查 `res.ok`，于是**把这段错误文本当成 `.md` 存下来**——文件下载"成功"，打开是一行英文。两个都补了：服务端按 RFC 5987 给两个名字（ASCII 兜底 + `filename*=UTF-8''` 真实名），前端在 `!res.ok` 时直接报错而不是产出垃圾文件。

```
content-disposition: attachment; filename="Transformer.md";
  filename*=UTF-8''Transformer_%E7%9A%84%E5%B9%B6%E8%A1%8C%E5%8C%96...md
```

**导出是这条链的终点，终点处静默失败等于前面全白做**——所以导出也走了 HTTP 实测，而不是"代码看起来对"。


这段同时说明三件事：**每句结论都有编号**、**过渡句单独成句且不挂编号**、**参考文献三条都能在库里点到**（[1] 是本地 PDF，`[2]`/`[3]` 带 arXiv 链接）。

编号是**跳的**（1、3、4、5，没有 2 和 6）：`CiteIndex` 全篇一个 chunk 一个号，2 号和 6 号分给了"检索到但没被引用"的两段。编号跳号好过重新编号——重编会让 `ref_map` 里的 `引#2` 指向一段正文从未出现过的原文，一份导出文件拿到别处就对不上了。

这次运行还留下一个"防线真的拦住了"的实例，`trace.dropped` 里逐字可查：

```json
{"reason": "no_citation", "declared": "bridge", "why": "bridge_with_claim_cues",
 "text": "此外，对于视觉任务，纯粹的 Transformer 模型在没有强正则化的情况下，训练结果通常略低于同规模的 ResNet 模型。"}
```

模型把它标成 `bridge`（想免引用），文本里却有「低于」这个比较断言 + 没挂 `[引#N]` → 改判 claim → 无引用 → 删除。**同一句话在旧实现里会作为"过渡句"光明正大地留在正文里。**

## 10. 已知局限

1. **写作有方差。** 同主题两次运行，句子 9~11、段落标题会变（`temperature=0` 也不能保证端点确定）。对比实验必须看落盘 json。
2. **bridge 的判定靠线索词。** 弱断言（"遇到了一些挑战""值得关注"）能蒙过去。彻底的解法是让判定也走模型，但那样每句都要一次调用，代价不成比例；当前选择是"宁可放过弱断言，也不误删正常句子"。
3. **段落 query 决定成败。** 规划器给的中文 query 太抽象时，检索会端回表格残渣（实测 top-24 里只有 2 段正文）。已用"主题 + query"合并检索缓解，但根子在语料：5 篇论文、中英混排、表格 chunk 占比高。
4. **相关性闸只有一档阈值**，0.30 在"漏写"和"乱写"之间取平衡。它挡住过整段胡话（量子纠错主题），也误杀过本可写的段落（"局限性"一节 4 段证据全 0.217~0.339）。
5. **参考文献元数据依赖入库质量**。本地上传的 PDF（`upload_<hash>`）没有 arXiv 号，条目里只能给标题，且没有在线 PDF 可跳。
6. **段首主题句可以不带引用。** “尽管如此，在实际应用中，基于注意力机制的模型仍然面临一些挑战”这类句子没有具体断言、也没有线索词，按规则判为 bridge。它作为段落入口是合理的（下一句立刻给出带引用的具体例子），但它确实是一句“没证据的话”。判成 claim 删掉，段落就没有起头；留着，就等于承认这个口子。当前选择留着，并在界面上标「无需引用」——不假装它有证据。
7. **相邻段落可能复述同一个数字。** 同一篇论文的两段原文被两节各自命中时，正文会出现“从 1.2TB 降到 350GB”写两遍。溯源是准的（两处都指向各自的 chunk），但作为文章是重复的。要治得在生成时带上“已用过的证据”，属于内容规划层的事，不在本任务的溯源范围内。

## 11. 踩坑清单

1. **chunk payload 的 `paper_id` 是复合键**（`{arxiv_id}::{version}`），不是 `papers.id`。用它查库必空 → `refs=0`。改用 `arxiv_id` 做 join。
2. **"参考文献"四个字不能做滚动锚点**（截图脚本）：页头副标题里就有，`waitForFunction` 立刻命中，拍到的是加载态。锚点改用"库内已核验"/"引文映射表"。
3. **`{"type":"bridge","text":"在此基础上，"}`**：模型把承接词当独立句子输出，渲染成正文里一行残片。判废 + 服务端补结构性过渡。
4. **bridge 变成免死金牌**：把难写的判断句标 bridge 就不用给引用。文本复核改判 claim，改判后无引用即删。
5. **数字编造的漏网**：最初只校验"小数 / 3 位以上整数"，"显存降低 3 倍"这种一位数结论直接放过。加了量级单位（% 倍 × 成）一类。
6. **删标识留下空括号**：`（arXiv:…，doi:…）` 删完变 `（，doi:）`，比假文献更误导。要清空括号 + 裸标签。
7. **映射表列了未引用证据**：读者看到一堆 `[—]` 以为引用错乱。只列正文真的引用的。
8. **相关性闸用段落 query**：一节 4 段证据全被刷掉，整段变占位。闸门用主题。
9. **检索量不足**：每段 6 条证据但只取 top-24，过 `usable()` 只剩 2~4 段。提到 top-40（`RETRIEVE_MULTIPLIER=6`）。
10. **`next build` 写 `.next/trace` 报 EPERM**（沿用 08）：是执行环境的限制，不是文件锁；换目录、删 `.next` 都无用。
11. **`docker restart ai4s-web` 之后 `docker restart ai4s-gateway`**（沿用 06~08）：nginx 启动时解析上游 IP。
12. **中文文件名把导出打成 500**：`Content-Disposition` 头按 latin-1 编码，中文直接抛 `UnicodeEncodeError`。而且前端只 `res.blob()` 不查 `res.ok`，会把 `Internal Server Error` 存成 `.md`。服务端改 RFC 5987 双名，前端补 `!res.ok` 分支。
13. **`used_in` 的语义是"检索命中"不是"正文引用"**：`ref_map` 里一条从未被引用的证据（`ref_no` 为空）却显示四段都用过。拆成 `used_in`（引用它的句子）+ `hit_in`（命中的段落）。
14. **`et al.` 后面又补了一个句点**，渲染成 `et al..`。作者串自带句点时要跳过补点。
15. **价值判断词也是断言**："展现出巨大的潜力"被包装在"在此基础上，……"后面当过渡句用。`潜力/前景/价值/关键/核心/趋势/主流/首选/重要` 补进 `_CLAIM_CUES`；纯结构性的过渡句（"本节进一步讨论 X"）不受影响，改判后仍判 bridge。
