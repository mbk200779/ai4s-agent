## 一、先讲清楚：为什么"排得对"不能只靠精排

融合（dense + sparse + RRF）解决的是**召回**——保证正确的片段进了候选池。
它解决不了**排序**：RRF 只看两路的排名位次，候选池里"语义相似但答非所问"的段落恰好两路都能命中。

cross-encoder 结构上能补这一段：它把 `(query, passage)` 拼在一起读一遍，能分清
「β2 = 0.98 是本文的设置」和「β2 在光纤里是色散系数」——这是双塔做不到的。

**但第一版把精排当成"完全接管"，结果是把 Recall@5 从 84.9% 打到 54.5%。**

原因不是模型太差，而是**目标错位**：本项目的正确答案常常是一句 `β2 = 0.98` 或一行表格，
它在语义上并不"像答案"；而融合分里已经编码了「参数名 ≈ 数值」「实验设置段」「表格形态」
这些领域信号，通用 cross-encoder 是拿网页数据训出来的，看不到这些。

所以本步的结论不是"换更强的模型"，而是**三路合成 + 规则证据**：

```
final = α · norm(rerank)  +  (1-α) · norm(fusion)  +  rule_bonus · [规则命中]
        ↑ 语义精排            ↑ 融合先验（领域信号）      ↑ 字面硬证据
        α = 0.2              （0.8）                    0.35
```

三个权重都有扫描或实测依据，见第五节。

## 二、精排模块与降级逻辑（期望输出 ①）

### 2.1 在链路里的位置

```
question ─► 查询理解(03) ─► 分流策略(03) ─► 融合 top20 ─► 规则召回注入 ─► 精排 ─► top5
                    │                        (candidate_k=20)    │            │
                    │                                             │            └─ 失败/超时/关闸 → 融合原序（不报错）
                    └─ search_text（英文译文）─── 精排读的是同一段文本 ─────────┘
```

两个接线细节，错了会静默变差：

- **`candidate_k = max(top_k, RERANK_TOP_N)`**（`retrieve.py`）：要给精排 20 条才有的可选。
  精排关闭时保持 `top_k`——不能因为"上了精排"就让关闭档也悄悄变了召回宽度，否则 A/B 对比不成立。
- **精排读 `text`（检索文本）而不是 `question`**：QA 链路会先把中文问句翻成英文再检索，
  检索用译文、精排用原句就是两边各说各话，而且默认模型是英文的。
- **拒答用的原始分在重排之前取**：`top_raw_score = max(raw_score of 候选池)`，
  不是"重排后 top5 里的最高 raw"。否则会出现误拒答——精排把 RRF 分低但语义准的段落提到第 1，
  原本 RRF 高的那条被挤出前 5，最高原始分凭空掉到阈值以下（实测「Attention 用了多少块 GPU」
  就是这么被拒的：0.0146 < 0.015，改口径后 0.0151 且答案正确）。

### 2.2 两种排序模式

| 类型 | mode | 行为 | 为什么 |
|---|---|---|---|
| point / nav / generic | `flat` | 按最终分全局降序 | 单点事实，最优解就是"最相关的那一条排第一" |
| compare / survey | `coverage` | **按论文轮转**：先排每篇的最高分，再在篇内排 | 对比题的价值是"每篇都给出对应片段"；全局排序会把一篇的 5 段全排前面，另一篇一段不剩——那是把对比题做成单篇问答 |

`coverage` 的收益在数据上最明显：论文覆盖@5 从 **0.786 → 0.881**（见第五节）。

### 2.3 降级逻辑：五条出口，一条铁律

**铁律：精排的任何失败都不得影响主链路。** `Reranker.apply()` 没有 `raise` 路径，
所有异常都收敛成 `applied=False` + `degrade_reason`。

| 出口 | 触发条件 | `degraded` | trace 里的原因 |
|---|---|---|---|
| 开关关闭 | `enabled=False`（env 或请求体） | false | `None`（这是主动关，不是故障） |
| 无候选 | `candidates == []` | false | `None` |
| 语言闸门 | 非多语言模型 + 问句 CJK 占比 ≥ 5% | **true** | 「问句非英文，英文精排模型不适用，已降级为融合原序」 |
| 单条候选 | `len(candidates) == 1` | false | 「只有 1 条候选，无需精排」 |
| 熔断中 | 连续失败 ≥ 2 次后 30s 内 | **true** | 「熔断中（上次失败，Xs 后重试）」 |
| 推理异常/超时 | `future.result(timeout)` 抛错、打分条数不匹配 | **true** | `{异常类型}: {消息}` |

降级后 `results = candidates[:top_k]`（融合原序，若开了规则召回则注入项按分合并），
调用方拿到的永远是"能用的五条"，永远不是异常。

### 2.4 超时不是"掐掉就完事"：三个配套机制

| 机制 | 实现 | 解决什么 |
|---|---|---|
| **墙钟预算** | `future.result(timeout=1500ms)`，推理丢进 `ThreadPoolExecutor(max_workers=1)` | onnxruntime 推理是同步阻塞的，没有中断接口，只能掐等待的一端 |
| **熔断** | 连续失败 2 次 → 30s 内直接降级 | 单次超时可能只是这条问题特别长，不该一次就熔断；但连续两次说明环境真的不行，再等下去每条请求都白等 1.2s |
| **单飞闸门** | 全局 `threading.Event`，`_RERANK_BUSY` 已置位时**不排队直接降级** | 超时只是"不再等它"，那次推理还在跑。不拦的话后续请求全排在同一条队列上，表现为"一次超时之后全都在超时" |

外加一条：**模型加载后先做一次热身推理**（`model.rerank("warm up", [...])`）。
不热身的话第一次真实请求要背模型 graph 初始化的开销，实测必撞超时 → 熔断 → 整轮评测全降级。

### 2.5 缓存：key 必须是 `query_hash + index_snapshot_id`

```python
key = f"{model_name}:{query_hash(query)}:{index_snapshot_id(vector_store)}"
# 例：Xenova/ms-marco-MiniLM-L-6-v2:9f3c1d2a7b0e4c58:2b7e0f19c4a3
```

| 设计点 | 做法 | 不做会怎样 |
|---|---|---|
| query 归一化 | 小写、压空白、去首尾标点后 `sha1[:16]` | 「β2 是多少」「β2是多少？」算两次，缓存命中率腰斩 |
| 快照 = 内容指纹 | `sha1(collection#size#(arxiv_id:version:片段数)...)`，60s 缓存 | 只按"集合名+点数"做指纹：**换版本时点数不变**，旧缓存会继续命中，改了正文却看不到变化 |
| 模型名做前缀分区 | 见上 | A/B 第二组直接读到第一组的缓存，测出来"两个模型一模一样"（这个坑真踩了，见第六节） |
| 存 `chunk_id → 分数` | 不是存整条结果 | 候选集微调后仍能命中大部分；但**部分命中按 miss 重算**，不拿半份分数凑排序 |
| 容量/TTL | 512 条 LRU，900s | 演示环境内存有限，也要防止长跑后缓存变成"上一次入库的化石" |

### 2.6 trace：过程数据全部外露

`trace.rerank` 直接来自 `RerankOutcome.to_trace()`：

```json
{
  "enabled": true, "source": "env", "applied": true, "degraded": false,
  "degrade_reason": null, "model": "Xenova/ms-marco-MiniLM-L-6-v2",
  "mode": "cross-encoder", "candidates": 20, "output": 5, "returned": 5,
  "cache": "miss", "cache_key": "…:9f3c1d2a7b0e4c58:2b7e0f19c4a3",
  "index_snapshot_id": "2b7e0f19c4a3", "latency_ms": 412.7,
  "moved": [{"chunk_id": "…", "page": 7, "from": 3, "to": 1, "delta": 2}],
  "scores": [{
    "rank": 1, "page": 7, "kind": "paragraph",
    "fusion_rank": 3, "rerank_raw": 6.71, "rerank_score": 1.0,
    "fusion_score": 0.62, "final_score": 0.696
  }]
}
```

`moved` 只记"位次变动 ≥ 2"的条目——那是精排真正改判的地方，
前端 `RoutingTrace.tsx` 直接展开这一块，比"精排跑了 412ms"有用得多。

`final_score` 就是三路合成分，**融合分在 `apply()` 之前快照**（`fusion_scores`），
不是事后从 `r.score` 读——`_reorder` 会把 `r.score` 改写成合成分（这个坑也踩了）。

## 三、规则召回表（期望输出 ②）

### 3.1 为什么这一层必须存在，且必须"扫全语料"

数值类问题的答案常常只出现在**一个孤立的单元格**里，那段文本没有任何语义上下文，
dense 和 sparse 都不会把它召回——**不是排得靠后，是压根进不了候选池**。
这时精排无能为力，只能靠字面扫描把它捞出来。

代价是 `O(片段数 × 探针数)` 的正则匹配：实测 285 段 × 3 探针 **约 2ms**，比一次 embedding 便宜得多。

同一张表还被三种问法共用：point 问「β2 多少」、nav 问「8×A100 出现在哪一页」、
compare 问「两篇的 β2 差多少」——所以它放在**召回层**，不塞进某个策略。

### 3.2 规则表（`NUMERIC_RULES`，10 条）

同时通过 `GET /api/v1/rag/numeric-rules` 暴露——规则表是代码里的数据，文档会过期，端点不会。

| # | 规则 id | 名称 | kind | 权重 | 示例 | 设计说明 |
|---|---|---|---|---|---|---|
| 1 | `num-symbol-subscript` | 带下标的希腊符号 | symbol | **1.00** | `β₂` / `β2` / `\beta_2` | 三种写法必须互相命中：问句写 β₂、正文写 β2、附录写 `\beta_2` |
| 2 | `num-symbol-bare` | 裸希腊符号 | symbol | 0.55 | `α` / `λ` / `ε` | 无下标时区分度低（α 满篇都是），权重压一半 |
| 3 | `num-hardware-count` | 硬件数量×型号 | hardware | **1.00** | `8×A100` / `8 块 V100` / `eight P100 GPUs` | 数量与型号必须同时出现；正文写「8 NVIDIA P100 GPUs」也要命中「8×P100」 |
| 4 | `num-hardware-model` | 硬件型号 | hardware | 0.45 | `A100` / `V100` / `TPU v3` | 只有型号说明这段在讲硬件，不足以定位 |
| 5 | `num-metric-value` | 指标 + 数值 | metric | **1.00** | `BLEU 28.4` / `F1 = 0.87` / `accuracy 92.3%` | 指标名与数值间距收紧到 12 字符，否则会跨列命中表格里的无关数字 |
| 6 | `num-scientific` | 科学计数法 | numeric | 0.85 | `10⁻⁹` / `1e-4` / `10^-9` | PDF 里常被抽成 `10−9`，上标要归一到 e 记法 |
| 7 | `num-percent` | 百分比 | numeric | 0.60 | `92.3%` / `15.4 %` | 单独出现区分度一般，配指标名时极准 |
| 8 | `num-range` | 区间 | numeric | 0.50 | `64~512` / `0.8–1.2` | 超参搜索空间里常见，单独出现偏弱 |
| 9 | `num-formula-complexity` | 复杂度/公式记号 | formula | 0.80 | `O(n²)` / `\frac` / `\sum` | 复杂度记号是公式类查询最直接的锚点 |
| 10 | `num-chart-ref` | 图表/公式编号 | chart | 0.35 | `Table 3` / `Figure 2` / `图 4` | 满篇都是「Table 1」，只当辅助信号 |

### 3.3 从问句抽"探针"（`scan_query`）

一个 `Probe` 是「要找的东西 + 它的所有等价写法」：

```python
Probe(rule_id="num-symbol-subscript", kind="symbol", raw="β₂", label="beta2",
      patterns=("β\\s*[_^]?\\s*\\{?2\\}?", "β₂", "\\bbeta\\s*[_^]?\\s*\\{?2\\}?\\b", "\\\\beta\\s*[_^]?\\s*\\{?2\\}?"),
      weight=1.0)
```

三个归一化处理：

- **数词**：`eight P100 GPUs` ↔ `8×P100`，`八块卡` ↔ `8`（`_NUMBER_WORDS`）；
- **上下标**：`β₂`（unicode）/ `β2`（ASCII）/ `β_2` / `\beta_2` 四种写法等价；
- **去重**：同名探针只留第一次出现（顺序即权重顺序），避免同一符号被抽成 4 个探针重复加分。

### 3.4 表格判定：不是 `kind == "table"`，而是"单元格形态"

**这是本层唯一一个反直觉的设计。** 本项目的 PDF 表格抽取质量参差：
`kind=table` 的片段里有大量 `' | | | | '` 空壳，而真正有内容的表格行常被切成 `paragraph` 或 `reference`。
所以按**形态**判，不按 kind 判（`is_cell_like`）：

| 判据 | 说明 |
|---|---|
| 竖线 ≥ 2 | 表格线残留 |
| ≥ 3 行且数字占比 ≥ 10% | 一行一个数 |
| ≤ 40 字符且含数字 | 单个单元格 |

命中形态时规则分 **× 1.6**（`NUMERIC_CELL_MULT`），而不是"表格加固定分"——
形态是**相关性证据**，不是**类型偏好**：固定加分会把所有表格一起上浮，乘系数只放大真的命中了探针的那几条。

另一条反向修正：`kind == "reference"` 的片段 **× 0.5**。
参考文献里同样会出现 `BLEU 28.4` 这类串，但那是引用别人的数据，不是本文的结论。

### 3.5 注入策略（`retrieve.py`）

| 情况 | 处理 |
|---|---|
| 片段已在融合候选里 | **只标注** `hit_source = "fusion+rule"`，不重复注入（重复注入会让同一条在 trace 里出现两次，A/B 时也算两票） |
| 新片段 | 注入，`hit_source = "rule:<命中标签>"`，`raw_score = None`（没有融合分，不参与 RRF 拒答判定） |
| 注入条数 | `NUMERIC_RECALL_LIMIT = 8`；分数按 `boost / top_boost` 归一到 0~1，和融合分同量级 |
| 论文范围 | **只在"融合候选里已出现过的论文"内部扫**（`NUMERIC_PAPER_SCOPE = True`），见 3.6 |
| 策略 | `nav` **跳过**（它本来就在全语料做字面扫描，重复劳动会搅乱锚点命中排序）；`chitchat` 跳过 |
| 拒答口径 | 首条是规则命中的孤立片段时 `threshold = 0.0`（没有融合分，拿阈值卡它等于用尺子量温度） |

### 3.6 为什么规则召回要限定论文范围（本轮最重要的一次返工）

这是端到端冒烟抓出来的问题，离线评测**没有**报错——因为指标全都在涨。

**现象**：问「β2 设为多少」，关掉精排一切正常（`β2 = 0.98`，Attention 第 7 页）；
打开规则召回后答案变成 `β2 = −20 ps/nm/km`，引用一篇光纤孤子论文的第 2 页。

**原因**：符号是多义的。`β2` 在 Transformer 论文里是 Adam 的 0.98，在光纤论文里是色散系数 −20 ps/nm/km。
两条都"字面命中 β2"，规则分一样高（还是单元格形态，×1.6），
规则的 `rule_bonus = 0.35` 又是**硬加成**，于是它稳稳坐上前二，生成阶段照着它回答。

**为什么离线评测没发现**：`p-beta2` 在 full 配置下的 MRR 只是从 1.00 掉到 0.50，
看起来像"精排把正确段落从第 1 挪到第 2"，很合理，没人会追。
只有把整条链路跑一遍、看见答案本身错了，才知道第 1 名是谁。

**修法**：融合候选已经指出"用户问的是哪几篇"，规则层没有语义能力判断归属，就不该越权：

```python
anchor = {r.arxiv_id for r in candidates}      # 融合候选带来的论文
numeric_res = numeric_rules.recall(corpus, probes, paper_ids=anchor)
```

规则召回只在已选定的论文内部找那个孤立单元格；"该找哪几篇"留给融合。
范围、跳过条数都进 trace（`numeric.paper_scope` / `numeric.out_of_scope`），
冒烟时能直接看到「scope=4、out_of_scope=40」。

**代价**：如果融合完全没召回正确论文，规则层也救不回来。
这是有意的权力划分——跨论文引入新证据是融合的职责，两侧都越权只会互相打脸。

**修复前后（同一条问题）**：

| 配置 | 修复前 | 修复后 |
|---|---|---|
| 只开规则召回 | β2 = −20 ps/nm/km（光纤论文 p2） | β2 = 0.98（Attention p7） |
| 精排 + 规则召回 | β2 = −20 ps/nm/km（光纤论文 p2 排第 2） | β2 = 0.98（Attention p7 排第 1） |
| `p-beta2` MRR（离线评测） | 0.50 | 1.00 |

顺带一个反直觉的副作用：修复后 routing 集的「论文覆盖@5」从 0.952 掉到 **0.881**。
0.952 是假的——跨论文注入把不相干的论文塞进前 5，覆盖数被刷高了。0.881 才是 coverage 模式的真实收益。

## 四、开关配置（期望输出 ③）

### 4.1 三层开关，从全局到单次请求

| 层 | 位置 | 键 | 默认 | 用途 |
|---|---|---|---|---|
| 环境 / 部署 | `docker-compose.yml` → `api.environment` | `RERANK_ENABLED` | `true` | 一键关掉精排（整机） |
| | | `RERANK_MODEL` | `Xenova/ms-marco-MiniLM-L-6-v2` | 换模型 |
| | | `RERANK_TIMEOUT_MS` | `1500` | 墙钟预算（分布右尾实测 1200ms，留 25% 余量） |
| | | `NUMERIC_RECALL_ENABLED` | `true` | 一键关掉规则召回 |
| 应用配置 | `app/core/config.py` | `rerank_alpha` | `0.2` | 精排权重 α |
| | | `rerank_rule_bonus` | `0.35` | 规则证据加成 |
| 单次请求 | `POST /api/v1/rag/route` | `rerank: bool \| null` | `null`（跟随 env） | **A/B 用**：同一批问题跑两遍 |
| | | `numeric: bool \| null` | `null` | 单独隔离规则召回的收益 |
| | `POST /api/v1/qa/ask` | `rerank` / `numeric` | 同上 | 端到端 A/B |

`source` 字段会记下这次到底是谁决定的（`env` / `request` / `disabled`），trace 里能看到，
避免"以为在测精排，其实环境变量早就关了"。

### 4.2 配套运维端点

| 端点 | 作用 |
|---|---|

## 五、Recall@5 前后对比数据（期望输出 ④）

### 5.1 α 扫描（33 条样本，融合 top20 → top5）

`backend/scripts/tune_rerank_blend.py`，模型 `Xenova/ms-marco-MiniLM-L-6-v2`，
候选池固定、只改混合权重：

| 配置 | Recall@5 | MRR@5 | 分数据集 Recall |
|---|---|---|---|
| 融合原序（= 关精排，α=0） | 78.8% | 0.679 | routing 100% / rerank 56% |
| 混合 α=0.2（无规则加成） | 81.8% | 0.700 | routing 100% / rerank 62% |
| 混合 α=0.5 | 84.9% | 0.605 | routing 100% / rerank 69% |
| 混合 α=0.8 | 63.6% | 0.516 | routing 76% / rerank 50% |
| 纯精排（α=1） | **54.5%** | 0.495 | routing 65% / rerank 44% |
| α=0.2 + 规则加成 0.35（默认） | 84.8% | 0.715 | routing 100% / rerank 69% |
| α=0.3 + 规则加成 | 84.8% | 0.720 | routing 100% / rerank 69% |
| α=0.4 + 规则加成 | 84.8% | 0.684 | routing 100% / rerank 69% |
| α=0.5 + 规则加成 | 87.9% | 0.624 | routing 100% / rerank 75% |
| α=0.6 + 规则加成 | 84.8% | 0.577 | routing 94% / rerank 75% |
| boundary（只让精排决定第 k 名） | 84.9% | 0.719 | routing 100% / rerank 69% |
| head2（前 2 名锁定） | 81.8% | 0.722 | routing 94% / rerank 69% |

怎么读这张表：

1. **α=1 是断崖**（84.8% → 54.5%）。纯精排不是"稍微差一点"，是把数值类召回整个打穿。
   α 越大越接近"语义模型说了算"，数值题最先崩。
2. **α≥0.5 之后 Recall 是拿 MRR 换来的**：α=0.5 的 Recall 停在 84.8~87.9%，但 MRR 掉到 0.62，
   且 routing 集上 Recall 反而掉到 94%。这不叫"更好"，叫"更赌"。
3. **规则加成是"白拿"的**：同一 α=0.2 下 MRR 从 0.700 涨到 0.715，Recall 从 81.8% 涨到 84.8%。
4. **α=0.2 与 α=0.3 在统计上不可区分**（84.8%/0.715 vs 84.8%/0.720，差 0.005 MRR ≈ 0.17 条样本）。
   取更保守的 0.2：它更信融合先验，而数值类场景里融合先验恰恰是更可靠的那一路。
5. **`boundary` / `head2` 并不比调 α 优雅**：`boundary` 84.9%/0.719 与 α=0.2 几乎同分，
   但实现上多一条分支，且"哪一条该由精排决定"本身又是一个要调的参数。
   α 只有一个旋钮、两种排序模式都能复用，所以选 α=0.2。

> 一条方法论备注：早期版本有个 `promote_only` 策略，指标是 100%——因为它用 gold 决定
> "前 k 名里没有 gold 就换人"。那是拿答案做题，指标没有意义。`boundary` / `head2`
> 重写成"判定条件里不出现 gold"之后才可信。

### 5.2 固定候选池的 A/B（正式评测）

候选池 = 融合 top20，评估 top5，唯一变量是「排不排、用哪个模型」。

**routing 数据集**（18 条，gold 在候选池里的比例 **94.4%**）：

| 配置 | Recall@5 | MRR@5 | 论文覆盖@5 | 平均耗时 | 降级 |
|---|---|---|---|---|---|
| fusion（关精排） | 100.0% | 0.931 | 0.786 | 0.0 ms | 0/18 |
| numeric（只开规则召回） | 100.0% | 0.931 | 0.833 | 126.1 ms | 0/18 |
| rerank:minilm | 100.0% | 0.903 | 0.714 | 362.1 ms | 0/18 |
| **full:minilm（默认配置）** | **100.0%** | 0.893 | **0.881** | 596.5 ms | 0/18 |
| rerank:jina-turbo | 88.9% | 0.698 | 0.714 | 494.4 ms | 0/18 |
| full:jina-turbo | 100.0% | 0.893 | 0.881 | 648.1 ms | 0/18 |

**rerank 数据集**（16 条数值/公式题，gold 在候选池里的比例 **87.5%**）：

| 配置 | Recall@5 | MRR@5 | 平均耗时 | 降级 |
|---|---|---|---|---|
| fusion（关精排） | 62.5% | 0.486 | 0.0 ms | 0/16 |
| numeric（只开规则召回） | 68.8% | 0.499 | 103.2 ms | 0/16 |
| rerank:minilm | 62.5% | 0.490 | 422.9 ms | 0/16 |
| **full:minilm（默认配置）** | **68.8%** | **0.521** | 654.9 ms | 0/16 |
| rerank:jina-turbo | 62.5% | 0.341 | 556.2 ms | 0/16 |
| full:jina-turbo | 68.8% | 0.521 | 687.8 ms | 0/16 |

**结论（可直接引用）**：

- Recall@5 **没有下降**：routing 持平 100%，数值题 62.5% → **68.8%（+6.3pt）**；
- 对比/综述的**论文覆盖** 0.786 → **0.881（+9.5pt）**——这是 coverage 模式的主要价值
  （早期一版是 0.952，那是跨论文注入刷出来的假收益，见 3.6）；
- MRR 略降（0.931 → 0.893），换来的是 Recall 不降 + 覆盖 +9.5pt。
  掉分位置集中在 `c-beta-diff`（1.00 → 0.33）：对比题里精排把两篇的差距段落排到了后面，
  而 `p-beta2` 这条在修复跨论文注入后回到 1.00；
- **`jina-reranker-v1-turbo-en` 不能做默认**：routing 集 Recall 掉到 88.9%、MRR 0.698。
  延迟也没优势（494ms vs 362ms），只作为"换模型"选项保留。

### 5.3 规则召回的单独收益（关掉精排、只开规则召回）

| 数据集 | Recall@5 | 典型翻盘题 |
|---|---|---|
| routing | 100% → 100%（覆盖 0.786 → 0.833） | — |
| rerank | 62.5% → **68.8%** | `q-att-alpha`（长度惩罚 α=0.6 在哪个设置下）、`q-bert-110m`（110M 参数包含多少层）、`q-lora-40m`（40.1M 对应哪个 rank） |

这三条都是"答案在一行表格/一句设置里"的题：融合召不回、精排也救不了，只有字面扫描能捞。

### 5.4 已知边界（不粉饰）

| 现象 | 数据 | 原因 | 处理 |
|---|---|---|---|
| 注入会挤掉边界上的 gold | `q-vit-batch4096`：fusion ✓(0.20) → numeric ✗ | 它在融合里只是第 5 名（0.20 分），注入任意一条 0.9+ 的规则命中都会把它推出前 5 | 注入条数 8/5/3 三档 Recall 完全一致（11/16 = 68.8%，见 `scripts/probe_limit.py`），说明收益不靠"数量"；此题属 α 也覆盖不到的边界 |
| 长片段贴着超时线 | `p-att-bleu` 实测 1200.4ms，正好压在线外 | 20 条候选里有数字密集型长片段，tokenizer 成本高于均值（均值 ~630ms） | 预算从 1200 → 1500，实测降级条数 1/18 → 0/18；单飞闸门 + 熔断仍兜底 |
| 中文问句走精排没意义 | CJK ≥ 5% 直接降级 | 默认模型是英文的，中文问句等于随机排序 | 语言闸门显式跳过并写明原因；要真正支持中文得换 `jina-reranker-v2-base-multilingual`（20 对约 2.5s，演示环境不可接受） |

`q-bert-768`、`q-eight-p100` 两条在整个候选池里就没有 gold（`gold_in_pool = 87.5%` 的那 2 条），
属于**召回问题**，不该算到精排头上——评测里 `gold_in_pool` 这一列存在的意义就是防止这个误判。

## 六、踩坑记录

| 坑 | 现象 | 根因 | 修法 |
|---|---|---|---|
| **英文模型 + 中文问句** | 「训练用了多少块 GPU」被排成两段无关 figure，正确的 `8 NVIDIA P100 GPUs` 掉出前 5 | cross-encoder 打分对中文输入等于随机 | 语言闸门：非多语言模型遇 CJK ≥ 5% 直接降级，并写明原因 |
| **两个模型结果一模一样** | `rerank:jina` 与 `rerank:minilm` 的 top-5 完全相同，但都 `applied=true` | `Reranker._model` 是全局单例，第二个模型**静默复用了第一个**；缓存 key 也没分区 | 改成 `_models: dict[str, Any]` 按名缓存；key 前面挂 `{model}:` |
| **α 怎么调都一样** | 每个 α 都测出同一个 Recall | `tune_rerank_blend.py` 在 `apply()` **之后**读 `c.score`，那时已被改写成精排归一化分 | 在 `apply()` 之前快照 `fusion = [c.score for c in cands]`；生产代码同样处理 |
| **指标虚高 100%** | `promote_only` 策略 Recall 100% | 策略用 gold 决定"要不要替换第 k 名"，拿答案做题 | 改成不看 gold 的 `boundary` / `head2` |
| **首次调用必超时** | 评测第一轮 `deg=16/16`，全部降级 | 模型加载 + graph 初始化算在第一次推理里，直接撞预算 | 加载后热身一次；熔断改"连续 2 次"；加单飞闸门；截断 400 字符 |
| **`docker cp` 之后 a/b 结果不一致** | 容器里跑的还是旧代码 | 只改了宿主文件没同步 | 每次改完 `docker cp`，最后重建镜像（本轮已重建） |
| **规则召回跨论文抓错** | 「β2 设为多少」答成 `β2 = −20 ps/nm/km`（光纤论文 p2），而正确值是 Attention 的 0.98 | 符号多义 + 规则分是硬加成；规则层没有语义能力判断"用户问的是哪一篇" | 规则召回限定在融合候选的论文范围内（`NUMERIC_PAPER_SCOPE`），trace 记 `paper_scope` / `out_of_scope`；详见 3.6 |
| **符号权重永远取到 0.55** | 所有希腊符号探针都按 `num-symbol-bare` 计分，`β₂` 也拿不到 1.00 | `RULE_BY_EXTRACTOR` 是 dict，两条 symbol 规则同 key，后写的覆盖前写的 | `_probe()` 增加 `rule_id` 参数，带下标时显式指定 `num-symbol-subscript` |
| **"A100" 里凭空抽出 `10^-0`** | 「8×A100 训练」多出一个科学计数法探针 | 正则里幂记号是可选的，`100` 被读成 10 的 0 次幂 | 幂记号改为必选（`^` / 上标 / `**` / 负号） |
| **精排把问答改成拒答** | 「Attention 用了多少块 GPU」原本能答，开精排后返回「置信度过低（0.0146 < 0.015）」 | 拒答口径取的是重排后 top5 的最高 RRF 原始分，重排一换人这个数就变了 | 改为在重排**之前**取候选池最高原始分，写进 trace（见 2.1）；重排只负责顺序，不负责"找没找到" |
| **`beta_2` 一个都抽不到** | 问句写 `beta_2`、`\beta_2` 时探针为空 | `\b` 在 `beta` 与 `_` 之间不成立（`_` 是 word 字符） | 改用 `(?![a-z])` 收尾；"名字 + 空格 + 数字"仍不允许，否则 `epsilon 1e-9` 会变成 `epsilon1` |
