# 13 · 索引 pipeline 版本化

> 一句话：**索引可以同时存在多份，切版本只是换一个指针。**
> 于是"换 embedding 模型"从"停服全库重灌"变成"后台建一份新的、灰度 30%、不行就回滚"。

相关文件：

| 重建任务（交付物 2） | `backend/app/services/index_rebuild.py`、`backend/app/tasks/index_tasks.py` |
| 集合切换（检索侧） | `backend/app/services/vector_store.py`（`use_collection`）、`rag/retrieve.py`、`rag/strategies.py` |

## 1. 问题：调一个参数，代价是全库重灌

有三个旋钮一改，已有的向量就不能用了：

| 旋钮 | 改了什么 | 旧向量为什么废了 |
| --- | --- | --- |
| embedding 模型 | 语义空间整个换掉 | 维度可能不同，同一段话的位置全变 |
| 送进模型的截断长度（`MAX_EMBED_CHARS`） | 同一段文字编码出的向量不同 | 检索结果变了，但配置里看不出来 |
| 切分策略 | chunk 的边界变了 | 片段本身变了，不只是向量 |

没有版本化时只有两条路：**停服重灌**（演示前一天没人敢动），或者**不动**（等于这个参数永远调不了）。

而在同一个 collection 里用 payload 字段区分版本也不行：

- Qdrant 的 named vector 维度是 **collection 级**的，换模型（1024 → 768）根本建不进去；
- 即使维度相同，两代向量的相似度也**不可比**，混在一个结果集里排序是没有意义的；
- 重建期间新点会污染线上查询，于是"边建边用"这件事不可能安全。

所以版本化的单位必须是 **collection**，不是行。

## 2. 版本字段与索引命名规则（交付物 1）

### 2.1 先分清三种"版本"

这套系统里有五个版本号，各管一段，**不能合并**——合并之后"回滚"就不知道该回滚哪一段：

| 字段 | 管什么 | 当前值 | 改了它要做什么 |
| --- | --- | --- | --- |
| `paper_versions.pipeline_version` | **解析**管线（PDF → chunk） | `v1.0.0` | 重新解析受影响文档 |
| `index_versions.pipeline_version` | **索引**管线（chunk → 向量） | `idx-1.0.0-555810c4` | 重建索引（本任务） |
| `confidence_version` / `unc_version` | 判定阈值口径 | `conf-v1.0.0` / `unc-v1.0.0` | 只改展示口径，不动数据 |
| `review_version` / `writing_version` | 生成参数 | `rev-v1.0.0` / `wrt-v1.0.0` | 只影响新生成的内容 |

解析与索引分开的理由很实在：换 PyMuPDF 的解析行为要重解析（几十分钟/篇），
换 embedding 模型只要把已有文本重新编码（几分钟/全库）。硬塞进一个字段，
每次改索引都得连带重解析一遍。

### 2.2 签名：只放会改变向量的东西

```python
def current_signature() -> dict:
    return {
        "schema": INDEX_SCHEMA,                      # payload 结构代次
        "splitter": SPLITTER,                        # structured-fragments/v1
        "dense_model": EmbedderService.DENSE_MODEL_NAME,
        "sparse_model": EmbedderService.SPARSE_MODEL_NAME,
        "embed_max_chars": MAX_EMBED_CHARS,          # 1500
    }
```

三个判断：

- **`embed_max_chars` 必须进签名。** 它是最容易漏的一项：截 1500 和截 3000
  是两套不同的向量，但它既不在模型名里、也不在 collection 名里。实测改一下，
  版本号从 `idx-1.0.0-555810c4` 变成 `idx-1.0.0-6716eb0b`——如果不进签名，
  新向量会被写进旧 collection 并覆盖旧点，而"重建期间查询不受影响"这条保证同时失效。
- **`batch_size` / `pages_per_batch` 不进签名。** 它们只影响重建的耗时与内存，
  不影响写进去的点。放进来会让"同一套索引"仅因为并发度不同就被判成两个版本。
- **模型名必须是常量。** 签名和真正加载的模型要同一个来源（`EmbedderService.DENSE_MODEL_NAME`）。
  写两处的话，换模型时改了一处，签名不变——这正是版本化要防的事。

### 2.3 命名规则

```
pipeline_version = idx-<索引管线版本>-<签名 sha1 前 8 位>     例：idx-1.0.0-555810c4
collection       = <基础名>__<pipeline_version>              例：ai4s_papers__idx-1.0.0-555810c4
```

- 版本号里带 hash 而不是只存库：**collection 名要能自解释**。在 Qdrant 控制台里
  看到 `ai4s_papers__idx-1.0.0-555810c4` 就知道"第 1 代索引管线、第 555810c4 套参数"，
  不用回查数据库。反过来叫 `ai4s_papers_v2` 的话，半年后没人说得清 v2 是什么。
- 分隔符用双下划线：版本号里已经有短横（`idx-1.0.0-…`），再拿短横当分隔符分不开。

### 2.4 存量数据：不搬家，也不伪造签名

`ai4s_papers` 里已有的 279 个点，是版本化之前写进去的。**它用了哪套参数已经不可考**。

两个选择：

1. 按当前配置补一个签名，让它"看起来像用今天的参数建的"；
2. 明确登记成 `origin='legacy'`、签名为空。

选 2。选 1 的后果是：下一次真的重建会算出一个**相同**的版本号，
于是新点被写进旧 collection 覆盖旧点——两份数据混在一起，且回滚点没了。
留空签名反而是准确的：它明确说"这一版不知道是怎么来的，别拿它跟别人比"。

于是启动时（`ensure_registry`）：

```
index_versions 为空?
├─ 基础 collection 有点 → 登记 idx-legacy（origin=legacy, 签名空, status=active）
└─ 没点（全新部署）    → 登记当前签名版本（origin=built, status=active）
再补一条 global 路由指向它
```

`idx-legacy` 是唯一一个 collection 名不按规则走的版本——它的数据物理上就在基础名里。

### 2.5 三张表

| 表 | 一行代表 | 关键列 |
| --- | --- | --- |
| `index_versions` | 一个可服务的索引版本 | `pipeline_version` / `collection` / `signature` / `status` / `origin` / `points` |
| `index_builds` | 一次重建（可续跑） | `cursor_version` + `cursor_offset`（断点）/ `status` / `elapsed_s` / `peak_rss_mb` / `cpu_s` |
| `index_routing` | 一条切流规则 | `scope`（global/project）/ `pipeline_version` / `stable_version` / `percent` |

`status` 的取值有意保持少：`building → ready → active → retired`，
失败是 `failed`。灰度中的"目标版本"是 `ready`（能服务），
"稳定版"是 `active`——**同时存在两个 active 是错的**，会让人读不出谁是基线。

## 3. 重建任务（交付物 2）

### 3.1 为什么重建只要几分钟

chunk 的**文本**在关系库（`chunks.text`），向量只是它的一个派生视图。
换模型/换截断长度只需要把同一批文本重新编码——不需要重新下载 PDF、不需要重解析、
不需要再调一次 LLM 抽章节树。

这就是"换切分策略"和"换 embedding 模型"的分界线：前者改文本（要重解析），
后者只改向量（本文这条路径）。

### 3.2 断点是 (version_id, offset)，不是"已完成多少条"

```sql
cursor_version TEXT,      -- 处理到哪个 paper_version
cursor_offset  INTEGER,   -- 该版本内已提交的 chunk 偏移
```

为什么不用累计量：`done_chunks=128` 推不出"下一批该读哪儿"——不知道这 128 条
分布在几个版本里、每个版本剩多少。崩溃后重跑必须能从一行精确接上。

每批的顺序是 **先 upsert 向量、再落游标**：

```
读一批 chunk → 编码 → upsert 到目标 collection → 更新 cursor → 下一批
```

中断落在中间（向量写完、游标没落）时，重跑会重做那一批。
点 ID 由 `(arxiv_id, version, kind, chunk_index)` 派生，重写是**幂等覆盖**，
所以不会产生重复点，也不会漏。

### 3.3 可中断 / 可续跑：实测

取消**不是立刻杀线程**，而是在批边界停。理由：正在编码的那一批已经写了一半点，
强行打断会留下"写了一半的批次"而游标还停在这批之前；如果这时它恰好被切流，
就会漏召回。让它在批与批之间停，任何时刻 collection 都是
"游标之前全有、之后全无"——一个**一致的半成品**。

实测（279 段 / 5 篇 / batch 64）：

```
跑 1 批后（模拟进程被杀）: running  done=40  cursor=ver_c692149a6aa34683@40
取消请求时:              cancelling done=0      ← 第一批还在编码，取消要等它落地
最终:                    cancelled done=40 cursor=40
续跑后:                  done      279/279  points=279   ← 没有重复点，耗时 165.8s
```

`done_chunks < total_chunks` 且 `cursor > 0` 就是"中断了但可续"的形态。
取消与放弃是两件事：`run_build` 对 `cancelled` / `failed` 的 build 允许再跑，
只有 `done` 会立刻返回——把取消做成不可恢复，重来就得从第 0 条开始，
正好抵消了重建最大的好处。

### 3.4 两个"看起来能跑通但结果不对"的坑

| 坑 | 症状 | 修法 |
| --- | --- | --- |
| 点 ID 用"已处理条数"当偏移 | `chunk_index` 有空洞时（重试过的文档）点 ID 与 SQLite 对不上，溯源全部查不到 | 用 `rows[0].chunk_index` 当偏移，它与解析时同一套 |
| `paragraph` 列不存在 | 重建后"第 3 页第 2 段"全部变成第 0 段（页码还在，段号没了） | 按"同页内出现顺序"重推一遍（`_paragraph_ordinals`） |

另外 DB 的 `chunk_type`（text/table/figure/…）与 payload 的 `kind`（paragraph/table/…）
是双射但不同名，重建时要显式映射。漏了这一步，`figure` 片段会退化成 `paragraph`——
症状是"表格未识别"提示在重建后全部消失，且没有任何报错。

### 3.5 重建期间查询不受影响

因为写入的是**新建的** collection，查询仍然读旧的那个。两者互不相干，
切流之前新版本对线上完全不可见。

实测（重建进行到 91/279 时发起两次问答）：

| 时间点 | 问题 | 耗时 | 读的版本 |
| --- | --- | --- | --- |
| 重建中 | β2 设为多少 | 3.64s | `idx-legacy` |
| 重建中 | ViT 在 ImageNet 上的准确率 | 2.24s | `idx-legacy` |

没有失败、没有降级、答案与重建前一致。**但要说清一件事**：不中断 ≠ 零影响。
同机 16 核上重建把 CPU 占满（`cpu_s=1583s / 199.5s ≈ 7.9 核`），
期间问答会从 ~3s 涨到 ~4.5s。这是单机部署的物理限制，缓解手段是
调小 `index_batch_size`、给 worker 限核，或者干脆在另一台机器上重建。

## 4. 灰度与回滚开关（交付物 3）

### 4.1 四层优先级

```
显式指定 index_version  →  项目规则  →  比例灰度  →  默认版本
```

顺序的理由：显式是"我在排查/做 A/B"，压过一切；项目规则是"这个课题已经验过了"，
比抽样硬；比例是最后的推广手段。

| 规则 | 存在哪 | 典型用途 |
| --- | --- | --- |
| 显式 | 请求参数 `index_version`（问答接口已支持） | 同题 A/B、排障时钉死一版 |
| 项目 | `index_routing` 里 `scope='project'` 的行 | 答辩用的那个课题先切、其余不动 |
| 比例 | `scope='global'` 行 + `percent` | 30% 流量走新版 |
| 默认 | 上面都不命中时 | 全量那一版 |

### 4.2 分桶用 hash，不用随机

```python
def _bucket(key: str) -> int:
    return int(hashlib.sha1(key.encode()).hexdigest()[:8], 16) % 100
```

同一把 key 永远落同一个桶。为什么不用随机：**灰度要能解释**。用户问
"为什么我这边是新版、同事那边是旧版"，答案是"你的课题在 67 号桶，灰度线是 40"；
随机分桶只能回答"运气"。

代价是"同一课题反复问也只落一侧"，所以同题 A/B 要靠 `index_version` 显式指定，
不能指望灰度自己翻面。

实测（percent=40）：

| key | bucket | 命中 |
| --- | --- | --- |
| `proj_dce7e9f24c3648bf` | 67 | 稳定版 |
| `proj_graph_empty` | 94 | 稳定版 |
| `p3` | 9 | 新版 |

### 4.3 写路径不跟灰度

`write_version()` 在灰度期间返回**稳定版**，不是灰度目标版。

如果新入库的论文按比例写进新版、其余写进旧版，两个索引的**语料**就不一样了，
于是"A/B 出来的差异"里混进了"旧版缺 12 篇论文"这个变量——这是最容易做错、
也最难在结果里发现的一处。

### 4.4 回滚 = 改一行

```bash
POST /api/v1/index/rollback
→ {"pipeline_version": "idx-legacy", "percent": 0, "stable_version": null, "note": "回滚"}
```

**不碰数据**：旧 collection 一直在，回滚只是把 global 行的 `pipeline_version`
改回去，毫秒级。这是"旧版本保留"的真正价值——不是为了留个备份，
而是为了让回滚不需要等任何重建。

灰度进行中时，`rollback` 默认撤掉灰度（回到 `stable_version`）；
灰度已撤掉时，回到"除当前版本外最近一个 active/ready 的版本"。

### 4.5 trace 里的版本信息

每次检索的 trace 多了一个 `index` 块（在 `/qa/ask` 的 `routing.index`，
以及 provenance 落库的 `routing` 里）：

```json
"index": {
  "pipeline_version": "idx-1.0.0-555810c4",
  "collection": "ai4s_papers__idx-1.0.0-555810c4",
  "rule": "percent",
  "detail": "灰度 40%：proj_graph_empty 落在 94 号桶，走稳定版",
  "percent": 40, "bucket": 94, "stable_version": "idx-legacy",
  "origin": "built", "status": "active",
  "signature": {"schema": 1, "splitter": "structured-fragments/v1",
                "dense_model": "intfloat/multilingual-e5-large",
                "sparse_model": "Qdrant/bm25", "embed_max_chars": 1500},
  "candidates": ["idx-1.0.0-555810c4", "idx-legacy"],
  "fallback": null
}
```

为什么带 `rule` 而不只带版本号："为什么这次读的是旧版"是一个会被反复问到的问题。
只有版本号时，答案是"去看数据库里那三行规则"；带上规则之后，界面一行就能说清
"课题 A 单独钉了旧版" / "灰度 40%，本课题在 94 号桶"。

### 4.6 指向不存在的 collection 时不切、但要说出来

路由配置指向一个没建好的索引（人工改错了、或者 collection 被删了）时，
`use_collection` 返回 False，检索留在原地，并把事实写进 trace：

```json
"fallback": {"from": "idx-2.0.0-…", "collection": "…", "reason": "collection_missing",
             "to": "idx-1.0.0-555810c4"}
```

不静默回退：界面/日志里必须能看出"这次本该走新版但没走成"，
否则"灰度生效了没有"永远查不清。用户的问答也不会因为运维动作而 500。

## 5. 一次重建的耗时与资源（交付物 4）

环境：单机 16 核 / 容器内 `embed_threads=8` / `batch_size=64`。
语料：5 篇论文、279 段（table 80 / figure 69 / reference 66 / paragraph 63 / chapter 1）。

| 指标 | 冷启（新 worker 进程） | 暖启（模型已加载） |
| --- | --- | --- |
| 片段数 | 279 | 279 |
| 耗时 | **199.5s** | **164.9s** |
| 吞吐 | 1.40 段/s（715s / 千段） | 1.69 段/s（591s / 千段） |
| 峰值 RSS | **5232.7 MB** | 5292.1 MB |
| CPU 时间 | **1583.3s** ≈ 7.9 核 × 199.5s | 1326.0s ≈ 8.0 核 × 164.9s |
| 批次 | 64 条/批，按版本切分、不跨版本拼批（第一个版本只有 40 条，所以首批 40） | 同左 |
| 写入点数 | 279（= chunk 数，无重复） | 279 |

冷启比暖启多出的 ~35s 就是 e5-large 的加载时间（读盘 + 建 ONNX 会话）。
这个差值是真实的运维成本：**每次重建的第一个批次都要为它买单**，
所以重建任务不该每批换个进程（worker 的 `max_tasks_per_child=1` 是给长文档解析定的，
重建走同一个队列时会继承这个行为——这也是为什么单独设一个任务名，方便在日志里认出来）。

进度采样（同一批数据）：

| 已完成 | 耗时 | 瞬时吞吐 |
| --- | --- | --- |
| 40 | 27.8s | 1.44 段/s |
| 91 | 66.9s | 1.36 段/s |
| 155 | 113.9s | 1.36 段/s |
| 219 | 156.3s | 1.40 段/s |
| 279 | 199.5s | 1.40 段/s |

吞吐从第一批到最后一批准平——**没有随批次衰减**，说明分批的内存释放是有效的
（跨文档的台阶式上涨是另一回事，见下）。

### 换算到真实规模

| 库规模 | 预估耗时 | 预估峰值内存 |
| --- | --- | --- |
| 本语料 279 段 | 3.3 分钟 | 5.2 GB |
| 1 万段（约 200 篇） | ~2 小时 | 5.2 GB（与规模无关，与 batch 有关） |
| 50 万段 | ~100 小时（单进程） | 5.2 GB |

50 万段这个量级必须并行：把 `(version_id)` 分片给 N 个进程各自写自己的 offset 区间。
本任务没有做并行重建，因为当前语料不需要——但断点粒度已经是 `(version, offset)`，
天然可以按 version 分片；这一点写在这里是为了说明"可续跑"不只是容错，也是并行的前提。

### 内存为什么是 5.2GB 而不是 2.9GB

`multilingual-e5-large` 常驻约 2.6GB（见 `limits.py` 的注释）。重建把峰值推到 5.2GB，
多出来的部分主要是 ONNX arena 与 tokenizer 的批次缓冲：**只增不退**。
这也是 worker 配 `worker_max_tasks_per_child=1` 的原因——同一进程连做两个大任务，
第二个会跑在更高的基线上。

`peak_rss_mb` 记的是 `VmHWM`（峰值），不是"跑完时占用多少"：
峰值出现在某一次最大批次的编码中间，事后回读早就掉下来了。

## 6. 校验

```bash
# 离线：签名/命名、切流四层规则、断点字段、点 ID 一致性
MSYS_NO_PATHCONV=1 docker exec ai4s-api python /app/eval/index_version/check_index_version.py

# 加在线：trace 能否回答"读的是哪一版、为什么"
MSYS_NO_PATHCONV=1 docker exec ai4s-api python /app/eval/index_version/check_index_version.py \
    --live --base http://127.0.0.1:8000

# 真跑一次"中断 → 取消 → 续跑"（约 4 分钟，会写向量）
MSYS_NO_PATHCONV=1 docker exec ai4s-api python /app/eval/index_version/check_index_version.py --rebuild
```

四段共 33 例（加 `--rebuild` 为 38 例），输出 `ALL PASS`。其中几条值得单独说：

- `写路径不跟灰度` —— 灰度 30% 时 `write_version()` 仍返回稳定版；
- `分桶是确定的` —— 同一个 key 连续两次 `_bucket` 相同，且 `resolve` 给出同一个 `bucket`；
- `对已完成的 build 再调一次 → 立刻返回` —— 同一 `build_id` 重复投递是安全的（Celery acks_late 会重投）；
- `点 ID 与解析管线同一套` —— 直接比对 `pipeline._point_id` 与 `md5("frag::…")`；
- `未知版本 → 400` —— 拼错的版本号是调用方的错，不该表现为 500。

## 7. 踩坑记录

| 坑 | 现象 | 修法 |
| --- | --- | --- |
| `ensure_registry` 只在构造 `VectorStoreService` 时触发 | 部署完先打开面板，显示"零个版本"，看起来像功能没生效 | 面板接口自己先 `ensure_registry` 一次 |
| `run_build` 开头无条件 `status='running'` | **点了取消却跑完了**（取消信号被覆盖），且不报错 | 先判 `cancelling` 直接收尾，再置 running |
| 语料缓存只有一份全局 dict | 切流后 60 秒内，对比/综述用新版片段 + 旧版实体消解，两边对不上且不报错 | `_CORPUS_CACHE` 按 collection 分键 + `invalidate_corpus()` |
| legacy 补一个"当前签名" | 下次重建算出同一个版本号，新点覆盖旧点 | legacy 签名留空，`origin='legacy'` |
| 删掉 `import json` 后 `fingerprint` 还在用 | `/index/versions` 500，`NameError: json` | 补回；这类错误只有真调到那条路径才暴露 |
| 点 ID 用"已处理条数"当偏移 | chunk_index 有空洞时点 ID 与 SQLite 分叉，溯源全空 | 用 `rows[0].chunk_index` |
| `chunks` 表无 `paragraph` 列 | 重建后段号全归零 | 按同页出现顺序重推（`_paragraph_ordinals`） |
| 未识别的 `kind` 映射漏了 | `figure` 退化成 `paragraph`，"表格未识别"提示全消失且不报错 | `KIND_FROM_TYPE` 显式双射 |

## 8. 复现

```bash
# 1) 看一眼现状：有哪些版本、当前切到哪
curl -s localhost:8080/api/v1/index/versions | jq '{versions: [.versions[] | {pipeline_version, collection, status, points}], routing}'

# 2) 改配置（比如 .env 里改 EMBED 截断长度）后重建：不填版本号，按当前配置算
curl -s -X POST localhost:8080/api/v1/index/rebuild -H 'Content-Type: application/json' \
  -d '{"note":"换截断长度"}' | jq '.build | {id, target_version, total_chunks}'

# 3) 看进度（可随时中断，游标会留着）
curl -s localhost:8080/api/v1/index/builds/<build_id> | jq '{status: .build.status, done: .build.done_chunks, cursor: .build.cursor_offset, progress}'

# 4) 灰度 30% 到新版（版本号从第 2 步的返回里取）
curl -s -X POST localhost:8080/api/v1/index/routing -H 'Content-Type: application/json' \
  -d '{"pipeline_version":"idx-1.0.0-<新签名>","percent":30}' | jq .routing

# 5) 给某个课题单独钉新版（答辩用的那个）
curl -s -X POST localhost:8080/api/v1/index/routing -H 'Content-Type: application/json' \
  -d '{"pipeline_version":"idx-1.0.0-<新签名>","project_id":"proj_xxx","note":"已验收"}'

# 6) 回滚（毫秒级，不搬数据）
curl -s -X POST localhost:8080/api/v1/index/rollback | jq .routing

# 7) 确认某次问答读的是哪一版
curl -s -X POST localhost:8080/api/v1/qa/ask -H 'Content-Type: application/json' \
  -d '{"question":"β2 设为多少"}' | jq '.routing.index'
```

## 9. 没做的部分

- **并行重建**：当前按 `(version, offset)` 串行推进。分片天然的切点是 version_id，
  但需要先解决"多个 worker 共享 Qdrant 写入带宽"的限流，本语料用不上。
- **元数据 collection 不版本化**：`paper_meta` 里的向量只用于正文去重相似度，
  换模型只影响"判重像不像"，重算成本是每篇一次，跟着 chunk 版本切反而会增加一倍状态。
- **自动清理**：`index_keep_versions=3` 目前只是面板上的提示，不自动删。
  自动删历史版本会把"可回滚"悄悄变成"看情况可回滚"，宁可让人手动点。
