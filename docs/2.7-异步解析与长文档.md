# 2.7 · 异步解析与长文档鲁棒性

> 目标：解析不再在请求内完成，支撑 541 页教材级别的文档。
> 只改上传、任务队列、解析 worker、进度接口与内存配置，不动检索与问答链路。

## 一、改造前的问题

旧链路是「一次请求 → chord 拆 18 个子任务并行解析 → 合并」。它在 30 页论文上没问题，
在 541 页教材上会同时暴露四个问题：

| 问题 | 具体表现 |
|---|---|
| 整本 PDF 进内存 | `storage.get_pdf_bytes()` 拿全文 bytes，18 个子任务各自再下载一遍；页面图 `pages_png` 以列表形式累积 |
| broker 被中间结果撑爆 | chord 每个子任务把该段 `full_text` 与全部页面图塞进返回值，经 Redis 转发，几百 MB 临时键 |
| 进度无主 | 18 个子任务各跑各的，"现在到第几页"没有单一答案 |
| 断点无处安放 | 子任务粒度是页范围，重启后不知道哪些范围已完成，只能全部重跑 |

一句话：**并行拆页把"一本书"变成了 18 个互不知情的碎片，而进度与断点恰恰需要单一事实源。**

## 二、新的链路

```
POST /papers/upload
   ├─ 流式落盘 + 边写边算 sha256（不整份读入内存）
   ├─ file_hash 命中？──是──► 复制已有 chunk/ref/citation，秒级返回（不入队）
   ├─ 否：写 objects + project→paper→version(stage=queued)
   └─ 返回 task_id + progress_url（< 100ms）

worker: ingest_document(version_id)
   ├─ 流式下载到 /app/data/ingest/<version_id>/raw.pdf（复用它续跑，不重复下载）
   ├─ 循环：解析 20 页 → 先写 Qdrant（幂等 upsert）→ 再提交 SQLite 并推进游标
   ├─ structuring：章节树、参考文献、正文引用位置、paper_meta
   └─ stage=indexed，删工作目录
```

### 为什么不再用 chord

进度与断点都需要"单一事实源"。改成单任务顺序批处理后：

- `parse_cursor`（已解析到第几页）与 `index_cursor`（已写入多少个片段）写在版本行上，
  就是断点本身；崩溃后重启读这两个值继续，不需要任何额外状态；
- 每批结束都能更新一次进度，进度条天然平滑；
- broker 里只流动任务参数（一个 version_id），不流动内容。

并行度改由「同时处理几个文档」提供（worker 的 `-c`），而不是「把一本书切开」。

### 顺序为什么是「先向量、后关系库」

每批的两步写入顺序不能颠倒：

1. 先 `upsert_fragment_batch`：点 ID 由 `(arxiv_id, version, kind, 全局序号)` 决定，
   同一批写两次得到同一批 ID，天然幂等；
2. 再提交 SQLite（删本批区间 → 插 chunk → 推进游标）于**同一个事务**。

如果反过来（先提交关系库再写向量），第二步失败后重试会从新游标开始，
那一批的向量就永远丢了 —— 表现为"chunk 表里有、检索搜不到"。
现在的最坏情况只是"向量写了但游标没动"，重试会覆盖同一批点，无害。

## 三、内存上限（全部写在 `services/ingest/limits.py`）

上限不放在配置里，是因为配置项总会被调大"先跑通一次"。代码常量让每次改动都必须过一次 review。

| 常量 | 值 | 作用 |
|---|---|---|
| `MAX_PDF_BYTES` | 512 MiB | 上传即拒收，不把对象存储当无限缓冲 |
| `MAX_PAGES` | 3000 | 挡住"几万页空白"的构造文件（字节小、渲染久） |
| `PAGES_PER_BATCH` | 20 | 单批 = 一次向量化 = 一次提交 = 一次进度落盘 |
| `MAX_FRAGMENTS_PER_BATCH` | 600 | 密集表格页时页数不能代表工作量，片段数才是 |
| `MAX_TEXT_CHARS_PER_PAGE` | 120k | 扫描版 PDF 整页 OCR 成坨时截断 |
| `MAX_REFERENCE_CHARS` | 400k | 唯一跨批累积的大对象（References 在文末） |
| `MAX_HEADINGS` | 5000 | 跨批累积的标题列表 |
| `CITATION_SCAN_CHUNKS` | 2000 | 引用抽取按 chunk 分窗，不整本读 |
| `MAX_EMBED_CHARS` | 1500 | 送进模型的字符上限，见下 |
| `RENDER_DPI` / `RENDER_PAGE_IMAGES` | 110 / True | 页面图供前端溯源高亮 |
| `MAX_VISION_CALLS_PER_DOC` / `LONG_DOC_PAGES` | 40 / 80 | 超过 80 页只保留 caption，关掉 vision（一张图一次多模态调用会跑成几小时） |
| `RSS_SOFT_LIMIT_MB` | 4096 | 进程 RSS 软上限，超限主动失败并留上下文 |
| `MAX_ATTEMPTS` | 3 | 尝试上限，超限置 failed |

### `MAX_EMBED_CHARS` 是怎么来的

实测（16 核 CPU、`intfloat/multilingual-e5-large` fp32）：

```
500  字符 × 20 条 →  6.0s
1500 字符 × 20 条 → 19.2s
2662 字符 × 20 条 → 30.0s
```

耗时与字符数线性相关，说明 fastembed 并不做 512-token 截断；
而 e5-large 的有效上下文就是 512 token（约 1500 字符），超出的部分既不影响向量，
又实打实地烧 CPU。所以入库前先截到 1500 字符：**向量质量与"模型自己截断"完全一致，
耗时按最长正文块算也降一半以上**。注意截断只作用于送进模型的输入，
`chunks.text` 仍存完整原文，溯源与展示不受影响。

### RSS 软上限为什么是 4096

模型基线不是零：540M 参数的 e5-large 常驻后，单个子进程 RSS 就有 ~2.6GB。
所以 4096 - 2600 ≈ **1.4GB 是留给单本文档的预算**，对 20 页一批的流式解析非常宽裕。
这个数字必须和 `celery_app.conf.worker_max_memory_per_child=4_600_000`（KB）配套看：
前者在文档内发现超限，后者在任务结束后回收进程。

## 四、可重入与失败处理

- **重复触发不产生脏数据**：`ingest_document` 幂等。已完成直接返回（`skipped=True`）；
  中断过的从游标继续；同一批重试覆盖同一批 chunk_index 与同一批 Qdrant 点。
- **重试有上限**：`attempt` 写在版本行上，`>= MAX_ATTEMPTS` 置 `failed`，
  `error_message` 与 `error_trace` 保留（前端进度条直接显示）。
- **内存超限不重试**：`IngestMemoryError` 单独一类，重试只会再撞一次，直接终态。
- **模型不可用不硬等**：两层防护。
  1. `_llm_available()`：没配 key 就直接走启发式，不假装能调模型；
  2. `_call_with_deadline()`：即使配了 key，也把章节树/参考文献两次调用放到后台线程里
     并设 `LLM_STRUCTURE_TIMEOUT_S=45s` 死线。之所以不能只靠 `litellm` 的 `timeout` 参数，
     是因为实测把它设成 45 后，dashscope 的 OpenAI 兼容端点那次调用仍然跑了 136s。
     超时就放弃、退到确定性启发式（按字号分层 / 按编号切分），任务照常结束。

### 老数据的 `status` / `stage` 要对齐

`stage` 是这次新加的列，加列时老行统一拿到默认值 `queued`，于是库里出现
`status=indexed` 而 `stage=queued` 的矛盾行——进度接口会把一本早就解析完的论文
报成「排队中」，而且没有任何报错。

`init_db()` 里的 `_backfill_stage()` 每次启动按 `status` 把 `stage` 对齐回来
（幂等，只有真不一致才写）。两条语句都带 `stage` 条件，所以 api 与 worker
同时启动、同时跑这段代码也不会互相踩。

写这段时踩过一个坑：最初只 `except sqlite3.OperationalError: pass`，
结果并发启动撞上 `database is locked` 就被静默吃掉了，迁移看起来"没生效"却毫无线索。
现在只忽略「表还不存在」，lock/busy 一律退避重试 4 次，其余异常照常抛出。

## 五、接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/v1/papers/upload` | 落库 queued 立即返回 `task_id` + `progress_url`；命中 hash 时 `reused=true` |
| GET | `/api/v1/ingest/tasks/{task_id}/progress` | 轮询：阶段、页码、百分比、ETA、片段/文献/引用数 |
| GET | `/api/v1/ingest/tasks/{task_id}/events` | SSE：同一份快照，变化才推，终态自动收尾 |
| GET | `/api/v1/ingest/versions/{version_id}/progress` | 刷新页面后按版本重新挂上进度 |
| POST | `/api/v1/ingest/versions/{version_id}/resume` | 从断点续跑（保留 `parse_cursor`） |

进度响应示例：

```json
{
  "stage": "parsing", "stage_label": "解析正文", "status": "pending",
  "page": 240, "total_pages": 541, "pct": 44,
  "chunks": 240, "refs": 0, "citations": 0,
  "attempt": 1, "attempt_limit": 3,
  "elapsed_ms": 407687, "eta_ms": 511000,
  "done": false
}
```

`status` 与 `stage` 是两个维度：`status` 是结论（pending/indexed/failed/duplicate），
`stage` 是过程（queued/downloading/parsing/structuring/indexed/reused/failed）。
`status=pending + stage=parsing` 就表示"还在跑，已到第 240 页"。

## 六、541 页实测

测试对象：`scripts/gen_large_pdf.py` 生成的 541 页教材样张
（0.96MB，1,126,571 字符，平均 2082 字符/页，60 条参考文献，正文含 `[N]` 引用标记）。
硬件：16 核 CPU、无 GPU，worker `-c 1`，embedding 为 fp32 `multilingual-e5-large`。
复现命令：

```bash
# 1. 生成样张（确定性内容，字节稳定）
docker exec ai4s-api python /app/scripts/gen_large_pdf.py --out /app/data/bench/textbook_541.pdf
# 2. 采样 worker 容器内存（另开一个终端）
./backend/scripts/bench_rss_sampler.sh ai4s-worker 2 /tmp/rss.log
# 3. 上传 + 轮询 + 二次上传
docker exec ai4s-api python /app/scripts/bench_ingest.py \
    --file /app/data/bench/textbook_541.pdf --interval 3 \
    --json-out /app/data/bench/bench_541.json
```

| 指标 | 数值 |
|---|---|
| 上传响应（POST → 200，含 sha256 与判重） | **68 ms** |
| 首屏可用（进度条出现真实页码 0/541） | **3.0 s**（采样间隔 3s，实际 ≤3s） |
| 首批 chunk 可检索（前 20 页入库） | **21.1 s** |
| 解析 541 页（28 批，每批 20 页） | **448 s** |
| 汇总（章节树 31.5s + 文献 45.0s 被死线截断） | **76.5 s** |
| 端到端（POST → indexed） | **526 s ≈ 8 分 46 秒** |
| 峰值容器内存 | **3.43 GiB**（启动基线 1.19 GiB，其中约 2GB 是 embedding 模型一次性加载） |
| 解析期间进程 RSS | 2.92 ~ 3.26 GB，28 批内无单调增长（详见下节） |
| 二次上传（同文件） | **28 ~ 37 ms**，`reused=true`，不入队、不重算向量 |
| 解析结果 | 541 chunk / 60 refs / 12 citations，异常 0 |

耗时构成（按批日志的 `parse` / `index` / `commit` 拆分）：

```
batch pages 0-19   20.4s  parse=1.6s index=18.7s commit=0.0s
batch pages 300-319 16.1s  parse=1.2s index=14.9s commit=0.0s
batch pages 520-539 15.6s  parse=1.4s index=14.1s commit=0.0s
batch pages 540-540  1.9s  parse=0.2s index=1.6s commit=0.0s
```

**解析本身只占 8%，剩下 92% 是 embedding**。20 个片段（每片段约 2000 字符）在
fp32 e5-large 上要 14~19 秒，这是纯 CPU 推理的硬成本，也是端到端时间的主要来源。
要再快只有三条路：换 GPU、换小模型、或降低 chunk 数量（会影响检索粒度）。
当前实现已经把能省的都省了（`MAX_EMBED_CHARS` 截断、单批单次 upsert、批量提交）。

### 内存为什么不算"持续增长"

`[ingest]` 日志每批打一次进程 RSS，同条件下的一轮完整运行采样点：

```
批 0-19    3156 MB      批 240-259  3161 MB
批 20-39   3160 MB      批 440-459  3227 MB
批 100-119 3156 MB      批 480-499  3219 MB
批 200-219 3161 MB      批 500-519  3209 MB
                        批 520-540  3261 MB
```

28 批、541 页，RSS 始终在 3.15~3.26 GB 之间小幅波动（±3%），没有随页数单调增长的迹象。
结构上的原因有三条：

1. 页面图渲染一页、上传一页、立即释放，不累计 `pages_png` 列表；
2. 每批结束显式清空 `fragments` / `page_texts`，不让 GC 决定什么时候回收；
3. 参考文献不再在内存里跨批累积，而是以 `reference` 片段落库、汇总时按需读回。

两层护栏兜底：`RSS_SOFT_LIMIT_MB` 在文档内发现问题并留上下文，
`worker_max_tasks_per_child` / `worker_max_memory_per_child` 在任务结束后回收子进程。

## 七、自检

| 自检项 | 结果 |
|---|---|
| 上传 541 页 PDF，进程内存不持续增长 | 通过，见上表（RSS 3156→3261MB，28 批无单调增长） |
| 中断后重启任务能接着跑 | 通过，200 页样张在 80/200 页处被 `docker restart` 打断，从第 80 页续跑至 `indexed`，无重复 chunk |
| 同一文件二次上传秒级返回 | 通过，28 ms 且 `reused=true`（未入队、未重算向量） |

### 中断续跑怎么验证

`scripts/verify_resume.py` 的流程：上传一份 200 页文档 → 跑到约 1/3 →
`docker restart ai4s-worker` → 观察进度从断点继续（不是从 0 开始）→
跑完后核对 chunk 数与 `parse_cursor`，确认既没有重跑也没有重复行。

实测输出（`bash backend/scripts/verify_resume.sh 200`）：

```
version_id=ver_bde4bcabec264091
progress_page=80/200 stage=parsing
>>> 重启 worker 制造中断（任务应被自动重新投递并续跑）
final stage=indexed status=indexed page=200/200 chunks=200 refs=60 cites=9
db: {'chunk_rows': 200, 'distinct_chunk_index': 200,
     'min_chunk_index': 0, 'max_chunk_index': 199,
     'parse_cursor': 200, 'page_count': 200, 'index_cursor': 200}
PASS
```

（脚本还会打印 `work_dirs=`，统计 `/app/data/ingest` 下剩几个目录。这一轮是 1，
但不是本次任务的——是一个更早被清理掉的版本留下的孤儿目录，正好促成了下面那节
`sweep_work_dirs()` 的加入。加上清扫后该项为 0。）

`chunk_rows == distinct_chunk_index == 200` 是关键：如果被打断的那一批被重复写入，
这两个数会不相等。`min=0 / max=199` 说明 0..199 恰好铺满，没有空洞。

### worker 被 SIGKILL 时消息会丢，所以要有巡检

`task_acks_late=True` 只能保证**进程优雅退出**时重新投递。`docker restart` 等 10 秒后
会直接 SIGKILL，此时 Redis broker 里已投递但未 ack 的消息就没了——数据库里留下一条
`status=pending / stage=parsing` 的行，永远不动。

这一点是实测撞出来的（验证脚本第一次运行时正好把在跑的任务打死了）。补法：
`PaperVersionRepository.list_stuck()` 找出 `status=pending AND stage IN (downloading/parsing/structuring)
AND started_at <= now-90s` 的版本，`recover_stuck` 任务重新投递，靠 `parse_cursor` 从断点续跑。
触发点两个：worker 启动时立刻跑一次（救上次崩溃留下的孤儿），beat 每 10 分钟跑一次
（救 broker 重启丢消息但 worker 还活着的情况）。实测日志：

```
[ingest] 巡检接管孤儿版本 ver_bde4bcabec264091：从第 80 页续跑
```

同一趟巡检顺手清工作目录：被强杀的版本会留下 `raw.pdf`（几十 MB 一个），
`sweep_work_dirs()` 只删「mtime 超过 1 小时」且「版本行已不存在或已是终态 indexed」
的目录，正在跨批解析的目录不会被误删。

## 八、已知偏差

1. `worker -c 1`：一次只解析一本书。吞吐靠加 worker 副本，而不是靠把一本书切开——
   后者会让进度与断点失去单一事实源。
2. 页面图（110 DPI）占 MinIO 空间约 0.35MB/页，541 页约 190MB。
   若不需要溯源高亮，把 `RENDER_PAGE_IMAGES` 置 False 可全部省掉。
3. `citations.bbox` 仍是段落级（PDF 解析只给到 block 坐标），句子级需要重跑 layout。
4. 复用只在 `(file_hash, arxiv_id, version)` 三者都相同时生效。
   文件相同但版本号不同（v1 vs v7 同字节）会退回重新解析——
   因为 Qdrant 点 ID 里带 version，直接抄行会让向量与点 ID 对不上。
5. worker 重启依赖 `task_acks_late=True` + `task_reject_on_worker_lost=True` 才能自动重新投递；
   这两个参数在 `celery_app.conf` 里已开，别关。
