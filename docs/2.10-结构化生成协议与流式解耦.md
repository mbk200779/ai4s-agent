# 06 · 结构化生成协议与流式解耦

> 一句话：**正文流式上屏，角标最后回填**。
> 把"自然语言"和"证据"拆成两条通道，既拿到打字机体验，又不牺牲引用的可校验性。

## 1. 问题：流式与引用天然冲突

引用要校验，校验要等整句写完；流式要的是"边写边发"。两者在时间上是矛盾的：

- **先发字、后校验**：用户看到的 `[引#3]` 是模型随口说的编号，可能指向完全无关的片段，
  点下去就是死链——而且是**已经渲染在屏幕上、无法收回**的死链。
- **先校验、后发字**：等 3 秒拿到完整答案再一次性返回，流式就只剩传输格式上的意义。

所以协议必须把答案拆成两半，各自用合适的时机发送：

```
正文（自然语言）  ──token 事件──→  立刻上屏，一个角标都不带
证据（句 → 片段） ──claim 事件──→  校验完成后回填到对应句末
```

这样"没校验过的角标"在物理上不可能出现在流里——不是靠前端自觉，而是服务端根本不发。

## 2. 事件类型定义（交付物 1）

### 2.1 信封：每个事件都必须有的四个字段

| 字段 | 含义 | 为什么要它 |
| --- | --- | --- |
| `trace_id` | 一次对话的唯一 id，形如 `tr_7d4a9cb8e66b49d5` | 答辩回放、线上排障的唯一锚点；provenance 记录里也存了一份 |
| `seq` | 从 1 连续递增 | 缺号就是丢帧（反代缓冲、连接中断），前端据此判断"流是否完整" |
| `ts` | 毫秒时间戳 | 与其它系统日志对时 |
| `elapsed_ms` | 相对本次请求起点的毫秒数 | 直接看出慢在哪一段，不需要自己减时间 |

### 2.2 四类业务事件

| 事件 | 何时发 | 关键字段 | 前端责任 |
| --- | --- | --- | --- |
| `stage` | 每个阶段的 start / done | `stage`（understand/retrieve/rerank/generate）、`phase`、`ms`、`detail` | 推进度条；`done` 时显示真实耗时 |
| `retrieval` | 检索+精排结束后 | `chunks[]`（序号/论文/页/类型/分数/是否带锚点/预览）、`top_raw_score`、`reject_threshold` | 亮出"命中了什么"，让用户能提前点开原文 |
| `token` | 模型每吐一块 | `text`（增量） | 只做字符串拼接，**不插角标** |
| `claim` | 生成结束后逐句 | `claim_id`、`span`、`status`、`reason`、`citations[]` | 按 span 把句子切开，句末回填角标；unsupported 加虚线 |
| `done` | 全部结束 | `answer`、`answer_annotated`、`claims`、`answer_refs`、`citations`、`anchor_index`、`timings`、`trace_key` | 汇总行、复制带出处全文、回放链接 |
| `error` | 生成中断 | `message` | 保留已生成部分并标错，不静默截断 |

`stage` 的 `detail` 是各阶段自己的账本，前端不解析语义，只做展示：

- understand：`type_label`、`confidence`、`classifier`、`slots`、`search_text`、`translated`
- retrieve：`hits`、`injected`（数值规则注入几条）、`papers`、`probes`
- rerank：`applied`、`degraded`、`reason`、`cache`、`moved`（被移动位置条数）
- generate：`chars`、`raw_chars`、`stripped_markers`（摘掉几个角标）、`ttft_ms`

### 2.3 类型定义（TS 摘要）

完整定义见 `frontend/src/types/stream.ts`，核心几段：

```ts
export interface EventBase {
  trace_id: string;
  seq: number;
  ts: number;
  elapsed_ms: number;
}

export interface ClaimEvent extends EventBase {
  claim_id: string;
  span: [number, number];   // 在正文里的字符区间，角标插在 span[1]
  text: string;
  status: 'supported' | 'unsupported';
  reason: string | null;
  citations: Evidence[];    // 越界/无锚点/低分也在这里，不删
}

export interface Evidence {
  index: number;            // [引#N]
  status: 'supported' | 'unsupported';
  reason: string | null;
  chunk_id: string | null;
  ref_id: string | null;    // 句子级锚点 id（s27 / t3c2）
  precision: string | null; // sentence | cell | block | line | ocr
  page: number;
  text: string | null;      // 被引用的那一句
  rects: number[][] | null; // 页面坐标，可直接画框
  bbox: number[] | null;
  match_score: number | null;
}
```

### 2.4 前端只能遵守的三条

1. `token` 到达时**只拼接字符串**，不解析、不渲染任何形如 `[引#N]` 的东西（流里本来也没有）。
2. 角标只能由 `claim.citations` 生成；`status==='unsupported'` 的角标**不可点击**
   （做成 `cursor-not-allowed` 的灰框，悬停显示原因）。
3. `unsupported` 的 claim **必须留在正文里**，只允许加样式（虚线下划线 + 「证据不足」标签），
   不允许过滤掉——过滤会让"这句话其实没有证据"这个事实消失。

## 3. 服务端分段推送（交付物 2）

### 3.1 为什么是"后台线程 + 队列"，不是 async generator

检索、精排全是同步阻塞调用（ONNX / Qdrant / HTTP）。如果在同一个生成器里"先算完再 yield"，
前端拿到的仍然是"卡 2 秒 → 一次性刷出全部 stage"——只是换了传输格式。

```
POST /qa/stream
  └─ gen()  ← Starlette 放线程池里迭代，不占事件循环
       └─ queue.get(timeout=heartbeat)  ← 等事件
              ↑
   work()  后台线程：analyze → route(on_stage 回调) → chat_stream → claims → done
```

每到一个**真实边界**就 `emit()` 一次，消费端边收边发。心跳用 `: ping` 注释行，
不进事件序列也不进归档——它只负责让反代/隧道相信连接还活着（`STREAM_HEARTBEAT_S=8`）。

### 3.2 阶段边界从哪来：`route(on_stage=...)`

`已检索` 与 `已精排` 的边界在 `RAGRetriever.route()` 内部（策略召回 → 规则注入 → 重排），
外面只看到一次函数调用的总耗时。所以给 `route()` 加了个可选回调：

```python
fire("retrieve", "start", ...)   # 派发策略前
fire("retrieve", "done", ms=strategy.latency_ms, hits=..., injected=...)
fire("rerank", "start", mode=..., candidates=...)
fire("rerank", "done", applied=..., degraded=..., cache=..., ms=outcome.latency_ms)
```

回调默认 `None`，评测脚本与旧调用方零影响；回调自己抛异常也被吞掉——
进度条坏了不能把检索带崩。

### 3.3 摘角标：`CitationFilter`

约束是"token 流中不得出现未经校验的角标"，而校验必然发生在生成结束之后。
所以流里出现的 `[引#N]` 注定是未校验的，只能摘掉并记录**位置**，等 claim 事件回填。

难点是标记会被切块（`...结论[引` + `#3]。`）。过滤器因此要缓冲"看起来像标记前缀"的尾巴：

```python
_PREFIX_RE = re.compile(r"^\[(?:引(?:#\d*)?)?$")   # "[", "[引", "[引#12"（含未闭合）
```

普通方括号（`[1]`、`[a]`）不匹配这个形状，照常吐出去，正文不受影响。
`flush()` 时若残留仍是标记前缀（答案在 `[引#3` 处断流），直接丢弃——
吐出去等于在流末尾留个半截角标，比少几个字更糟。

### 3.4 逐句校验：`build_answer`

拿到"清洗后的正文 + 角标位置"后：

1. 用锚点模块的切句器切 claim（和 05 的锚点共用一套规则，句子边界不会打架）；
2. 每个角标按"最后一个起点 ≤ 角标位置"的句子归属；
3. 每条证据做 `anchor_select.select(claim, chunk_text, anchor_doc)`，拿到 `ref_id + rects + match_score`；
4. `match_score >= CLAIM_MIN_EVIDENCE`（默认 0.15）才算 `supported`；
5. 没有角标的句子、编号越界、匹配过低、片段无锚点——**全部保留成 `unsupported` 并附 `reason`**。

### 3.5 三段分支

| 情况 | 事件序列 |
| --- | --- |
| 正常 | stage×8 → retrieval → token×N → claim×M → done |
| 拒答（检索为空 / 融合分低于阈值） | stage(understand/retrieve/rerank) → retrieval(count=0 或有但低分) → done(rejected=true, claims=[]) |
| 闲聊 | stage(understand) → stage(generate) → token×N → done(claims=[]) |

拒答不发 token：拒答文本不是模型生成的，硬塞进正文会让人以为"模型这么答的"。

### 3.6 归档：让链路可回放

结束时把整条事件日志（含 done）写成 JSONL，落到
`qa/stream/<date>/<trace_id>.jsonl`，`done.trace_key` 指回它；
另外 `GET /api/v1/qa/stream/{trace_id}` 原样读回。

> provenance 记录的是**结果**，事件日志记录的是**过程**（阶段耗时、精排是否降级、
> 摘掉几个角标、哪句判了 unsupported）。答辩要回放的是过程。

### 3.7 实测时序（`tr_7d4a9cb8e66b49d5`，热态）

| 阶段 | 耗时 | 说明 |
| --- | --- | --- |
| 首字节 | 32.5 ms | 第一个 stage 事件到达 |
| 理解 | 562.3 ms | 规则分类 + 中文问句翻译成英文（一次 LLM 调用） |
| 检索 | 261.1 ms | 点查策略召回 21 条候选，规则召回注入 1 条 |
| 精排 | 642.0 ms | 21 对打分，未降级 |
| 生成 | 792.5 ms | 首 token 401.5 ms |
| 合计 | 2288.4 ms | 17 个事件 |

对比一次性 `/qa/ask` 的同题：用户感知延迟从 **~2.3 s 的空白**变成 **0.4 s 见字**。

## 4. 前端按事件渲染（交付物 3）

### 4.1 订阅：手写 SSE 分帧

`fetch` 给的是任意切分的字节流，一个 TCP 块里可能有"三条半事件"。
按 `\n\n` 切、余下的留在缓冲里，是唯一稳的做法；直接对每个 chunk 做 `JSON.parse`
会在"事件被切开"时随机炸。

三处必要防御：

- **单帧坏掉**：`try/catch` 丢掉这一帧，不影响后续；
- **流正常闭合但没有 done**：显式标错「事件流提前结束（未收到 done）」——
  否则界面会停在一段"看起来答完了"的半截文字上；
- **组件卸载**：`AbortController.abort()`，别让用户切走之后还在烧 token。

### 4.2 四块 UI 与事件的对应

| UI | 数据来源 | 缺数据时 |
| --- | --- | --- |
| 阶段条（理解/检索/精排/生成） | `stage` 事件 | 整块不渲染 |
| 命中片段列表 | `retrieval.chunks` | 整块不渲染 |
| 正文 + 角标 | `token` 拼接 + `claim.span` | 正文照常显示，无角标 |
| 汇总行（主张/有据/证据不足/耗时/trace） | `done` | 整块不渲染 |
| 事件流调试面板 | 全部原始事件 | 折叠 |

### 4.3 角标回填是结构上成立的，不是时序运气

```tsx
const ordered = [...claims].sort((a, b) => a.span[0] - b.span[0]);
// 逐句切分正文，在 span[1] 处插入角标
// span 越界（正文被截断过）就跳过这条，绝不把角标插到字中间
if (s < cursor || e > text.length) return;
```

角标的数据源只有 `claims`，而 `claims` 只可能来自 `claim` 事件。
所以"claim 未到 → 没有角标"是**类型层面**成立的：不存在一条能绕过它渲染角标的路径。

## 6. 踩过的坑

1. **点 ID 不是 chunk ID（最贵的一坑）**
   Qdrant 返回的 `hit.id` 是 uuid5 点 ID，而锚点、引用、provenance 全挂在 `chunks.id`（`chk_xxx`）上。
   检索层只拿得到前者，于是 `anchors_map()` 按检索结果去查**永远是空**——
   症状是"每篇论文都没锚点"，不报错、不告警，只表现为"高亮永远只能到页"。
   修复：`ChunkRepository.resolve_point_ids()` 做批量映射 + 进程级缓存，
   `retrieval_service` 与 `strategies.load_corpus` 两处都换 ID。

2. **角标位置差一个空格，全部 claim 变 unsupported**
   切句器会把句末空白裁掉（`span.end` 落在句号后），而标记位置通常在空白之后
   （`... 0.98 [引#1]`）。用"闭区间包含"判归属会一条都挂不上，
   表现为"每个 claim 都写着'这句话没有引用标注'"，而 `stripped_markers` 明明是 1。
   改成"最后一个起点 ≤ 位置"，并在注释里写清为什么。

3. **精排 0.3ms 不是 bug**
   同一问题二次请求会命中精排缓存（`cache: hit`），`ms` 是真的。
   前端显示 `<1ms` 而不是 `0ms`，避免看起来像没跑。

4. **Next.js 的 rewrites 有 30s 硬超时**
   本地开发用 `localhost:3000` 打 `/api/v1/qa/stream` 会经由 Next 代理；
   长答案可能被掐。演示与抓日志一律走网关 `localhost:8080`（nginx 直连 FastAPI，
   `proxy_buffering off`、`proxy_read_timeout 300s`）。

5. **反代会把静默连接掐掉**
   检索+精排期间可能十几秒没有事件。8s 一次 `: ping` 注释行保活；
   前端顺手把 ping 计数显示在事件面板里——它归零就说明中间有东西在攒包。

6. **归档里不能混心跳**
   心跳只保活，不进日志：否则回放时会出现一堆无意义的空事件。

7. **`done` 的 `trace_key` 是自引用**
   日志要先落盘才能拿到 key，所以归档里的 done 记录没有 `trace_key` 字段（其余字段完整）；
   实时推送的那条才带。这不影响回放（回放靠 trace_id 而非 key）。

8. **向量库里有孤儿点**
   重新入库同一篇论文会生成新的点 ID，旧点没有删掉，
   于是检索偶尔命中"库里已经不存在的 chunk"（`has_anchors=false`、`chunk_id` 是裸 uuid）。
   当前用"解析不到就退回页级定位"兜住；根治要在重入库时按 `paper_id+version` 删旧点。

## 7. 验收对照
