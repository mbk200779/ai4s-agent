# 2.25 演示期保活与上台自检

> 场景：网站跑在自己的笔记本上，答辩/评审就在这几天，不打算（也没预算）迁云。
> 目标不是「让它 7×24」，而是「**别在台上掉链子**」。
> 配套：`deploy/demo-keepalive.ps1`（一次性加固）、`deploy/demo-check.sh`（上台前自检）。

---

## 0. 先说清楚做不到的那件事

**关机期间，网页打不开是必然的。** 网站不是一个静态文件，它是这台机器上跑着的 8 个
Docker 容器；隧道那一头连的是这台机器的 IP。关机 = 源站消失，Cloudflare 只能返回 502。
没有任何参数能改变这一点——唯一的解法是换一台不关的机器（见 `deploy/云服务器迁移清单.md`）。

所以本文只解决两件**能**解决的事：

| 要解决 | 手段 |
| --- | --- |
| 机器**自己**睡着/重启，导致演示中途断 | 演示期加固（第 2 节） |
| 已经断了，能不能**自己爬起来** | 开机自启 + `restart: unless-stopped` + 兜底任务（第 3 节） |
| 机器好好的，但**公网**打不开 | 换入口 + 上台前自检（第 4、5 节） |

## 1. 这台机器的现状（2026-11-11 实测）

| 项 | 实测值 | 结论 |
| --- | --- | --- |
| 型号 | LENOVO 21TL，32G 内存，笔记本 | 有电池、有盖子 → 存在睡眠风险 |
| 联网 | WLAN `NFU`，229 Mbps；以太网**未插** | 校园网 + WiFi 双跳，国际链路质量差的主因之一 |
| 连续运行 | `2026-10-29 18:10` 至今 **13 天** | 平时确实不关机，问题是「主动关」和「意外断」 |
| Docker 自启 | `AutoStart = True`，`HKCU\...\Run` 有 Docker Desktop | 登录后自动起，**不用手动操作** |
| 容器重启策略 | 8 个容器全是 `restart: unless-stopped` | 引擎起来后容器自己回来 |
| 电源 | `STANDBYIDLE=0`、`HIBERNATEIDLE=0` | 插电时永不睡眠/休眠，已就绪 |
| 更新活动时间 | 8:00 → 次日 1:00 | 只剩 **1:00–8:00** 这个窗口会静默重启 |
| Docker 内存 | 上限 15.3G，当前占用 **3.62G** | 余量充足（已停用同机 Dify，见第 8 节） |

**结论**：常规开机自恢复这条链路本来就是通的，不需要每次跑 `start-all.sh`。
真正要防的是三件事，按发生概率排序：

1. **公网链路本身不稳**：连续三轮实测分别是 **1/3、2/3、3/3** 通过。
2. **半夜自动重启**：更新窗口 1:00–8:00，早上来发现网页 502。
3. **Qdrant sparse 索引 panic**：11-10 已发生过一次，症状极隐蔽——**问答正常、只有入库全 500**。

## 2. 一次性加固（需要管理员，2 分钟）

```
右键 deploy\演示加固-右键管理员运行.bat → 以管理员身份运行
```

等价的命令行方式：

```powershell
# 管理员 PowerShell
powershell -NoProfile -ExecutionPolicy Bypass -File .\deploy\demo-keepalive.ps1 -Days 7
```

做了四件事，每件都对应上面一个风险：

| 动作 | 为什么这么做 |
| --- | --- |
| 暂停 Windows 更新到 7 天后 | 更新装完会自动重启，且重启后**要求登录才起 Docker**。这是演示前一天最典型的翻车方式。写 6 个注册表值才生效，只写 `PauseUpdatesExpiryTime` 会被系统忽略 |
| 禁用唤醒定时器（`RTCWAKE=0`） | 避免半夜被计划任务唤醒 → 睡回去 → 隧道重连，第二天连接数不足 |
| 关闭网卡省电 | 长时间无流量后网卡进入低功耗，唤醒失败表现为「本地通、公网死」 |
| 插电永不睡眠 + 合盖不睡 | 合上盖子去吃饭/开会是最高频的误动作。Modern Standby 机型部分固件不开放 `LIDACTION`，脚本会如实报「需手动改」而不是假装成功 |

**没有做**：停用 `wuauserv` 服务。它会被 Windows 自己恢复，而且让机器长期不打补丁；
「暂停 7 天」覆盖演示窗口就够了，到期自动恢复。

`-Revert` 可完整撤销。演示结束当天跑一次：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\deploy\demo-keepalive.ps1 -Revert
```

> 执行策略是 `Restricted`，直接双击 `.ps1` 会被拦。所以给了 `.bat` 包装（内部用
> `-ExecutionPolicy Bypass`，只对这一次进程生效，不改系统设置）。
> `.bat` 存为 **GBK** 编码——cmd 按系统代码页 936 解析，UTF-8 中文会乱码。

## 3. 万一还是重启了，它能不能自己起来

能，而且不用你动手：

```
开机 → 你登录 Windows → Docker Desktop 自启（30~60s）
     → 8 个容器按 restart: unless-stopped 自己回来
     → cloudflared 重新注册 4 条连接（约 10s）
     → 全程 1~2 分钟，无需任何命令
```

唯一的例外是「开机了但没人登录」——Docker Desktop 是用户级进程，没登录就不启动。
这在无人值守场景才成立，演示时人就在边上，不构成问题。

想再加一层保险，可以注册登录后自检任务：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\deploy\demo-keepalive.ps1 -InstallBootTask
```

登录 2 分钟后跑一次 `start-all.sh`，容器没起来就拉起，日志写到 `/tmp/ai4s-boot.log`。

## 4. 公网不稳怎么办：准备三个入口

这是**演示当天最可能出问题的一环**，而且改不了——隧道 4 条连接全部注册在
Cloudflare 洛杉矶边缘（`lax01/07/12/13`），家宽到 LAX 这一段实测丢包 75%，
`cloudflared` 没有指定接入区域的参数。能做的只有「换一条路给评委」。

| 优先级 | 入口 | 适用 | 备注 |
| --- | --- | --- | --- |
| 1 | `http://localhost:8080` | 投影/本机演示 | 最快最稳，实测 16ms |
| 2 | `http://10.110.32.40:8080` | 评委手机连同一个 WiFi | 实测 200，不依赖公网 |
| 3 | `https://demo.mabokai.site` | 提前发链接、远程看 | 成功率约 1/3~3/3 波动 |

**演示稿上别只印二维码。** 二维码扫不开比没有二维码更尴尬。建议写
「现场演示：局域网 / 本机」，公网地址作为「回去可以再看」的补充。

如果一定要一个稳定的公网地址，`deploy/cpolar-接入指南.md` 里已经备好了国内隧道方案
（cpolar 免费版，1 Mbps / 24 小时换域名），演示当天开、当场发地址即可，
不经过 Cloudflare 边缘。需要先去 cpolar 注册拿 authtoken。

## 5. 上台前 30 秒自检

```bash
bash deploy/demo-check.sh              # 常规（不调大模型，零成本）
bash deploy/demo-check.sh --with-qa    # 额外跑一次真实问答，确认额度没耗尽
```

`start-all.sh --status` 已改为调用它（同一套判断，不会再出现两套自相矛盾的结论）。

输出末尾直接给结论，三档：

- **可以演示** —— 直接上台
- **可以演示，但有 N 项需要注意** —— 逐条看 `!` 行
- **还有 N 项不通过** —— 逐条看 `·` 行，每项下面都有处置提示

检查项与对应故障：

| 检查项 | 失败含义 | 30 秒处置 |
| --- | --- | --- |
| 容器健康 | 某容器 exited/unhealthy | `docker logs --tail 30 <名字>` |
| 本地 8080 | 网关没起来 | `bash deploy/start-all.sh` |
| Qdrant 可读 | 引擎 panic 或未就绪 | `docker restart ai4s-qdrant`，等 20 秒 |
| 业务集合 0 个点 | 库被清空 | 去论文库重新导入 |
| 队列积压 | worker 卡住 | `docker restart ai4s-worker` |
| D 盘 < 10G | 写满会导致入库失败 | 清理 `docker system prune` |
| 公网 3/3↓ | 隧道/边缘链路问题 | `docker restart ai4s-tunnel`，或换入口 |
| 问答失败 | LLM 额度耗尽 | Dashscope 充值 / 换模型 |

## 7. 为什么不能靠「一直别关机」这件事本身

有人会想：那我保证不关机不就行了。实际上演示期间机器会被这三种力量关掉：

1. **Windows 更新**：装完补丁后强制重启，倒计时可以很短。这是第 2 节第一项要解决的。
2. **合盖**：去开会顺手合上，回来发现睡了。
3. **电池**：拔了电源进电池模式，Modern Standby 下仍在耗电，几小时后关机。

加固把 1、2 摁住了；3 靠「插着电源」这一条物理动作，脚本管不了。
所以上台前还有一条固定动作：**确认电源线插着**（`Get-CimInstance Win32_Battery` 的
`BatteryStatus=2` 表示正在充电，当前为 99%）。

## 8. 与 Dify 共存

这台机器上还装着一整套 Dify（`D:\docker desktop\dify\dify\docker`，12 个容器），
与 AI4S 共用同一个 Docker 引擎和 15.3G 内存上限。**2026-11-11 已停用**，内存占用从
5.4G 降到 **3.62G**（释放约 1.8G）。

```bash
bash deploy/dify-toggle.sh status   # 看状态
bash deploy/dify-toggle.sh stop     # 停掉 + 改为不自启
bash deploy/dify-toggle.sh start    # 恢复原策略并拉起
```

**只 `docker stop` 是不够的。** Dify 的 11 个容器是 `restart: always`，官方语义是
「即使手动停止，daemon 启动时仍会拉起」——电脑重启一次它们就全回来了，等于没停。
所以脚本额外做了 `docker update --restart no`，原始策略备份在
`deploy/dify-restart-policy.bak`，`start` 时按备份逐条还原。

数据安全：`stop` 不删容器也不删卷，Postgres 与 Weaviate 的数据都还在。恢复后
Dify 自带 nginx 会重新占用 **80 端口**（AI4S 用 8080，两者不冲突）。

> 演示期间如果跑 500 页以上的论文入库，embedding 峰值会额外吃 2~3G，与 Dify 叠加
> 有触发 OOM 的可能——这也是停掉它的主要原因。
> **不要用 `docker system prune`** 腾空间：它不会停容器，但会删掉未使用镜像，重建要十几分钟。

## 9. 故障速查（现场 30 秒处置）

| 现象 | 最可能原因 | 一条命令处置 |
|---|---|---|
| 页面能开，但所有操作报 502 | 网关缓存了旧容器 IP（api 重建后） | `docker compose restart gateway`（配置已改为动态解析，正常不该再出现） |
| 全站打不开，公网 502 | 本机没网 / 隧道断开 | `docker compose ps` 看 `ai4s-tunnel`；`docker compose --profile tunnel restart tunnel` |
| 页面白屏、控制台 404 | web 容器未起或构建中断 | `docker compose up -d --build web` |
| 上传后一直「解析中」 | worker 挂了或队列积压 | `docker compose restart worker`；`docker logs ai4s-worker --tail 30` |
| 问答报「Free quota exhausted」 | LLM 额度耗尽 | 换 `LITELLM_MODEL` 到另一个有额度的 provider，或充值 |
| 新论文一律解析失败，问答却正常 | Qdrant 写失败（读不受影响） | `curl -X POST localhost:8000/api/v1/index/rebuild -d '{"target_version":"<当前版本>"}'` |
| 导入报 `TypeError: Chunk.__init__() got an unexpected keyword argument 'anchors'` | worker 镜像比 api 旧：表加了列，代码没跟上 | `docker compose build worker && docker compose up -d worker`；判据见下「镜像是否同源」 |
| 导入报「进程内存 xxxx MB 超过软上限」 | 单篇峰值超过 `RSS_SOFT_LIMIT_MB`（图片多的论文会到 6GB） | `INGEST_RSS_SOFT_LIMIT_MB=7168` 写进 `.env` 后重建 worker；不要靠重启绕过 |
| **库里有 6 篇，答出来却说「3 篇里没有」** | 写入与检索用的不是同一个 collection（索引分裂） | 见下「索引是否分裂」，重建当前版本索引一次对齐 |
| 公网时通时不通 | 国际出口丢包（已知问题） | 改用 `localhost:8080` 或局域网 IP 演示，公网只作备注 |

**镜像是否同源**（两条都必须是 `True`）：

```bash
docker compose exec -T api    python -c "import inspect;from app.models.entities import Chunk;print('anchors' in inspect.signature(Chunk.__init__).parameters)"
docker compose exec -T worker python -c "import inspect;from app.models.entities import Chunk;print('anchors' in inspect.signature(Chunk.__init__).parameters)"
```

**索引是否分裂**（检索用的集合点数应等于 SQLite 的 chunk 总数）：

```bash
# SQLite 侧
docker compose exec -T api python -c "import sqlite3;c=sqlite3.connect('/app/data/ai4s.db');print('chunks:',c.execute('select count(*) from chunks').fetchone()[0])"
# 路由指向哪个集合，它有多少点
docker compose exec -T api python -c "import sqlite3;c=sqlite3.connect('/app/data/ai4s.db');print(c.execute(\"select collection from index_versions v join index_routing r on r.pipeline_version=v.pipeline_version where r.scope='global'\").fetchone())"
curl -s localhost:6333/collections/<上面的集合名> | python -c "import json,sys;print('points:',json.load(sys.stdin)['result']['points_count'])"
```

两个数对不上就是分裂了，处置：`POST /api/v1/index/rebuild`（`background:true`，314 片段约 9 分钟，期间不要重启 worker）。

**一条命令看全貌**：`bash deploy/demo-check.sh`（不加 `--with-qa` 不消耗 LLM 额度）。
