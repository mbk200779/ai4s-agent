# 2.24 库外推荐：库内答不出时，去 arXiv 找几篇补进来

## 1. 问题

空检索卡片（`docs/2.16`）已经把「库里没有」说清楚了，也给了「换个问法」这个出口。
但有一类问题换多少种说法都没有用：**库里根本没有这个主题的论文**。

实测现场：库里只有 5 篇 Transformer / BERT / LoRA / ViT，问「RAG 如何缓解大模型幻觉」——
关键词 `rag` / `alleviate` / `hallucinations` 在库内命中 0 段，卡片如实说「库里没有能支撑这个问题的内容」，
然后呢？用户手上没有任何一个动作能改变下一次的结果。

这一条链路上缺的不是又一句解释，而是一个**能改变库内容**的动作。

## 2. 做法

空检索卡片里新增「库外推荐 · arXiv」：按问句关键词去 arXiv 检索，列出库里没有的论文，
每条给出标题、摘要、原文链接、以及**可核对的相关性说明**，并提供「一键导入数据库」。

```
空检索卡片
├─ 已检索范围 / 关键词命中表        ← 12 已有：证明"我们找过了"
├─ 换个问法（库内三条建议）          ← 12 已有：低成本出路
├─ 库外推荐 · arXiv                 ← 本文：能改变下一次结果的那条路
│   ├─ 候选卡片 × N
│   │   ├─ arXiv:ID · 年份 · 分类        相关性 强/中/弱 · 0.73
│   │   ├─ 标题（点开 abs 页）
│   │   ├─ 摘要（2 行，可展开）
│   │   ├─ 为什么推荐：标题命中 rag；摘要命中 alleviate、hallucinations…
│   │   ├─ 摘要原句（命中最多的那一句）
│   │   └─ [一键导入数据库] [看原文 ↗]  → 进度 / 已入库 / 失败原因
│   └─ 脚注：相关性只按词面命中计算，不含语义判断
└─ 最近邻（不是证据）                ← 12 已有：纯解释
```

顺序是刻意排的：先库内两条低成本出路，再「补库」这条能改变结果的出路，最后才是看近邻这种纯解释。

## 3. 为什么只接 arXiv

| 候选源 | 能否一键入库 | 可用性（实测） | 结论 |
| --- | --- | --- | --- |
| arXiv Atom API | **能**，入库链路只认 arXiv ID | 无 key 无配额，1.0~1.4 s/次 | 采用 |
| Semantic Scholar | 部分（有 arXiv ID 的才可导） | 无 key 时连续 **429** | 不用 |
| OpenAlex | 部分 | 有 key 义务、arXiv 覆盖不全 | 不用 |

决定性的一条是"能不能导进来"：推荐一条进来后点导入只能失败的论文，比不推荐更糟。
S2 无 key 实测 429（本项目就没有 key），把它做成主路径等于把功能交给运气。

## 4. 检索式：为什么必须逐级放宽，又不能乱放宽

arXiv 的 `all:` 是硬 AND：把问句里的词全 AND 起来经常直接 0 条，
而"这次没有"和"检索式太严"在界面上长得一模一样。

两组实测（2026-11-11，同一时段）：

| 检索式 | 「RAG 缓解幻觉」 | 「Transformer vs RNN」 |
| --- | --- | --- |
| 全部词 AND | 8 条 | 6 条 |
| 前 4 词 AND | 8 条 | 8 条 |
| 前 3 词 AND | 8 条 | 8 条（首条 `Procedural Core…`，跑题） |
| 前 2 词 AND | — | 8 条 |
| 按词长取前 3 | 8 条 | 8 条 |

可见"词多"不是主要问题，**空壳词**才是：`core` / `improvement` / `compared` 这类词留在 AND 里，
召回不会归零，但排序会被带到 `Robust Core-Periphery Constrained Transformer` 这种同形不同义的论文上。

于是分两层处理：

1. `_QUERY_STOP` 只用于**构造外部检索式**，滤掉 `core/main/improvement/compare/large/language/model…`。
   它与 `rag/uncertainty.py` 的 `_LATIN_STOP` 分工不同：后者决定"关键词有没有命中"，
   改一个字都会改变空检索判定；前者改错了最多召回变差。
   全被滤掉时退回原表——宁可检索式偏宽，也不要拿空检索式去问 arXiv。
2. 仍按「前 5 词 → 前 3 词 → 前 2 词」逐级退，**只退到够用为止**（剔掉库内已有的之后满 5 条即停）。
   实测「RAG 缓解幻觉」第一档就命中，全程 1.1 s；「蛋白质折叠自由能垒」也 1.1 s。

顺序按问句原序取前缀，不按词长：实测按词长排会先丢掉 `rag` 这种短但决定主题的词——
`hallucinations AND alleviate AND language` 反而 0 条。

## 5. 相关性怎么算、为什么不用模型写一句

三项词面信号，权重不同：

- 标题命中 ×2：标题写了这件事，这篇大概率就是讲这件事；
- 摘要命中 ×1：只说明它被提到过；
- **摘要同句共现 ×2**：一句话里同时出现几个问句关键词，是最接近"这一段在讲这个问题"的证据。

同句共现这一项是排序的关键。实测「RAG 缓解幻觉」：

| 论文 | 标题 | 摘要 | 同句共现 | 得分 | 名次变化 |
| --- | --- | --- | --- | --- | --- |
| CrAM（摘要原句：*RAG can alleviate hallucinations of LLMs…*） | rag | 3/3 | 3 | 0.73 | 原第 2 → **现第 1** |
| 4bit-Quantization in Vector-Embedding for RAG | rag | 3/3（分散在背景段） | 1 | 0.47 | 原第 1 → 掉出前 5 |

这与 12 号空检索用「同段覆盖度」而不是「词是否命中」是同一个理由：
**共现**比**出现**更能说明"这句话在讲这件事"。

**为什么不调 LLM 写一句"这篇论文与你的问题高度相关"**：

1. 这个功能恰恰在 LLM 配额耗尽时最需要可用（本项目实测遇过 `Free quota exhausted`），
   把兜底路径挂在一个会挂的服务上，等于没有兜底；
2. 一句模型评价不可核对，而"标题命中 rag；摘要命中 alleviate、hallucinations"可以当场核；
3. 一次调用要 2~5 s，比检索本身还慢。

代价是它只能说明"词面对上了"，不能说明"语义相关"——所以界面上明写这句免责，
并附上摘要原句让人自己判断。界面上写的是"为什么推荐 / 命中"，不是"相关度 92%"。

过滤门槛：**至少两个关键词**落在标题或摘要里才推荐。只要求一个的话，
检索式退到两词时（`quantum AND …`）会把一堆量子论文全带进来——它们命中的是那个泛词，不是这个问题。

## 6. 去重：两道关，都要给明确反馈

| 关卡 | 位置 | 行为 |
| --- | --- | --- |
| 推荐阶段 | `_library_snapshot()` | 已在库的**不出现**在候选里，单独计数：「另有 N 篇已在库中未重复推荐」 |
| 导入阶段 | `POST /papers/arxiv/import` | 命中 `file_hash` 复用 → `reused=true`，界面显示「跳过重复解析（命中已解析文件，复用 25 个片段）」 |

推荐阶段的判重按 **arxiv_id + 归一化标题**双键。
只按 ID 判会漏掉一类最常见的重复：本地 PDF 上传进来的论文，库里存的 arxiv_id 是
`upload_<hash>`，不是真实 arXiv ID。实测库里那篇 `Attention Is All You Need` 就是这种形态，
它对应的 arXiv 版本 `1706.03762` 若按 ID 判就是"新论文"，导进来就是第二行同名记录。
归一化标题（小写、只留字母数字与汉字、空白折叠）相等即视为已在库——
误判的代价是少一条推荐，比多一条重复记录轻。

## 7. 状态机：四种导入结果都有话说

| 后端返回 | 界面 | 用户的下一步 |
| --- | --- | --- |
| `stage=queued` + `task_id` | 按钮变「排队中 / 解析正文 4%」+ 细进度条；完成后「25 个片段已入库 · 可以用原问题重问了」 | 点「用它重问」，同一个问题再问一遍 |
| `reused=true` | 「跳过重复解析（命中已解析文件，复用 25 个片段）」 | 直接重问 |
| 4xx/5xx | 红字「导入失败：<后端 detail>」，按钮变「重试导入」 | 重试或看原文 |
| 网络异常 | 红字「网络异常，导入请求没发出去」 | 重试 |

进度不复用 `IngestProgressPanel`：那是个整块面板（阶段刻度、片段/文献/引用三行），
塞进一张列表卡片会把推荐列表变成三个进度条组成的长页面。这条路径上用户只需要一行"现在到哪了"，
所以是自带的轻量轮询（1.2 s 一次，10 分钟上限）。

## 8. 检索侧失败与空结果

| status | 文案（后端返回，前端照抄） | 前端动作 |
| --- | --- | --- |
| `ok` | 「在 arXiv 找到 N 篇库里没有的论文，另有 M 篇已在库中未重复推荐」 | 列表 |
| `no_query` | 「这句问话里没有可用的英文实词，arXiv 只支持英文检索」 | 重新检索 |
| `no_result` | 三种：全在库 / 回来 N 篇但都只命中一个词 / arXiv 也没有 | 重新检索 + 显示**真正试过的检索式** |
| `error` | 「arXiv 检索失败（Timeout），稍后再试」 | 重新检索 |

`no_result` 里把试过的检索式原样列出来（`all:rag AND all:alleviate …`），
是因为"没找到"必须可复核——用户看到检索式才能判断是关键词问题还是确实没有。

不翻译：问句的中文 → 英文翻译在问答链路里已经做过一次（空检索卡片上"实际检索文本"那一行），
前端把它原样传给推荐接口（`search_text`），后端不再翻。少一次模型调用，
也少一份"两次翻译不一样"的不确定性。没翻成功时如实说没翻成功，而不是拿中文去检索再回一句"没找到"。

| 推荐接口（首次） | 200，1.1~1.2 s，5 条候选 |

| 候选相关性 | 前三：0.73 / 0.60 / 0.60；「RAG 缓解幻觉」前两条的摘要原句都是 `RAG can alleviate hallucinations…` |
| 一键导入（`2406.11497`） | 14 页 → 解析 4% → 96% → `indexed`，**40 s**，25 个片段 |

## 10. 已知限制

1. **只有 arXiv**。非 arXiv 的论文（期刊、会议无预印本）搜不到。要扩源，先解决"怎么入库"，
   否则会变成一串导不进来的链接。
2. **相关性只有词面**。同义改写（`hallucination` vs `fabrication`）命中不了；
   实测「Transformer 相比 RNN 的核心改进」的候选全是同时含这两个词的论文，
   真正的原论文 `1706.03762` 不在 arXiv 返回的前 12 条里。这一层靠 arXiv 自己的排序，
   我们只做过滤与重排，不能凭空造出语义理解。
3. **缓存 10 分钟 + 会话内缓存**。导入新论文后立刻"重新检索"能看到变化（服务端会重算库状态），
   但 arXiv 侧的结果集会复用缓存，不会重新排。

## 11. 部署注意：这条链路会真的往 Qdrant 写

功能本身只是"多一个导入入口"，但它把「上传后删除」「批量删除」「反复导入同几篇」这几类操作
的频率放大了，于是把一个底层的坑顶到了表面——**Qdrant v1.11.0 的 sparse 倒排索引在
大量 upsert + delete 之后会 panic**：

```
Panic occurred in file lib/sparse/src/index/inverted_index/inverted_index_ram.rs
  at line 63: index out of bounds: the len is 422 but the index is 423
ERROR qdrant::actix::helpers: Can't reach one of the workers: channel closed
```

表现不是"检索变慢"，而是**这个 collection 的所有写操作 500**：新论文一律解析失败
（`UnexpectedResponse: ... Can't reach one of the workers: channel closed`，重试三次后落 `failed`），
而已经建好的向量还能读，所以问答看起来是好的，只有入库坏了——极易误判成解析器的问题。

恢复步骤（本次实测有效，数据源始终是 SQLite，向量只是派生视图）：

```bash
docker stop ai4s-qdrant
docker run --rm -v <项目>_qdrant_storage:/q alpine sh -c \
  "mv /q/collections/<坏掉的 collection> /q/collections/<坏掉的 collection>.broken-$(date +%Y%m%d)"
docker start ai4s-qdrant
# 从 chunks 表重新编码（30 个片段 21 s，279 个片段约 3 min）
curl -X POST localhost:8000/api/v1/index/rebuild \
  -H 'Content-Type: application/json' \
  -d '{"target_version":"<当前写版本>","background":false,"note":"sparse 索引 panic 后重建"}'
```

重建后 `points_written` 应与 `total_chunks` 相等；随后用任意一篇库内论文问一句，
有 `[引#N]` 回答即恢复。**坏掉的目录不要直接删**，先改名留档，确认无误再清。

另：`import_arxiv` 已改成同步 `def`（跑在线程池），避免下载 PDF 的几秒把事件循环按住；
同一篇**解析失败过**的论文再次导入时，会先 `reset_for_retry`（保留 `parse_cursor`）
再入队——否则 `attempt` 已到上限，点「重试导入」只会立刻再失败一次。
