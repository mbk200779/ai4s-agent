# 2.12 综述生成：观点聚类与冲突标注

> 任务 08。目标是让「综述」真的成为综述，而不是把检索片段换个顺序拼起来。
> 本文只写**做出的选择与代价**，接口字段、prompt 全文见代码：
> `backend/app/services/review/`、`backend/app/schemas/review.py`、
> `frontend/src/components/review/`。

## 1. 问题：综述为什么必然写成「摘要拼接」

08 之前的 `review_service.generate` 是这么干的：检索 top-k → 拼成上下文 → 一段 prompt 让它写 Markdown。这个做法有三个结构性缺陷，不是调 prompt 能解决的：

1. **一篇论文刷满证据池。** 按相关度排序，同一篇论文的不同段落天然最像主题；top-10 里八段来自同一篇，写出来就是"这一篇的摘要"。
2. **反例永远排不到一起。** 反例片段措辞更保守、和主题的相似度更低，单次 top-k 基本捞不到。检测不到反例，综述就只会有一面之词。
3. **模型遇到矛盾只能含糊。** 当上下文里同时躺着"A 优于 B"和"B 优于 A"，而输出又要求"连贯的综述"时，模型的唯一出路就是写「研究表明两类方法各有优势」——**这正是任务书禁止的那句话**。它会这么写不是因为不听话，是因为没有别的写法可选。

所以 08 换掉了中间表示：先算出**观点结构**（谁在说什么、有几个人在说、谁反对），再按结构写。模型只负责"在给定的簇里把话说顺"，它不再有机会把两个相反结论焊成一句。

## 2. 流水线

```
证据池  →  claim 抽取  →  观点聚类  →  冲突检测  →  按簇渲染  →  claim 表
pool.py    claims.py      cluster.py    conflict.py   generate.py   service.py
```

| 阶段 | 输入 | 输出 | 失败时 |
|---|---|---|---|
| 证据池 | 主题 | 15~20 段正文（含来源标记） | 空池 → 拒答 |
| claim 抽取 | 片段（分批并行） | claim（statement / axis / polarity / condition / quote） | 单批失败只丢该批 |
| 观点聚类 | claim 列表 | 观点簇（立场、篇数、证据） | 语义模型不可用 → 字面归并 |
| 冲突检测 | 簇列表 | 冲突边（类型、判据、三态 confirmed） | LLM 不可用 → `confirmed=null` 待复核 |
| 正文生成 | 簇 + 冲突边 | 每簇一组带引用的句子 | 模型不可用 → 模板兜底 + `degraded=true` |

四次模型调用（抽取可并行、轴归一化一次、冲突复核一次、写正文一次），实测总耗时 **54~85 秒**。

## 3. claim 抽取：为什么必须带 axis + polarity + condition

一条结论的完整身份是 `(axis, polarity, condition)` 三元组，缺一个都会在后面的环节出事：

- **`axis`（比较轴）**：这条结论在判断哪个维度，写成 `对象A 相对 对象B：指标`。它是聚簇的主键。
- **`polarity`（极性）**：沿这条维度的方向。`support` 支持正向主张、`oppose` 主张反向、`conditional` 只在条件下成立。
- **`condition`（条件）**：数据集规模、模型规模、任务类型、语言等前提。

三条硬性处理：

1. **有前提却标 support 的，强制降级为 conditional。** 「在 X 条件下 A 优于 B」和「A 优于 B」是两条不同的结论；混在一起，冲突判定会把"条件不同"当成"结论互斥"。
2. **引文必须回贴原文。** `quote` 用两段式匹配回原文核对：先做归一化子串匹配（处理 PDF 的断行连字符、弯引号、ﬁ 连字），失败再按 token 覆盖率在句级窗口里找 ≥0.7 的句子。都不过就**丢弃**并记 `quote_not_found`——模型改写过的引文不是证据。

   核对的对象不能只是"模型声明的那个片段号"。实测一次运行 10 条 claim 丢了 7 条，原因是模型把 3 号片段里的句子挂到了 4 号上（同一批塞 6 段时很常见），而那 7 句在池内另一段上的覆盖率是 0.9~1.0：错的是编号，不是引文。所以判定失败后要在整个证据池里回搜一遍（`_search_pool`），命中就采用真实所在片段的 `chunk_id / 页码 / arXiv`，`chunk_index` 跟着改，claim 上记 `extra.relocated`。回搜的前提没变——引文必须在这批原文里逐字存在，所以不会放过编造的句子。修前 12 段证据只出 3 个观点簇，修后同题 8 条结论 0 条被丢。
3. **反向与限定结论优先抽。** prompt 里点名列出「不如／更差／落后／few percentage points below／仅在……时成立／较小数据集」，要求必须单独成条。实测这条要求把 `oppose` 类 claim 从 0 条提到了 2~4 条——**冲突标注的前提是先把反例抽出来**。

## 4. 观点聚类：极性是簇键的一部分

本模块只有一条不变量，其余都是实现细节：

> **相反结论永远进不了同一个簇。**

为什么必须是结构约束而不是 prompt 约束：「LoRA 匹配全量微调」与「LoRA 不如全量微调」的余弦相似度能到 0.9+，只要按语义相似度聚类就必然合并；一旦合并，写手拿到的就是一个"中性簇"，它只能写出「研究表明两者关系复杂」。把 `polarity` 放进簇键之后，这两条从聚类那一刻起就分属两簇，**生成阶段没有"把它们写在一起"的输出位置**。

簇键 = `(规范化轴, 极性)`，三步构造：

1. **轴归并（LLM 为主）。** 同一维度的措辞会漂（`ViT 相对 BiT ResNet：ImageNet 准确率` / `ViT 相对 ResNet：ImageNet 准确率`），靠阈值调参解决不了——`Transformer：下游任务性能` 与 `BERT 相对 其他系统：GLUE测试准确率` 余弦不低但根本不是同一个轴。只有"看懂维度是否相同"才能归并，所以交给 LLM 输出 `{canonical, members}`。
2. **实体重叠闸（不信任模型的那一层）。** LLM 归并结果要过一道确定性检查：标准轴与成员轴的**拉丁实体集合必须有交集**。实测挡掉了两处错误归并——模型试图把 `Vision Transformers：方法设计`、`ViT：方法设计` 并进 `Transformer：方法设计`，这三者的对象根本不是一回事（被挡下的记录在 `trace.cluster.rejected_merges`）。
3. **同轴同极性再按结论相似度切一刀。** 轴是模型给的标签，它会打错：实测有一条「ViT 把图像切成 16×16 的块再线性嵌入」被打上 `ImageNet 准确率` 的轴，于是它和真正比准确率的结论落进同一桶，接着与"小数据下 ResNet 更好"配成一对，被复核模型硬解释成"条件性分歧"。轴是模型的**判断**，结论文本是**事实**，两者一致才允许合并（`review_statement_split_sim=0.5`）。

排序全确定性：`(论文数倒序, claim 数倒序, 轴键, 极性)`，所以同样的输入两次运行簇编号不会漂。

簇的 `id` 就是排序后的序号，直接写成阿拉伯数字 `1 / 2 / 3…`（`cluster.py`），正文标题因此是 `## 1｜结论…`。早先用的是 `O1/O2`（O = 观点簇的英文缩写），纯粹是展示序号、没有分类或引用含义；换掉的原因是它和正文里的引用编号 `[引#N]` 并排出现时是两套字母体系，读者要多分辨一次。改数字后有一处必须配套：**冲突块不能也用纯数字**，否则与章节号撞号，所以冲突边的 `id` 是 `冲突1 / 冲突2`，且冲突块以 `###` 挂在所属章节之下而不是平级 `##`。另外凡涉及 id 的地方都只能按**列表位置**排序，不能按字符串比大小（`"10" < "9"`）。

## 5. 冲突检测：规则召回 + LLM 复核

**召回条件是"同轴 且 方向相反"，其中至少一边必须是 `oppose`。**

这一条踩过坑：最初写成 `polarity !=`，于是 `support` 与 `conditional` 也被当成冲突候选——「LoRA 不增加推理延迟」和「LoRA 在短序列下延迟更低」是**同方向、不同范围**的两句话，被配成一对之后，复核模型还将错就错地给出了"条件不同导致分歧"的理由。`support` 与 `conditional` 不是互斥关系，只有 `oppose` 才构成对立。

之后还有一道 **结论相似度闸（0.6）**：一对互斥结论必须"说的是同一件事、只是方向相反"。实测该闸把误报对（0.526）和真冲突对（0.702）干净地分开了。

复核给三类型，**外加三态 confirmed**：

| 类型 | 含义 | confirmed |
|---|---|---|
| `direct_contradiction` | 同一条件范围内互相否定，不可能同真 | true |
| `conditional_split` | 各自在自己的条件下成立，分歧来自条件差异 | true |
| `scope_mismatch` | 比较对象/指标其实不同，不构成矛盾 | false |

`confirmed` 是三态而不是布尔：`null` 表示"规则召回了但没排进复核批次"。压成两态会把"没核实"和"核实过不算冲突"混为一谈。**被否掉的冲突也返回**（`confirmed=false`），界面上折叠显示——读者看到两条像是矛盾的结论而系统没标冲突时，会怀疑漏检；把"系统看过、判为不相干"的那些摊开，疑问就消失了。排除也是结论，也要能被审计。

## 6. 三条约束的落实位置

任务书的三条约束都没有写在 prompt 里求模型自觉，而是落在渲染器上：

| 约束 | 落实位置 | 机制 |
|---|---|---|
| 不得把相反结论合并成一句「研究表明」 | 聚类 + 渲染 | 极性是簇键（结构上不可能同段）；冲突簇里出现「研究表明／普遍认为／存在争议」等措辞的句子判违规删除 |
| 每条结论至少 1 条引用 | 渲染 | 句子必须带 `[引#N]` 且编号落在该簇证据集合内，否则**整句删除**（不是替换成「无依据」留在正文——那仍是在正文里说话） |
| 单篇支持必须标注「仅单篇支持」 | 渲染 | 由 `paper_count` 决定，模型写不写都不影响 |

正文是**服务端渲染**的：模型只输出 `{cluster_id, text}`，标题、立场徽标、证据篇数、条件、冲突块全部由渲染器生成。三个后果：模型没有"合并两簇"的位置；`仅单篇支持` 不会因为它忘记而消失；冲突块的判据一定来自复核结果而不是模型复述。

### 6.1 为什么让模型写行内 `[引#N]`，而不是 `refs: [2,8]`

最初的设计是 `{"text": "...", "refs": [2, 8]}`。实测模型会把字段名写进正文——`……参数数量。refs":[2]`——**整块 JSON 因此解析失败，只能整体降级成模板，全篇变成模板腔**。改成行内 `[引#N]`（本项目 QA 链路用了很久的约定，模型几乎不出错）之后，JSON 结构简化成"一个字符串"，解析失败率降了一个量级；句子边界与引用归属由服务端切。

### 6.2 分句必须连引用一起切

模型按约定写「……推理延迟更低。[引#2]」——引用在**句号之后**。如果只在句号处切，`[引#2]` 会被甩到下一句开头：本句"没有引用"被判删除，下一句凭空多出一个引用，整篇引用归属全错位。实测这个 bug 让 15 个簇各自丢掉第一句，直接触发模板降级。

正确的句子单元是「到句末标点为止的正文 + 紧跟其后的引用标记」，正则：

```python
_UNIT_RE = re.compile(r"[^。！？!?]*(?:[。！？!?]+|$)(?:[\[［]引#\d+[\]］])*")
```

### 6.3 抹平措辞只在冲突簇里判违规

早先是对全文一律检查，结果一条讲 LoRA 秩的句子因为写了「研究表明」被删掉——它压根不涉及任何分歧，那只是行文习惯。禁令要落在"可能被用来抹平分歧"的位置，否则就成了对文风的独裁。

### 6.4 降级不静默

- 模型漏写某个簇 → 该簇用模板补齐，响应体 `degraded=true`；
- 填不满 60% 的簇 → 带明确提醒重问一次，取更好的那份；
- 模型完全不可用 → 全篇模板（簇结论 + 原文引文），`degraded=true` 并在界面顶部明示。

## 7. Prompt 版本与配置

两条**独立**的版本线，缺一不可：

```python
REVIEW_PROMPT_VERSION = "review-v1.2.0"     # 管三个 prompt 的文本
settings.review_version = "rev-v1.0.0"      # 管阈值
```

`review-v1.2.0` 的改动只有一处：写手 prompt 里 `cluster_id` 的示例从 `"O1"` 改成 `"1"`，配合簇编号数字化。示例不改会让模型照着 `O1` 的格式回填、与实际的 `1` 对不上，整段被丢弃。

响应体 `config` 回显 `version / prompt_version / fingerprint`。为什么分开记：调阈值不改 prompt 才是常态，只留一个号就会出现"版本号没变但结果全变了"的不可解释状态；反过来把综述 prompt 塞进全局 `PROMPTS[prompt_version]`，会让"改综述"必须连带 bump 问答的版本号。

阈值全部可配（改动请同时 bump `review_version`）：

| 配置 | 默认 | 作用 |
|---|---|---|
| `review_pool_per_paper` | 5 | 单篇进池上限（防一篇刷满） |
| `review_pool_max_chunks` | 20 | 证据池总量 |
| `review_subqueries` | 3 | 视角检索条数（专治"反例捞不到"） |
| `review_claim_batch` | 12 | 单批片段数（并行抽取） |
| `review_axis_merge_sim` | 0.78 | 轴归并的**兜底**阈值（仅 LLM 不可用时） |
| `review_statement_split_sim` | 0.5 | 同桶内按结论相似度二次切分 |
| `review_conflict_axis_sim` | 0.72 | 冲突二次召回的轴相似度 |
| `review_conflict_statement_sim` | 0.6 | 冲突对"说的是同一件事"的闸 |
| `review_conflict_llm_pairs` | 6 | 送复核的对数上限 |

## 8. 返回结构

`POST /api/v1/review/generate` 返回三件套，共用一套证据编号：

```jsonc
{
  "markdown": "……正文，含冲突块……",
  "claims": [                       // claim 表：一行 = 一个观点簇
    {
      "id": "O13", "statement": "ViT 在小规模数据集上的表现不如 BiT ResNets",
      "axis": "ViT 相对 BiT ResNet：ImageNet 准确率",
      "stance": "oppose", "stance_label": "反对",
      "strength": "single_paper", "paper_count": 1, "claim_count": 1,
      "papers": [{"arxiv_id": "2010.11929", "title": "..."}],
      "conditions": ["在小规模数据集上"],
      "evidence": [{"quote": "While large ViT models perform worse than BiT ResNets...",
                    "page": 7, "ref": 1, "quote_score": 1.0}],
      "refs": [1], "sentence_count": 1,
      "conflicts": [{"id": "C1", "with_cluster": "O14", "type": "conditional_split", ...}],
      "note": "仅单篇支持"
    }
  ],
  "conflicts": [                    // 冲突边：confirmed 三态
    {"id": "C1", "clusters": ["O13", "O14"], "type": "conditional_split",
     "type_label": "条件性分歧", "confirmed": true,
     "reason": "A 和 B 的结论分别基于小规模数据集和大规模数据集，条件不同导致了表现差异。",
     "rule": {"axis_match": "exact", "axis_sim": 1.0, "stances": ["oppose", "support"]}}
  ],
  "refs": [{"n": 1, "arxiv_id": "2010.11929", "page": 7, ...}],
  "stats": {...}, "config": {...}, "degraded": false,
  "trace": {"timing": {...}, "cluster": {...}, "conflict": {...}, "dropped_claims": [...]}
}
```

`trace` 是有意暴露的：轴归并的每一次合并与被拒、结论切分、被丢弃的 claim 与句子、各阶段耗时都在里面。调参和答辩复盘靠它，不靠猜。

### 8.1 界面

综述页从"一个 Markdown 框"改成四块：**概览条**（文献/结论/观点簇/冲突/仅单篇/立场分布）、**正文**、**观点表**、**冲突与分歧**。

观点表一行一个簇，表头写死在界面上：`结论（一行 = 一个观点簇）｜立场｜论文 / 证据｜证据强度｜冲突`。点行展开该簇的每条证据原文（引文编号、arXiv·页码·章节、英文原句、对应结论）。`仅单篇支持` 是独立一列而不是脚注——它和结论本身同级，读者据此决定要不要自己去补第二篇。

表头是后加的：一开始没有列头，`1 篇 / 2 条` 这种数字读者只能靠猜是"论文数/证据数"还是"证据数/句子数"。凡是列里塞了缩写数字，列名就必须写在脸上。

冲突卡片并排展示两方（立场、篇数、成立条件），下面是复核判据与轴；被否掉的折叠在"已复核排除的疑似冲突"里。

## 10. 已知局限

1. **本次 15 个观点全部"仅单篇支持"。** 这是语料的问题，不是聚类的问题：库里只有 5 篇论文（BERT、ViT、LoRA、Attention、一篇孤子分子），主题分散，没有两篇在同一个轴上正面交锋。系统如实地把这件事标出来了（界面上也有一条说明），而不是把"单篇"包装成"多篇一致"。要让"多篇支持"成为常态，需要同一主题下 ≥3 篇论文——这是语料建设的任务。
2. **抽取有方差。** 同一主题多次运行，claim 数 9~17、簇数 9~18 会浮动（`temperature=0` 仍不能保证端点完全确定）。所以做对比实验必须看 `review_sample.json` 这类落盘产物，不能凭"我记得上次是 12 个簇"。
3. **会有非结论句混入。** 像「ViT 将图像分割成固定大小的块」这种方法描述也被抽成了 claim。它不影响三条约束，但会让综述显得啰嗦。下一步可以给 claim 加"是否可判定"的置信度，只让高置信的进正文、低置信的留在表里。
4. **中文结论 ↔ 英文原文的相似度**沿用了 07 的跨语言模型；对术语密度极高的句子（公式、型号）仍会偏低，表现为该簇更容易被切分。

## 11. 踩坑清单

1. **`polarity != ` 当冲突条件** → `support` vs `conditional` 大规模误报，改成"至少一边是 `oppose`"。
2. **检索 top-k 直接当证据池** → 表格片段（逐列扫描的残渣 `| | |`、逆向文本）刷满池子。证据池只收 `paragraph`，且**检索量 ≠ 保留量**（拿 20 条筛 5 条，不能只要 5 条）。
3. **全库逐篇补检** → 把跑题论文（孤子分子）也拉进来，抽出一条语气正式、引文真实但彻底跑题的结论。改成"只补主题已命中的论文"。
4. **无锚点/错误轴的结论被并簇** → 轴是模型判断、结论文本是事实，加"结论相似度"二次切分。
5. **LLM 轴归并过度** → 加"实体必须重叠"的确定性闸，挡下 `ViT：方法设计` → `Transformer：方法设计`。
6. **JSON 里放 `refs` 数组** → 模型把字段名写进正文导致整块解析失败、全篇模板降级，改成行内 `[引#N]`。
7. **在句号处切句** → 引用被甩到下一句，引用归属整体错位、15 簇各丢首句。句子单元必须包含尾随引用。
8. **抹平措辞全文检查** → 删掉了大量正常句子（"研究表明"只是行文习惯），收窄到冲突簇。
9. **`next build` 报 `EPERM: open '.next/trace'`** → 误判成"文件被占用"，删目录、换目录、改 `node bin/next` 全无效。真因是命令跑在受限沙箱里，写不了那个 trace 文件；Next 的 `setup-exception-listeners.js` 把任何 uncaught 直接 `process.exit(1)`，于是整个构建 10 秒就死。放开沙箱后一次通过。**遇到 `EPERM` 先怀疑执行环境，别急着删文件。**
10. **`docker restart` 不重读 compose 环境变量**（沿用 06/07 的坑）；`rm -rf .next` 会被 bulk-delete 守卫拦，用 `mv .next .next_old` 改名后再建。
11. **列头缺失导致表格自解释失败** → `1 篇 / 2 条` 没有列名就是天书。界面上的每个缩写数字都必须有列头。
